# 프론트 실시간 로그 탐색

2026-10-28. [공통 SSE 합의](feature-development-workflow.md#2026-10-28-sse-조회-후속-합의), [프론트 처리 기준](contracts/frontend-integration-draft.md#2026-10-28-sse-후속-승인-프론트-처리-기준), [백엔드 API](contracts/log-sse.md)를 구현하는 작업이다. 기존 [정적 목록·상세 연결 기록](frontend-log-view.md)은 당시 동작과 이유를 보존한다.

## 데이터가 화면에 도착하는 순서

요청마다 SSR에서 `/api/v1/logs/live`를 한 번 조회한다. items·cursor·from·to·truncated를 같은 snapshot으로 브라우저에 인계하고 브라우저는 중복 snapshot 조회 없이 `/api/logs/stream?after=...`로 연결한다. 내부 API 주소와 파일 설정은 서버 전용으로 유지한다. 기존 `/api/logs?from=...&to=...`와 상세 중계는 유지한다.

Next.js 중계는 고정된 GET 경로만 허용하고 query·cursor의 ASCII 길이를 확인한다. cursor는 최대 56바이트의 불투명 문자열로 전달하며 내부 순서를 JavaScript Number로 해석하지 않는다. 중계는 브라우저에서 전달한 임의 주소·헤더를 상류로 전달하지 않는다. Last-Event-ID를 받으면 after와 둘 다 검사한 뒤 헤더 값을 우선한다.

fetch SSE 파서는 UTF-8·줄·프레임의 네트워크 분할을 처리한다. CR 단독 줄끝은 다음 바이트를 기다리지 않고 처리하며 CRLF는 한 줄끝으로 해석한다. CR로 끝나는 프레임에는 뒤따를 수 있는 LF 한 바이트의 여유를 확보한다. ready는 연결 안내이며 처리 cursor를 변경하지 않는다. log는 JSON·summary·id/data.cursor 일치와 화면 상태 처리가 모두 성공한 뒤 cursor를 갱신한다. 잘못된 프레임 뒤의 위치로 건너뛰지 않는다. 같은 eventId는 현재 목록에서 중복 제거한다. 범위 밖 로그도 정상 처리한 cursor는 갱신한다.

## 최근 24시간과 최신 50건

서버 snapshot의 to를 시계의 출발점으로 삼고 브라우저의 단조 증가 시계인 performance.now 경과 시간을 더한다. 브라우저 벽시계 설정이 달라도 표시 범위가 며칠씩 이동하지 않게 하기 위한 선택이다. 네트워크·hydration 지연이나 장시간 시계 오차를 완전히 보정하는 시각 동기화 프로토콜은 아니다. 수동 새로고침 성공 시 서버 기준점을 다시 받는다. 조회 성공·실시간 로그 수신 시각의 표시는 구분하며 heartbeat는 로그 수신 시각을 갱신하지 않는다.

활성 화면은 1초마다 범위를 이동하고 `[from, to)` 밖의 행을 제거한다. 삽입 때도 현재 범위를 다시 검사한다. 발생시각/eventId 내림차순으로 정렬하고 메모리에는 최신 50건만 남긴다. snapshot 잘림 또는 수신 중 상한 초과 안내는 다음 성공 snapshot까지 유지한다. 이는 화면에서 잘린 이력이 있다는 안내이며 DB의 전체 건수 추정이 아니다. 미래 로그는 수신 시 제외하고 보류 큐를 만들지 않으며 나중 자동 표시를 약속하지 않는다. 새 snapshot에서 다시 평가한다.

## 연결과 사용자의 조작

- 기본은 자동 연결이다. 정지하면 연결·재시도·로컬 만료를 중단하고 목록·cursor·상세와 정지 시각을 보존한다. 재개하면 범위를 재평가하고 마지막 처리 cursor부터 replay한다.
- 수동 새로고침은 이전 연결을 취소하고 새 snapshot을 받는다. 성공했을 때만 목록·cursor를 교체하고 상세를 닫는다. 실패하면 기존 결과·cursor·완료된 상세를 유지하며 연결을 이어받는다. 정지 중 새로고침해도 정지를 유지한다.
- 정상 EOF는 장애 문구 없이 3초 후 같은 처리 위치에서 연결한다. 실패는 3·6·12·24·30초 상한으로 재시도한다. 정상 로그 처리, 정상 EOF 또는 ready 후 15초 이상 유지한 연결의 실패는 다음 대기의 기준을 초기화한다. ready만 받은 짧은 실패 연결은 초기화하지 않는다.
- HTTP 400·409는 자동 반복하거나 새 snapshot으로 조용히 교체하지 않는다. 기존 결과와 명시적인 새 목록 조회 안내를 유지한다. 503·전송 장애·stream-error는 기존 결과를 보존하고 다시 연결한다. 연결 실패 자체를 저장 중단·유실로 표시하지 않는다.
- cursor는 현재 화면의 메모리에만 보관한다. 정지·unmount·문서 이동은 상류 요청을 취소한다. 재진입은 새 SSR snapshot으로 시작하며 영구 복구·전체 이력 보존을 보장하지 않는다.

## 자원 제한과 읽던 위치

연결 시작 5초·바이트 수신 idle 35초·완성/미완성 프레임 64KiB를 중계와 클라이언트에 적용한다. heartbeat도 idle을 갱신한다. JSON 조회의 총 기한을 장기 스트림에 적용하지 않는다. 중계는 pull에 따라 한 조각씩 전달하고 별도 무한 이벤트 큐를 만들지 않는다. 요청 취소·EOF·오류 때 reader와 상류 fetch, 타이머를 정리한다. 이 값은 개발 환경의 구현 기준이며 운영 프록시·부하 SLA가 아니다.

새 로그는 상세 선택과 진행 중인 상세 요청을 초기화하지 않는다. 선택 행이 목록에서 빠져도 상세를 유지한다. 닫을 때 기존 버튼이 사라졌으면 목록 제목으로 초점을 옮긴다. 자동 삽입·만료 때 보이는 행 또는 상세 원문의 위치와 표의 가로 스크롤을 보정하며, 초점이 있던 행 자체가 사라졌으면 목록 제목으로 안전하게 옮긴다. 새 로그 수는 이번 snapshot 이후 표시 목록에 추가된 건수이며 DB 전체 건수가 아니다.

## 검증과 남은 범위

기존 키보드·상세·원문 복사·모바일·확대·중계 검사를 유지한다. 합성 서버로 snapshot~연결 사이 저장, replay·중복·지연/동일시각·범위 밖/미래·만료·50건, 정지/재개·새로고침, ready/정상 EOF·400/409/503/DB 오류, UTF-8/CRLF 분할·잘못된 JSON·크기/기한·취소와 읽던 위치를 검사한다. 별도 MySQL·Spring Boot·Next.js 이미지에서는 실제 저장, SSR 및 연결 직전·정지 중 저장한 로그의 replay와 상세 보존을 검사한다. 전체 검증 진입점은 `./scripts/verify.sh`다.

검색·필터·커서 페이지·집계·트래픽·다크 모드는 이번 범위가 아니다. 인증·운영 프록시·여러 앱의 즉시 fan-out·고부하·장기 보존과 브라우저별 검증은 후속 범위다. SSE만으로 전체 이력이나 무손실 전달을 보장하지 않는다.

참고: [WHATWG SSE 처리 규칙](https://html.spec.whatwg.org/multipage/server-sent-events.html#parsing-an-event-stream), [Next.js Route Handler](https://nextjs.org/docs/app/api-reference/file-conventions/route).

## 변경 이유

- 2026-10-28: 사용자가 최신 main의 SSE 명세에 따른 프론트 구현을 지시했다. 정적 snapshot 한 번으로 끝나던 화면에 처리 cursor 기반 연결·복구를 추가하고, 최신 50건 화면과 DB replay의 의미를 구분했다. 상세 중계와 기존 오류 보존·접근성 동작은 유지한다. 최초 snapshot과 수동 재조회는 서버가 계산하는 최근 24시간을 사용하므로 이전 정적 조회의 같은 절대 범위 재시도 UI는 새 snapshot 재조회 안내로 대체한다. 정적 API의 시각 조건과 50건 초과 오류는 유지한다. 실제 필수 검증과 작업 커밋 후 학습 문서에 별도 기록한다.
