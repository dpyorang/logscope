# MVP 추가 합의 추천안과 결정 이유


> 2026-10-27 후속 사용자 승인: [기능 단위 개발 방식](../feature-development-workflow.md)을 따른다. 이 문서는 추천·이유를 보존하는 자료이며 모든 항목을 구현 시작 전에 확정할 필요는 없다. Java Gradle·프론트 npm 역할과 verify.sh 공통 진입점·기존 검증 유지·프론트 검사 추가 원칙은 확정됐다. 그 밖의 제안은 해당 기능 착수 시 필요한 범위만 결정한다. 기능 구현은 별도 요청 전까지 시작하지 않는다.

2026-10-27 검토 제안. 아래 내용은 확정 정책이 아니며, 사용자와 담당 분야의 합의 후 해당 정책·명세에 반영한다. [확정 기준](mvp-spec-alignment.md)과 [공통 아키텍처](../architecture.md)를 먼저 참고한다. 문서 작성은 기능 구현 승인이 아니다.


인프라의 구체적인 설정값·산정 이유·미결정 항목은 [MVP 인프라 추천안](mvp-infrastructure-proposals.md)에 별도 제안으로 보존한다. 해당 값은 총괄 합의 전 적용하지 않는다.

## 빌드와 전체 검증

**추천:** Java는 Gradle 9.8.2 Wrapper·Kotlin DSL, frontend는 npm으로 책임을 나누고 scripts/verify.sh가 순서대로 양쪽 필수 검사를 실행한다. 최초 제안 당시에는 기존 Gradle만 사용 규칙을 수정하지 않았다. 이후 사용자 승인으로 역할 분리 원칙을 AGENTS.md에 반영했으며 실제 검사 연결은 프론트 도입 단계에서 정한다.

이유는 프론트 도구를 자연스럽게 사용하면서 기존 서버 검증을 그대로 유지하고, 커밋 전 한 명령으로 실패를 확인하기 위해서다. Gradle에서 npm을 감싸는 추가 연결은 첫 MVP에서는 피하는 안이다.

총괄·프론트·인프라가 다음을 합의한다.

- Java 빌드·실제 MySQL 테스트·Spotless·비밀 검사·Compose·이미지 검증 유지.
- Node/npm 실제 버전 확인, npm ci, 타입·lint·format 검사, Next 빌드·이미지 검증 추가.
- UI 검증 도구·보조 도구 버전과 최소 필수 시나리오 확정. 각 단계 실패 시 커밋을 막고 테스트 생략·조건부 우회를 두지 않음.
- 새 검증 정책 확정 시 별도 문서와 AGENTS.md에 역할·명령·실패 기준 기록. 지금 스크립트와 Actions는 수정하지 않음.

## 실행 구성과 캐시

**추천:** Next Node 서버와 Spring Boot를 별도 컨테이너로 실행하고, MySQL·샘플 WAS와 함께 Compose로 구성한다. 브라우저는 Next에 접속하고 내부 조회 주소는 서버 전용 파일·환경 설정으로 주입한다.

이유는 SSR 실행과 Java 업무 로직의 책임을 분리하고 각각의 이미지·상태를 확인하기 위해서다. 포트, 외부 바인딩, health 확인, 의존 서비스 준비 대기, 빌드 산출물·캐시 헤더는 인프라·프론트가 정한다. health 검사가 매번 로그 검색을 수행하지 않는 구성을 권장한다. 초기 실행은 한 WAS로 검증하고 이후 세 대로 확대한다.

외부 프록시가 있다면 HTML·조회 응답을 캐시하지 않는 규칙까지 맞춘다. 실제 운영 배포·인증·TLS 선정은 이 로컬 MVP 구성과 분리하며 명시적 실행 승인 원칙을 유지한다.

## 조회 중계와 오류

**추천:** 브라우저용 GET /api/logs 및 /api/logs/{eventId}만 Spring Boot의 기존 목록·상세에 연결한다. 수집 POST와 임의 URL 중계는 제공하지 않는다. 불투명 커서와 쿼리를 명세대로 전달하고 내부 API 주소는 브라우저에 노출하지 않는다.

이유는 같은 출처의 제한된 조회 경로를 제공하면서 검색·검증을 Spring Boot에 유지하기 위해서다. 중계는 인증을 대신하지 않는다.

백엔드·프론트·인프라가 오류 매핑을 함께 확정한다. 제안 시작점은 백엔드의 유효한 오류 상태·code·errors·Retry-After 보존, 연결 실패·비JSON 또는 잘못된 성공 응답은 안전한 502 중계 오류, 중계 기한 초과는 안전한 504 오류로 구분하는 것이다. 중계 고유 code의 정확한 이름과 검증 규칙은 미결정이다. 원문 HTML·내부 주소·SQL·서버 stack trace는 반환하지 않는다.

## 조회 기한과 응답 크기

**추천 시작값:** SSR·중계의 백엔드 조회 전체 5초, 브라우저 8초, 조회 자동 재시도 없음. 이 값은 승인된 WAS 전송의 연결 1초·시도 3초와 다른 정책이다.

이유는 내부 요청이 먼저 종료될 여유를 두고 사용자에게 유한 시간 안에 실패를 알리기 위해서다. DNS·연결·본문 읽기·취소 전파, 프록시 기한을 함께 정하고 측정 후 조정한다. 네트워크 중단 시 취소를 어디까지 전달할 수 있는지도 검증한다. 측정된 SLA로 안내하지 않는다.

**응답 크기 추천:** 최대 size=100과 최대 길이의 Unicode 메시지·JSON escaping을 포함한 직렬화 크기를 산정한 뒤 목록·상세별 상한을 정한다. 수집 요청 256 KiB를 목록 응답에 그대로 적용하지 않는다. 유효한 응답이 상한 때문에 실패하지 않도록 합성 경계 데이터로 비교한다. 초과 응답을 자른 정상 JSON이나 빈 목록으로 바꾸지 않는다.

최대 4,096자 커서와 모든 조회 조건이 포함된 URL도 전체 계층에서 받을 수 있어야 한다. 헤더·URL·응답 제한을 무제한으로 풀지 않고 유효한 최댓값과 오류 응답을 백엔드·프론트·인프라가 맞춘다.

## SSR 화면과 상세 선택

**추천:** 최초 대기에는 화면 틀과 진행 안내만 제공하고 0건·마지막 성공 시각은 표시하지 않는다. 최초 실패에는 실패한 절대 조사 범위와 수동 재시도를 제공한다. 목록 데이터 실패는 중계로 같은 조건을 재시도하고 Next 페이지 자체 실패는 페이지 재진입으로 복구한다.

이유는 데이터 없음·조회 실패·페이지 전달 실패를 구분하고 재시도로 조사 범위가 바뀌지 않게 하기 위해서다. 재진입은 새로운 SSR 요청이므로 같은 절대 시간을 유지한다고 보장하지 않는다. 최초 로딩 중 필터 편집 허용 범위, 조작 준비 전 버튼, 실패 요청 조건 인계를 프론트·디자인이 확정한다.

재조회 중에는 기존 상세 읽기·닫기·복사는 유지하되 새 상세 열기만 잠시 제한하는 안을 권장한다. 조회 성공 시 상세 해제와 새 상세 요청이 충돌하지 않게 하기 위해서다. 이미 진행 중인 상세 요청과 늦은 응답의 폐기, 제한된 버튼의 초점 보존도 함께 정한다.

## 디자인 세부 규격

**추천 시작점:** 밝은 테마, 시스템 본문 글꼴·고정폭 시각과 trace, 본문 16px·목록/trace 14px·8px 간격 단위, 1,200px 이상 목록:상세 55:45, 미만 하단 상세. trace 기본 줄바꿈 켜기·전환·원문 복사, 화면 페이지 크기 50건 고정과 방향 설명 버튼을 권장한다.

이유는 밀리초 시각·서버·긴 로그의 가독성을 확보하고 조작을 단순하게 하기 위해서다. 수치는 디자인의 검토 시작값이며 최소 지원 폭이나 검증 결과가 아니다. 실제 글꼴·한글·긴 내용·200% 확대·키보드·대비 확인 후 프론트·디자인이 색상·초점·복구 문구를 확정한다. API size 1~100 지원과 화면의 50건 고정은 충돌하지 않는다.

## 진단과 커서 키 관리

**추천:** WAS별 구조화 진단 또는 격리 관리 지표로 대기열·시도·성공·포기를 확인하고 전송기 자체 진단은 수집에서 제외한다. 별도 운영 대시보드는 추가하지 않는다. 백엔드·인프라가 지표 이름·노출 위치·리셋·종료 집계 기준을 명세화한다.

커서 서명 키는 외부 파일로 주입하는 방향을 권장한다. 키 식별·교체·재시작 시 유지 여부와 기존 커서 무효화 안내를 정한다. 여러 백엔드 인스턴스를 실행한다면 키의 일관성도 고려한다. 이유는 서버마다 커서 유효성이 달라지거나 재시작 때 예측하지 못한 무효화가 생기지 않게 하기 위해서다. 실제 키·파일·설정은 생성하지 않는다.

## 공통 데이터와 검증 완료 기준

**추천:** 화면·API 기능 검토는 최소 51건에서 시작해 50건 경계의 양방향 탐색을 확인한다. 공통 was-2 오류, 세 WAS 혼합, 동일 시각·다른 ID, 예외 없음, 길이 한계·초과, 커서 만료·무효·조건 불일치, 404·비JSON·잘못된 성공·지연 응답과 SSR 실패 복구를 포함한다.

이유는 분야마다 다른 예시로 정상 동작을 주장하지 않고 같은 입력·기대 행·버튼·초점·오류를 비교하기 위해서다. 조회·SSR에는 자동 재시도가 없지만 샘플 WAS 전송에는 승인된 제한 재시도가 있음을 별도로 검증한다.

51건은 성능 규모가 아니다. 백엔드·인프라가 별도로 데이터 양·발생률·메시지 크기·실행 환경·측정 기간·검색 지연·처리량·메모리·장애·종료의 통과 기준을 제안하고 합의한다. occurredAt의 과거·미래 수집 허용 범위도 명시적으로 결정하며 그전에는 화면이 임의로 날짜를 금지하지 않는다.

## 합의와 문서 반영 순서

1. 총괄·프론트·인프라가 도구 역할과 검증 진입점을 합의한다.
2. 실행 구성과 조회 중계·오류·기한·크기·키 관리를 맞춘다.
3. 프론트·디자인이 SSR 복구·상세 경합·시각 규격을 맞춘다.
4. 공통 예시와 기능·성능 검증 기준을 확정한다.
5. 확정 사항은 기존 명세에 변경일·이유를 기록하고 새로운 정책은 별도 문서로 연결한다. 기능 구현은 별도 요청 후 시작한다.
