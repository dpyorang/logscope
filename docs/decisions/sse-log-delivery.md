# SSE 로그 전달과 복구 기준

2026-10-28 사용자가 폴링 대신 SSE로 실시간 로그를 받고 최초 연결·재연결·일시정지 후 복구를 구현하도록 요청했다. 이 결정은 백엔드 전달 기준이며 프론트 화면 구현은 별도 사용자 지시 후 진행한다. 상세 교환 규칙은 [SSE 명세](../contracts/log-sse.md)를 따른다.

## 선택과 이유

브라우저 폴링은 단순하지만 데이터가 없어도 주기 요청을 보내며 사용자가 원하는 서버 push 경험과 다르다. SSE는 로그처럼 서버→화면 단방향 전송에 적합하다. WebSocket의 양방향 메시지 프로토콜과 Kafka는 현재 기능에 필요하지 않아 도입하지 않는다. SSE 자동 재연결만으로 누락·중복 문제가 사라지는 것은 아니다.

발생시각은 늦은 전송·같은 시각 로그 때문에 replay 기준으로 쓰지 않는다. AUTO_INCREMENT도 할당 순서와 commit 순서가 다를 수 있다. 작은 번호가 미커밋인 사이 큰 번호를 받아 cursor가 앞서면 나중 commit된 로그를 놓친다. 단일 상태 행을 commit까지 잠그고 로그와 sequence 갱신을 같은 트랜잭션으로 묶어 이 경쟁을 막는다. 메모리로만 기록하는 연결 큐 대신 DB를 재전송 원본으로 사용해 재시작 뒤에도 이어받는다. 신호 버전은 조회와 대기 사이 경쟁을 막고 저장 성공 후에만 변경한다.

최초 목록과 cursor는 같은 repeatable-read view에서 읽는다. snapshot 뒤 저장된 것은 stream replay에 들어가므로 조회와 연결 사이 별도 위험 구간을 만들지 않는다. 재전송은 at-least-once이며 클라이언트가 정상 처리 cursor와 eventId 중복 제거를 맡는다. 수신 중 오류나 일시정지에서는 cursor를 앞당기지 않는다.

## 영향과 한계

순서 행은 쓰기를 직렬화하므로 현재 두 샘플 WAS의 개발 환경을 위한 선택이다. 고부하 처리량과 다중 앱의 즉시 알림을 보장하지 않는다. 장기 운영의 인증·보존·삭제·DB 복구 및 프록시 수명 설정은 후속 설계다. 다른 epoch/미래 cursor는409로 드러내고 정상 복구처럼 넘기지 않는다.

읽기는 한 번에50건·연결당128건으로 제한하고 연결은 약55~60초에 갱신한다. 동시에32개 연결만 허용하며 HTTP 완료와 작업자 종료를 모두 확인한 뒤 슬롯을 반환한다. 느린 클라이언트에 무한 대기열을 만들지 않기 위한 선택이다. 실시간 snapshot의 최신50건 한도와 전체 이력 탐색은 구분하며 기존 정적 조회의501 정책은 유지한다. Vector 배치 수집 지연은 SSE로 사라지지 않는다.
