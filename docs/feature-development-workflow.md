# 기능 단위 개발 방식과 진행 순서

2026-10-27 사용자 승인. 모든 세부 설계를 먼저 끝내기보다, 작은 기능을 구현하고 직접 확인하면서 필요한 결정을 한다. 첫 도착점은 로그 한 건을 화면에서 읽을 수 있는 상태다. 이번 승인은 개발 방식·문서 반영과 공유까지이며 기능 구현은 별도 요청 전까지 시작하지 않는다.

## 기능 하나를 진행하는 방법

1. 무엇을 만들고 사용자가 어떤 결과를 확인할지 쉬운 말로 설명한다.
2. 해당 기능의 목표·범위·완료 조건·관련 명세와 필요한 결정만 정한다.
3. 구현 요청을 받은 뒤 최신 main을 기준으로 작업 브랜치·worktree에서 구현한다. 새 브랜치는 [영역별 이름 규칙](branch-naming-policy.md)의 codex/backend/·codex/frontend/·codex/design/·codex/infra/ 형식을 사용한다. 같은 기능의 작업을 이어갈 때는 기존 작업 공간을 재사용한다.
4. 동작과 필요한 테스트를 확인하고, 실제 결과를 명세의 제안·가정과 구분한다.
5. 문서에 바뀐 내용·이유·검증 근거를 기록한다. 학습 기록은 작업의 검증·커밋 완료 후 담당 영역의 docs/learning/ 문서에 [공통 기록 형식](learning-record-format.md)으로 추가하며 PR·CI 절차 이력은 쓰지 않는다. 새 정책이면 별도 문서를 만든다. 기존 Markdown은 삭제하지 않는다.
6. 커밋 직전 전체 검증과 비밀 검사를 통과하고 PR·CI verify를 통해 병합한다. 병합한 결과를 확인한 뒤 다음 기능으로 넘어간다.

기존 승인 기본값은 시작점으로 사용한다. 문제가 발견되면 근거와 변경 이유를 남기고 관련 분야와 조율한다. 분야 간 API·정책을 일방적으로 바꾸거나 검증·보안·브랜치 보호 규칙을 미루지 않는다. 사용자가 판단해야 할 중요한 선택은 결과에 미치는 영향과 추천 이유를 함께 설명하며, 구현자가 정할 수 있는 세부사항은 담당자가 판단해 기록한다.

## 단계별 목표와 담당

| 순서 | 작업 | 사용자가 확인할 결과 | 주 담당 |
| --- | --- | --- | --- |
| 1 | 현재 문서와 공통 규칙 정리, 전체 검증·문서 PR 병합 | 모든 분야가 같은 시작 기준을 읽음 | 총괄, 필요한 분야 검토 |
| 2 | 합성 로그 한 건의 수집·저장·최소 조회 | JSON을 보내면 저장한 로그를 API로 다시 읽음. 중복도 한 건 유지 | 백엔드, 인프라 지원 |
| 3 | 프론트 최소 환경과 목록·상세 연결 | 브라우저에서 서버 ID·메시지·stack trace를 읽음 | 프론트·디자인, 인프라 지원 |
| 4 | 샘플 WAS 한 대의 자동 전송 | WAS에서 만든 오류가 logscope 화면에 나타남 | 백엔드, 인프라 지원 |
| 5 | 시간·서버·레벨·키워드 필터와 커서 탐색·복구 | 원하는 오류를 좁혀 찾고 이전·다음과 실패 복구를 사용 | 백엔드·프론트·디자인 |
| 6 | 샘플 WAS 세 대와 장애·통합 검증 | 세 서버 중 오류 발생 서버를 찾고 실패·중복·포화·종료 동작을 확인 | 관련 분야 공동 |

2단계는 샘플 WAS 없이 합성 JSON을 직접 전송한다. 승인된 필수 시간 범위 등 최소 조회 규칙은 지키되, 모든 검색·페이지 기능까지 한 PR에 넣지 않는다. 3단계에서 최초 화면 표시와 기본 실패 안내를 제공하고, 5단계에서 커서·상세 복구를 완성한다. 단계는 기능 경계이며 한 단계가 너무 크면 작은 PR로 나눌 수 있다.

Java 서버는 Gradle Wrapper·Kotlin DSL, 프론트 의존성·Next 빌드는 npm으로 관리한다. scripts/verify.sh를 공통 검증 진입점으로 유지한다. 프론트 코드 도입 시 Node/npm 확인·잠금 설치·타입·lint·포맷·빌드·해당 단계의 UI 검증·이미지 검증을 연결하며 기존 Java·실제 MySQL·Spotless·비밀 검사·Compose·이미지 검증은 유지한다. 필요한 검사 연결을 해당 기능의 완료 조건으로 삼고 미연결 상태에서 완료나 커밋 성공을 주장하지 않는다. 이번에는 실행 스크립트를 변경하지 않는다.

## 지금 필요한 결정과 나중에 할 결정

| 시점 | 결정할 내용 |
| --- | --- |
| 공통 시작 기준 | Gradle/npm 역할, 전체 검증 유지·프론트 검사 추가 원칙, 기능별 작업 공간·PR, 문서·비밀정보 보호 |
| 저장·조회 구현 | 새 migration과 저장 구조, 필드 검증·중복·최소 조회의 실제 동작과 테스트 |
| 프론트 연결 | 실제 버전 호환성, 필요한 중계 경로·오류·응답 제한·조회 기한·실행 환경·기본 화면 |
| WAS 전송 | 승인된 전송 초기값 적용, 필요한 진단·실패 집계와 업무 요청 영향 |
| 검색·페이지 | 승인된 커서 규칙 구현, 키 주입·수명, 시간 제한·검색·재시도·초점과 지연 응답 처리 |
| 세 WAS·장애 검증 | 실제 응답 크기·시간·메모리 측정, 포화·중복·장애·종료 기준과 필요한 조정 |
| 핵심 흐름 이후 | 큰 데이터 성능 목표, 운영 규모 검증, 필요 시 키 회전과 운영 진단 세부 정책 |

나중에 정한다는 것은 무제한·무검증으로 구현한다는 뜻이 아니다. 예를 들어 조회 중계의 크기 제한은 중계 구현 전에 정하고, 고급 키 회전은 미뤄도 커서 서명 키의 안전한 외부 주입은 커서 기능 도입 전에 정한다. 재시도·메모리 같은 이미 승인된 한도는 그대로 출발점으로 사용한다.

각 미결정의 추천값은 추가 합의 검토안·인프라 제안에 남겨두고 해당 기능 착수 때 검토한다. 모든 제안의 확정을 저장·조회 구현의 선행조건으로 삼지 않는다. 부하·시각 수치처럼 실행 후 확인할 내용은 시작값과 측정·조정 결과를 구분한다.

## 분야별 협업과 설명

- 총괄은 현재 기능에 필요한 담당만 조율하고 공통 문서·의존 관계·검증·PR 결과를 확인한다. 네 분야가 모든 기능을 동시에 구현하도록 지시하지 않는다.
- 백엔드는 저장·조회 → WAS 전송 → 검색·페이지 순으로 진행한다.
- 프론트는 최소 환경 → 한 건 표시 → 검색·복구 순으로 진행한다.
- 디자인은 실제 화면과 합성 로그를 보며 필요한 규격을 순차 확정한다.
- 인프라는 현재 단계에 필요한 실행·검증을 지원한다. 운영 배포는 별도 승인 범위다.
- 설명은 무엇을 만드는지 → 화면·동작이 어떻게 달라지는지 → 지금 결정할 이유 순서로 한다. 용어는 짧은 설명과 예시를 붙이고 선택지를 한꺼번에 과도하게 요구하지 않는다.

## 이전 계획과 변경 이유

- 2026-10-27: 기존에는 분야 간 세부 명세·추천 수치를 모두 맞춘 후 구현하는 흐름으로 정리했다. 사용자가 직접 기능을 확인하며 이해할 수 있도록 기능별 필요한 결정을 적시에 하는 방식으로 변경했다.
- 최종 MVP 범위·기존 승인 명세·전체 검증·비밀 관리·PR 규칙은 유지한다. 미결정 전체를 선행조건으로 두던 설명과 WAS 전송을 화면보다 먼저 두던 초기 순서는 이 문서의 최신 단계로 대체한다. 이전 문서는 학습·결정 근거로 보존한다.

## 2026-10-27 로그 탐색 외형 개선의 범위와 결정 시점

사용자가 총괄 추천안을 승인했다. 기존 기능 단위 진행 방식을 이번 프론트 작업에 적용한 후속 기준이며, 구현 착수 승인은 아니다. 공통 순서는 샘플 WAS 한 대 자동 전송 → 검색·커서·복구를 유지한다. 프론트 외형 개선은 별도 작은 작업으로 진행할 수 있으나 공통 순서를 변경하거나 다른 작업의 선행조건으로 삼지 않는다.

### 이번에 확정한 범위

- 밝은 테마의 기존 로그 탐색 외형을 개선한다. 헤더·색상·간격·목록·비모달 상세·좁은 화면 배치를 대상으로 하며 기존 API·SSR·조회·상세·오류 처리 동작을 유지한다.
- 헤더에는 제품명 `logscope`와 `로그 탐색`을 표시한다. 미구현 메뉴와 사이드바는 보류한다. 개별 서비스명은 상세에 표시하며 전체 목록이 특정 서비스의 결과인 것처럼 표시하지 않는다.
- 현재 표와 명시적인 상세 버튼을 유지해 기존 키보드 조작과 초점 복귀를 보존한다.
- 다크 모드는 별도 작업으로 분리한다. 검색·필터·커서·개요·차트·별도 오류 분석·트래픽은 이번 외형 개선에 포함하지 않는다.
- 최근 24시간과 현재 최대 50건·초과 시 제한 안내 등 기존 조회 기준을 유지한다. 디자인의 15분 예시는 후속 문서 정합성 보정 대상이며 현재 기준을 바꾸지 않는다.

### 구현하면서 담당자가 조정할 사항

디자인·프론트는 파란색 강조의 밝은 테마와 현재 1,200px 전환을 출발점으로 정확한 색·글꼴·간격·패널 너비·줄바꿈·화면 전환 폭을 실제 화면에서 조정한다. 긴 한글 메시지·stack trace·확대·키보드·초점·오류 상태와 대비를 확인하고 변경 이유와 검증 결과를 기록한다. 이 수치는 검증 완료값이 아니며 완료 전 실제 검증이 필요하다. 실제 시안을 여는 방법은 담당자가 해결할 작업 절차다.

확정 범위 안의 시각적 세부사항은 매번 총괄 승인을 기다리지 않는다. 범위·기존 동작·API·공통 정책이 바뀌는 경우에는 관련 분야와 다시 조율한다. 보안·필수 검증은 미루지 않는다.

### 해당 기능 착수 때 정할 사항

검색·필터·커서·복구는 기존 승인 명세를 유지하고 백엔드 연결·화면 처리 세부를 해당 단계에 조율한다. 화면 간 조건·URL은 여러 화면을 도입할 때, 오류 분석·개요는 핵심 탐색 이후 해당 기능을 시작할 때, 트래픽은 로그 MVP 이후 데이터 원천·지표부터 정한다. 후속 결정을 이번 외형 개선의 선행조건으로 삼지 않는다.

변경 이유: 프론트 초안에서 색상 수치·반응형 폭·시안 확인 절차까지 모두 구현 전 합의로 분류해 결정을 과도하게 앞당겼다. 사용자 승인으로 작업 범위와 화면 의미는 지금 확정하고, 시각적 세부는 실제 결과를 보며 조정하도록 나눴다. 기존 기록은 보존하며 충돌 시 이 후속 기준과 [프론트 연동 명세](contracts/frontend-integration-draft.md#frontend-design-next-scope)의 승인 반영 절을 따른다.

## 2026-10-27 후속 승인: 시안 기반 공통 화면 틀과 로그 탐색

사용자가 디자인 시안을 기준으로 공통 화면 틀과 로그 탐색을 맞추는 방향의 문서 반영·공유를 승인했다. 이는 다음 작업의 범위 승인이고 구현 착수 승인은 아니다. 앞의 단일 화면 외형 개선·사이드바 보류는 이번 후속 기준으로 대체하며 이전 결정과 이유는 보존한다.

- 디자인 문서의 전체 제품 화면 구성 초안과 `logscope-workspace.html`을 장기 디자인 기준으로 삼는다. 공통 헤더·사이드바·패널 구조를 적용하고 현재 실제 API의 로그 목록·비모달 상세를 그 안에 배치한다. 시안의 모든 기능·합성 데이터·JavaScript 동작을 그대로 구현한다는 뜻은 아니다.
- 초기 진입과 실제 메뉴는 로그 탐색만 제공한다. 미구현 개요·오류 분석·트래픽 메뉴는 숨긴다. 헤더는 제품명 `logscope`와 페이지명 `로그 탐색`을 유지하며 시안의 샘플 서비스명을 전체 목록의 서비스로 표시하지 않는다.
- 밝은 테마를 적용하고 다크 모드는 별도 작업으로 유지한다. 기존 표·명시적 상세 버튼·비모달 상세·원문·복사·줄바꿈·키보드·초점 복귀를 유지한다.
- 현재 최근 24시간·최대 50건·초과 제한 안내, 실제 API·SSR·중복 첫 조회 방지·캐시 및 응답/시간 한도·실패 시 기존 결과 보존·같은 절대 범위 재시도를 유지한다. 공통 WAS 한 대 자동 전송 → 검색·커서·복구 순서는 바꾸지 않으며 공통 화면 틀을 백엔드 작업의 선행조건으로 삼지 않는다.
