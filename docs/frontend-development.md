# 프론트 초기 개발 환경과 검증

2026-10-27. TypeScript·Next.js SSR 기본 화면을 구성한다. 로그 API 연동은 다음 작업이다. [환경 명세](contracts/frontend-environment-draft.md)와 [공통 아키텍처](architecture.md)를 함께 참고한다.

## 실행과 검사

Node 24.22.1, npm 11.19.1을 사용한다. frontend/.node-version과 package.json에 고정하며 실제 값이 다르면 검증이 실패한다. 공식 도구를 설치하고 PATH에서 사용할 수 있어야 한다. 시스템 전체 설치는 자동으로 수행하지 않는다.

```sh
cd frontend
npm run check:runtime
npm ci
npm run dev
```

http://localhost:3000 에서 기본 화면을 확인한다. 개발 서버는 loopback으로 실행한다. 실행 산출물은 npm run build 후 HOSTNAME=127.0.0.1 npm run start로 확인한다. standalone에 public과 .next/static을 함께 복사한다.

개별 검사는 npm run typecheck, npm run lint, npm run format:check, npm run build, npm run test:e2e다. 포맷 수정은 npm run format 후 전체 검증을 다시 실행한다. 정확한 의존성은 package-lock.json으로 관리한다.

커밋 전 공통 진입점은 루트 ./scripts/verify.sh다. 비밀 검사 → Java clean build·실제 MySQL Testcontainers·Spotless → 프론트 runtime·npm ci·타입·lint·포맷·빌드·Chromium → Compose·서버 이미지 → 프론트 이미지·컨테이너 생존/SSR 검사를 실행한다. 필수 도구가 없으면 생략하지 않고 실패한다. verify-frontend.sh는 잠금 파일의 Playwright에 맞는 Chromium을 설치한다. Ubuntu CI는 playwright install --with-deps chromium으로 OS 라이브러리를 준비한다.

## 화면과 실행 경계

루트 페이지는 connection()으로 요청 시 서버에서 렌더링한다. 현재 로그가 연결되지 않았음을 명시하며 가짜 조회 결과를 보여주지 않는다. HTML 언어 ko, 본문 바로가기·랜드마크·초점·좁은 화면 줄바꿈을 제공한다. 로그 화면의 최종 디자인은 다음 작업이다.

GET /health/live는 자체 응답만 확인한다. UP은 API·DB 준비나 제품 정상 동작을 뜻하지 않는다. ready 정책은 백엔드 연결 단계에서 정한다.

Compose frontend는 127.0.0.1:3000의 별도 Node 서비스이며 현재 app/db 준비에 의존하지 않는다. 이미지는 기본 node 사용자로 server.js를 직접 실행한다. Compose에는 init과 15초 종료 유예를 둔다. 운영 Compose와 배포는 이번 범위가 아니다.

```sh
docker compose --env-file .env.example up --build frontend
```

.env.example은 예시다. 프론트에 실제 비밀값·내부 API 주소·NEXT_PUBLIC 설정은 추가하지 않는다.

## 버전 조정 이유

TypeScript 7.0.2의 tsc는 실행됐으나 typescript-eslint가 컴파일러 API 미지원 오류로 lint를 중단했다. [공식 전환 안내](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/)와 [지원 범위](https://typescript-eslint.io/users/dependency-versions/)를 참고해 TypeScript 6.0.3을 사용한다. 검사 우회 대신 단일 호환 컴파일러를 택했다.

ESLint 9.39.5도 후보로 실행했으나 npm에서 지원 종료 경고를 확인했다. 최종은 ESLint 10.13.0, @eslint/js 10.0.1, typescript-eslint 8.72.1, @next/eslint-plugin-next 16.4.3, eslint-plugin-react-hooks 7.1.1의 flat config다. eslint-config-next 내부 플러그인의 ESLint 9 peer 제한을 강제로 우회하지 않고 공식 Next·Hooks·TypeScript 권장 규칙을 직접 적용한다. Next 규칙에 따라 홈 링크도 Link를 사용한다.

Prettier 3.9.10, Playwright 1.64.1, React 타입 19.3.0, Node 타입 24.19.2를 고정한다. 버전은 재현 기준이며 영구 안전성을 보장하지 않는다. 갱신 때 새 검증과 변경 이유를 남긴다.

## 필수 UI 범위와 한계

Chromium 1 worker·재시도 0회로 실제 standalone 서버를 검사한다. JavaScript 없는 첫 HTML의 한글 제목·본문·no-store, 키보드 본문 바로가기·360px 넘침·브라우저 오류·API 미호출, health와 public 자산 제공을 확인한다. 이미지도 임의 호스트 포트의 일회 컨테이너에서 health·SSR을 확인한 뒤 제거한다. 기존 앱·DB·볼륨을 변경하지 않는다.

다른 브라우저·전체 접근성·API·검색·복구·부하 성능 검증은 아직 없다. 실패 보고서·trace·스크린샷은 Git에서 제외하고 CI 실패 자료는 합성 화면만 7일 보관한다.

## 2026-10-27 다음 프론트 작업 범위: 로그 탐색 디자인 정리

사용자가 비교 검토의 추천안을 명세에 반영하도록 요청했다. 이번 반영은 다음 작업의 범위와 결정 목록을 정리하는 문서 작업이며, 구현 착수·분야 간 합의 완료를 뜻하지 않는다. 세부 합의는 [프론트 연동 명세의 디자인 적용 계획](contracts/frontend-integration-draft.md#frontend-design-next-scope)을 따른다.

다음 프론트 작업 단위는 현재 API에 연결된 로그 탐색 화면의 외형 정리로 제안한다. 헤더·색상·간격·목록·비모달 상세·좁은 화면 배치를 다루고, 기존 SSR·최근 24시간·최대 50건·조회 실패 보존·동일 범위 재시도·초점 복귀·원문 복사를 유지한다. 검색·필터·커서, 개요 집계, 별도 오류 분석, 트래픽은 포함하지 않는다. 기존 동작을 유지하면서 현재 API로 결과를 확인할 수 있는 작은 작업으로 나누기 위해서다.

적용 순서는 ① 현재 24시간 기준과 디자인 설명의 정합성 및 필요한 디자인 결정 정리 → ② 별도 구현 승인 후 로그 탐색 외형·공통 화면 틀 개선 → ③ 기존 기능 개발 순서와 백엔드 준비에 맞춘 검색·필터·커서·복구 → ④ 오류 분석·개요·트래픽의 별도 확장 검토를 추천한다. 이 순서는 프론트 작업의 제안이며 샘플 WAS 자동 전송보다 먼저 착수한다는 결정은 아니다. 공통 일정·우선순위는 총괄과 합의한다.

후속 사용자 승인으로 다크 모드는 별도 작업으로 분리하고, 미구현 메뉴·사이드바는 보류한다. 헤더는 logscope / 로그 탐색, 서비스명은 상세 표시, 표와 상세 버튼은 유지한다. 정확한 색상·간격·반응형 폭은 디자인·프론트가 실제 화면을 보며 조정한다. 현재 기준은 연동 명세의 「사용자 승인 반영: 확정 범위와 구현 중 조정」을 따른다. 확대·긴 메시지·trace·키보드와 실제 렌더링을 확인하기 전 외형 수치나 접근성을 검증 완료로 표현하지 않는다.

### 변경 이유와 확인 상태

- 2026-10-27: 총괄의 검토 의견을 확인하고 사용자 요청으로 다음 프론트 작업을 기존 로그 탐색 디자인 정리로 한정하는 계획을 반영했다. 전체 제품 시안의 메뉴·테마·집계를 한 번에 구현하는 것으로 오인하지 않도록 범위·의존 관계·추가 합의를 분리했다.
- 디자인 시안 HTML·CSS·JavaScript와 문서·현재 코드를 비교했지만 브라우저 보안 정책이 로컬 HTML 열기를 차단해 실제 렌더링·클릭은 확인하지 못했다. 이번 문서 반영도 화면·접근성·API 검증 완료를 뜻하지 않는다.
- 기존 Local 미커밋 디자인 초안은 수정하지 않았다. 학습 문서의 새 완료 기록은 규칙대로 필수 검증·작업 커밋 이후에 작성하며 이번에는 추가하지 않는다. 코드·의존성·실행 설정·커밋은 변경하지 않는다.

- 2026-10-27 후속 사용자 승인: 밝은 테마의 기존 로그 탐색 외형 개선 범위와 메뉴·테마·선택·헤더 기준을 확정하고, 색상·간격·반응형 수치는 구현 중 담당자가 조정하도록 결정 시점을 나눴다. 공통 WAS 자동 전송 → 검색·커서·복구 순서는 유지한다. 이전 문단의 제안·미합의 설명은 승인 범위에서 후속 기준으로 대체하며 구현은 별도 요청 전 시작하지 않는다.

## 2026-10-27 후속 승인: 시안 기반 공통 화면 틀

사용자가 디자인 시안을 기준으로 공통 화면 틀과 현재 로그 탐색을 맞추는 방향을 승인했다. [최신 공통 범위](feature-development-workflow.md#2026-10-27-후속-승인-시안-기반-공통-화면-틀과-로그-탐색)를 따른다. 앞의 사이드바 보류·단일 화면 외형 개선 범위를 대체하지만 기존 검토 기록은 보존한다. 구현 착수 승인은 아니다.

공통 헤더·사이드바·패널 구조에 실제 API 목록·비모달 상세를 배치한다. 초기 진입·실제 메뉴는 로그 탐색만 제공하고 미구현 메뉴는 숨긴다. 헤더는 logscope / 로그 탐색, 서비스명은 개별 상세 표시를 유지한다. 밝은 테마·기존 표와 상세 버튼을 유지하며 다크 모드는 별도 작업이다. 기존 최근 24시간·50건·초과 제한 안내·SSR/API·실패 보존·원문·복사·초점 등 동작과 필수 검증을 유지한다.

색·간격·너비·좁은 화면의 사이드바 전환은 디자인·프론트가 실제 결과를 보며 정한다. 긴 로그·trace·확대·키보드·초점·각 상태를 검증하고 범위·API·기존 동작 변경은 재조율한다. 시안의 행 선택·조건 초기화를 그대로 복제하지 않는다. 후속 검색·커서·집계·트래픽은 이번 작업에 포함하지 않으며 공통 WAS 전송 → 검색·커서·복구 순서는 유지한다.

변경 이유: 색상 정리에서 시안의 구조를 기반으로 한 일관된 확장으로 방향을 바꾼다. 시안 자체의 실제 렌더링 검증과 기존 구현의 검증은 구분하며 완료 전 실제 화면 확인이 필요하다. 이번에는 문서만 반영하고 구현·커밋을 시작하지 않는다.

사용자가 명세에 따른 SSE 연결 구현을 지시했다. 현재 구현 기준은 [프론트 실시간 로그 탐색](frontend-live-view.md)이다. 최초 SSR·수동 새로고침에 서버 기준 최근 24시간 snapshot을 사용하고 fetch SSE 중계로 이어받는다. 기존 정적 API·상세·검증 진입점은 유지한다. 이전의 최소 정적 조회와 별도 착수 대기 설명은 당시 기록으로 보존한다.

## 2026-10-28 검색 보기 추가

실시간 보기와 분리된 명시적 검색·기간/서버/레벨 필터를 추가한다. 이전 초기 구현의 검색 미제공 설명은 당시 범위로 보존하며, 현재 동작·오류 보존·검색 전용 시간 제한과 후속 범위는 [로그 검색 보기](frontend-search-view.md)를 따른다. 검색은 백엔드 ES API, 상세와 실시간은 기존 API를 사용한다. 입력마다 호출하지 않고 조회 또는 Enter로 적용해 요청과 화면 변경을 제어한다.
