# logscope 학습 정리 읽는 순서

2026-10-27. 사용자가 지금까지의 요청·제안·결정 이유를 이해하고 블로그에 정리하기 위한 학습 자료다. 실제 기능 구현과 정책 문서의 현재 상태를 구분해 읽는다. 이 자료는 새로운 기술 채택이나 구현 승인이 아니다.

각 영역 문서는 [공통 기록 형식](../learning-record-format.md)을 사용한다. 상단 목차의 주제·시간(KST)·간략한 내용에서 주제를 선택하면 아래 상세 기록으로 이동한다. 목차와 상세는 오래된 것부터 쌓이며, 새 기능·의미 있는 결정·검증·병합 결과는 끝에 추가한다. 기존 기록의 모르는 시각은 추정하지 않는다.

## 출발점과 지금까지의 흐름

사용자는 이커머스의 여러 WAS와 BATCH 서버에 로그가 흩어져 있어 오류가 발생한 서버부터 직접 찾아야 하는 문제를 설명했다. 목표는 로그를 logscope에 모아 오류와 발생 서버를 한곳에서 찾는 것이다.

사용자가 제안한 MVP는 샘플 WAS 3개, 로그 전송, 화면 시각화였다. 총괄은 별도 업무 앱 세 개 대신 샘플 앱 하나를 서로 다른 서버 ID로 실행하고, 차트보다 목록·필터·상세부터 제공하는 방향을 제안했다. 사용자가 수락해 MVP와 명세에 반영했다. 이는 실제 이커머스 기능보다 로그 문제의 해결 여부를 먼저 확인하려는 선택이다.

이후 분야별 명세를 모으는 과정에서 많은 미결정을 한꺼번에 검토했다. 사용자는 설명을 충분히 이해하기 어렵고 직접 기능을 보면서 결정하고 싶다고 말했다. 이에 모든 세부 설계를 끝내는 방식에서 작은 기능별 결정·구현·검증으로 진행 방식을 변경했다. 기존 명세와 제안은 그때 참고할 자료로 보존한다.

## 먼저 구분할 네 가지 상태

| 상태 | 의미 | 블로그 표현 예시 |
| --- | --- | --- |
| 사용자 요구 | 해결하고 싶은 문제와 기대 결과 | 여러 서버의 오류 로그를 한곳에서 찾고 싶었다 |
| 검토 제안 | 후보·수치·화면 시작점이며 아직 합의 전 | 목록 응답 한도를 비교 검토했다 |
| 채택한 명세 | 어떻게 만들지 정한 기준. 실행 성공과 별개 | 로그 전송을 비동기로 구성하기로 했다 |
| 구현·검증 결과 | 실제 실행한 변경과 확인 범위 | 초기 설정의 실제 MySQL 통합 테스트를 확인했다 |

문서에 숫자가 적혔다고 그 수치를 측정해 달성한 것은 아니다. 코드가 없는 상태에서 로그 수집·검색·SSR을 구현했다고 쓰지 않는다. 반대로 초기 프로젝트 빌드·MySQL 테스트·CI·브랜치 보호 등 실제 수행한 초기 설정까지 단순 제안으로 표현할 필요는 없다. 결과는 [초기 설정 기록](../setup-status.md)과 해당 PR·CI의 확인 범위를 기준으로 작성한다.

## 추천 읽기 순서

1. [MVP 계획](../mvp-plan.md): 무엇을 해결하고 어디까지 만들 것인지 이해한다.
2. [기능 단위 개발 방식](../feature-development-workflow.md): 한 번에 무엇을 만들고 확인할지 읽는다.
3. [인프라 학습 정리](infrastructure.md): 프로젝트를 실행·검증·협업할 기반을 이해한다.
4. [백엔드 학습 정리](backend.md): 로그가 들어와 저장되고 조회되는 흐름을 이해한다.
5. [디자인 학습 정리](design.md): 오류를 찾는 사람이 어떤 정보와 조작을 필요로 하는지 이해한다.
6. [프론트 학습 정리](frontend.md): 그 흐름을 브라우저와 서버가 어떻게 나눠 처리할지 이해한다.

모든 문서를 처음부터 외우거나 모든 기술을 공부한 뒤 개발할 필요는 없다. 첫 로그 한 건의 저장·조회 단계에서는 관련 백엔드 설명과 검증 기반을 먼저 읽고, 화면 연결 단계에서 SSR과 상태 처리를 이어 읽는다.

## 분야별 문서에서 확인할 질문

- 내가 직접 요청한 것은 무엇이고 AI가 구체화한 것은 무엇인가?
- 무엇을 선택했고 어떤 문제를 줄이려고 했는가?
- 다른 선택도 가능한가? 채택한 방식의 단점은 무엇인가?
- 쓰지 않는 것은 금지된 것인가, 현재 범위 밖인가, 아직 미정인가?
- 실제로 실행해 본 것과 문서상 결정만 한 것은 각각 무엇인가?
- 다음 기능에서 무엇을 확인해야 하는가?

대화 출처를 확인할 수 없는 결정의 제안자를 억지로 사용자나 AI로 분류하지 않는다. 각 분야 문서의 확인 필요 표시를 함께 읽는다.

## 블로그를 쓰는 방법

기술 목록을 나열하기보다 문제 → 선택지 → 선택 이유 → 실제 작업 → 확인 결과 → 남은 한계 순서로 쓴다. 예를 들어 초기 설정 글과 향후 로그 수집 구현 글을 분리하면 지금까지 실제로 한 일과 앞으로 만들 일을 혼동하지 않는다.

추천 글 순서는 개발 배경과 MVP, 초기 실행·검증 환경, 분야별 설계 판단, 첫 로그 저장·조회 구현기, 화면 연결, WAS 전송과 장애 확인이다. 뒤의 구현기는 실제 해당 작업 후 작성한다. 학습 문서의 설명을 그대로 성과로 바꾸지 말고 직접 확인한 명령·화면·결과와 자신의 이해를 추가한다. 비밀값·내부 접속 정보·실제 고객 데이터는 기록하지 않는다.
