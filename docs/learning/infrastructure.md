## 주제: 초기 환경·검증·브랜치 보호와 인프라 제안 학습 / 시간: 2026-10-27 (작성 시각 미기록)

### 이전 문서 안내와 기록 방식

2026-10-27 작성. 사용자 요청, AI 제안, 승인과 실제 검증을 구분해 공부·블로그 작성에 활용하는 자료다. 새로운 정책을 확정하거나 기능 구현을 승인하는 문서가 아니다. 버전은 프로젝트 채택 기록이며 현재 지원·보안 상태를 새로 검증했다는 뜻이 아니다.

근거는 이 인프라 채팅의 직접 대화, [초기 설정 기록](../setup-status.md), [운영 절차](../operations.md), [공통 규칙](../../AGENTS.md), [문서 관리 정책](../documentation-policy.md)와 아래 연결 문서다. 초기 세팅 구성 채팅의 원문 전체는 이번 작성에서 다시 조회하지 않았다. 그 작업은 전달받은 요약과 보존된 문서에 근거한다고 표시한다. 이번 작성에서는 환경·원격 설정·CI를 새로 실행 검증하지 않았다.

### 기록을 계속 쌓는 방법

2026-10-27 사용자 요청으로 앞으로 인프라 기능을 구현하거나 수정할 때마다 이 문서에 학습 기록을 추가한다. 이전 기록은 보존하고, 각 기록의 상단에 큰 주제와 작업 시간을 표시한 뒤 그 아래에 새로 만든 내용과 배운 점을 정리한다. 기록은 오래된 것부터 시간순으로 쌓는다.

- 시간은 Asia/Seoul(KST) 기준으로 기록한다. 정확한 시각을 확인하지 못한 과거 작업은 날짜만 적으며 추정 시각을 만들지 않는다.
- 각 기록에는 사용자 요청 → 만든 내용 → 선택 이유·대안 → 쉬운 개념·예시 → 실제 확인 결과 → 남은 일 순으로 적는다.
- AI 제안·사용자 승인·구현·검증·PR/병합 상태를 구분하고 확인한 코드·문서·PR 링크를 남긴다. 문서만 정한 것을 구현 완료로 기록하지 않는다.
- 후속 수정은 기존 기록을 지우지 않고 새 기록에서 바뀐 내용과 이유를 연결한다. 같은 기능의 추가 검증·병합 결과도 확인 시점과 함께 추가한다.
- 실제 비밀값·개인정보는 포함하지 않고 예시는 합성값만 사용한다.

새 기능 기록의 형식은 다음과 같다. 아래는 작성 양식이며 실제 구현 기록이 아니다.

### 1. 해결하려는 문제와 인프라의 역할

여러 쇼핑몰 서버와 배치 서버에 로그가 따로 쌓이면 오류가 났을 때 어느 서버부터 확인할지 알기 어렵다. logscope의 제품 목표는 로그를 한곳에 모아 발생 서버와 원인 메시지·예외를 찾는 것이다.

인프라의 첫 역할은 이 기능을 만들기 전에 믿을 수 있는 작업 기반을 마련하는 것이었다. 개발자 컴퓨터에서 앱과 실제 MySQL이 함께 동작하는지, 코드를 바꾸면 같은 검증을 다시 실행할 수 있는지, 검증하지 않은 변경이 main으로 들어가지 않는지 확인했다.

예를 들어 합성 서버 was-2의 오류를 화면에서 찾는 것은 제품 기능이다. 이 기능의 테스트에 쓸 MySQL을 띄우고, 테스트 실패 시 병합을 막는 것은 인프라 책임이다. 지금까지 기반 코드와 검사 스크립트는 구현·수정했지만 이 채팅에서 로그 수집·검색·샘플 WAS 같은 도메인 기능을 구현하지는 않았다.

### 3. 핵심 개념을 작은 예로 이해하기

#### Java, Gradle, Wrapper, Kotlin DSL

Java는 앱 코드를 작성하는 언어다. Gradle은 그 코드를 컴파일하고 테스트하고 실행 파일로 만드는 작업 도구다. Wrapper는 프로젝트가 정한 Gradle 배포본을 사용하도록 돕는 실행 파일·설정 묶음이다. 컴퓨터에 설치된 임의 Gradle 버전에 맡기지 않는다. 대신 JDK까지 영구 설치해 주는 것은 아니다.

Kotlin DSL은 build.gradle.kts 같은 빌드 설정을 Kotlin 문법으로 쓰는 방식이다. 현재 앱 소스는 Java다. 따라서 “Gradle Kotlin DSL 전환”과 “서버를 Kotlin으로 개발”은 다른 말이다.

Maven도 Java 빌드 도구다. 처음 Maven 구성이 있었고 사용자 요청으로 Gradle로 바뀌었다. 어느 도구가 절대 우월해서 바꿨다고 기록할 근거는 없다. 도구를 바꾸면 빌드 명령뿐 아니라 CI·Dockerfile·테스트 보고서 경로·운영 문서도 함께 맞춰야 한다는 것이 이 작업의 학습 포인트다.

#### BOM과 의존성 버전

Spring Boot BOM은 함께 사용할 라이브러리 버전의 관리 기준이다. JPA·Hibernate·JDBC·Flyway·Testcontainers를 각자 임의로 고정하기보다 Boot가 관리하는 조합을 따른다. 조합 관리 부담을 줄이지만 실제 실행 검증이 없어도 호환된다고 보증하는 것은 아니다.

#### Docker 이미지, 컨테이너, Compose, Testcontainers

이미지는 앱을 실행할 파일과 환경을 담은 틀이고 컨테이너는 그 틀로 실행한 프로세스 환경이다. Compose는 앱과 DB처럼 함께 실행할 서비스를 선언한다. Testcontainers는 테스트가 사용할 실제 DB 컨테이너를 준비하는 데 쓰인다.

예를 들어 개발용 Compose의 MySQL과 통합 테스트용 MySQL은 목적이 다르다. 테스트가 실제 MySQL을 사용한다는 것은 운영 DB에 테스트 데이터를 넣는다는 뜻이 아니다. H2 같은 대체 DB만으로 통과하는 결과보다 실제 대상 DB의 연결·Flyway 동작을 확인하려고 MySQL Testcontainers를 채택한 상태다.

불편한 점도 있다. Docker가 필요하고 시작 시간·메모리·이미지 내려받기 비용이 든다. 이 프로젝트는 그 비용 때문에 테스트를 자동 생략하는 방식을 금지한다.

#### Spotless와 전체 검증

Spotless는 코드 모양을 검사·정리하는 도구다. 포맷이 맞는다고 기능 버그가 없다는 뜻은 아니다. spotlessApply는 파일을 고칠 수 있고 spotlessCheck는 검사한다. 포맷을 고친 뒤에도 전체 검증을 다시 실행한다.

현재 verify.sh의 실제 순서는 비밀 검사 → Gradle clean build → Compose 구성 검사 → Docker 이미지 빌드다. Gradle build에 테스트와 Spotless 검사가 연결되어 있다. Next 검사 추가 원칙은 확정됐지만 현재 스크립트에 프론트 검사가 이미 구현되어 있다고 쓰면 안 된다.

#### GitHub 인증, PR, CI, 브랜치 보호

인증은 “이 저장소에 접근하는 내가 누구인가”를 확인하는 절차다. Codex 연결 도구의 인증과 로컬 Git·GitHub CLI 인증은 서로 구분해야 한다. 하나가 된다고 나머지가 자동으로 된다고 가정하지 않았다.

PR은 변경을 main에 넣기 전에 비교·검토하는 요청이다. CI는 GitHub의 실행 환경에서 자동 검사를 돌리는 과정이다. 브랜치 보호는 PR·CI 같은 조건을 충족하지 않으면 main 변경을 차단하는 서버 측 규칙이다. AGENTS.md는 사람이 따라야 할 규칙이고 브랜치 보호는 GitHub의 강제 장치다.

logscope는 혼자 개발하므로 다른 사람 승인 0명을 선택했지만 PR과 verify는 필수다. 관리자에게도 적용하고 강제 푸시·브랜치 삭제를 막았다. “승인 0명이라 main 직접 푸시 가능”은 잘못된 설명이다. 보호가 있어도 테스트가 놓친 버그까지 막지는 못한다.

#### 브랜치와 worktree

브랜치는 커밋을 따라가는 작업 이력의 이름이고 worktree는 특정 브랜치·revision을 파일로 펼쳐 놓은 별도 폴더다. 브랜치를 여러 개 만든 것만으로 같은 폴더를 동시에 수정해도 안전해지는 것은 아니다.

합성 예로 작업 A는 폴더 /workspace/task-a, 작업 B는 /workspace/task-b에서 각자 파일을 바꾼다. 두 폴더가 같은 저장소의 worktree라면 Git 객체와 ref는 공유한다. 독립적인 구현은 별도 worktree, 같은 작업은 기존 worktree 재사용이라는 규칙을 둔 이유다.

#### 백업, 복원, readiness

백업은 복원에 쓸 데이터를 보관하는 일이고 복원은 실제로 다른 DB에 되살려 보는 일이다. 덤프 파일이 생기거나 체크섬이 맞는 것만으로 앱이 다시 동작한다고 증명하지는 못한다.

기록된 리허설에서는 로컬 초기 DB를 별도 MySQL에 복원하고 Flyway V1·앱 연결·readiness UP을 확인했다. readiness는 앱이 요청을 처리할 준비가 됐는지 보는 상태 확인이다. 이것만으로 모든 기능·보안·운영 성능이 통과했다고 보지 않는다.

### 4. 채택 방식의 이유, 대안과 비용

| 채택한 방식 | 이해할 수 있는 이유 | 대안과 단점·한계 |
| --- | --- | --- |
| Wrapper·배포본 SHA-256 | 빌드 도구 버전과 배포본 무결성 확인 | 시스템 Gradle에 맡기는 방법보다 설정이 늘고 최초 다운로드 필요. 버전 고정만으로 보안 보장 안 됨 |
| Boot BOM | 라이브러리 조합 관리 단순화 | 개별 버전 지정은 유연하지만 호환성 책임이 커짐 |
| 실제 MySQL 통합 테스트 | 대상 DB 연결·migration을 직접 확인 | 가벼운 대체 DB보다 느리고 Docker 자원 필요. 운영 부하 검증 대체 불가 |
| multi-stage Dockerfile·별도 사용자 | 빌드와 실행 환경 분리, 실행 권한 제한 | 이미지 관리·빌드 비용 필요. 이것만으로 취약점 제거 안 됨 |
| Compose | 로컬 앱·DB 구성 재현 | 수동 실행보다 선언 관리가 쉬우나 무중단·다중 노드 운영 보장 아님 |
| Flyway 새 migration·validate | 스키마 변경 이력과 앱·DB 불일치 확인 | ddl-auto update/create는 편할 수 있으나 이 프로젝트에서 금지. 변경 파일을 계속 관리해야 함 |
| UTC·open-in-view=false | 서버 간 시간 기준 통일, 웹 응답 중 DB 접근 의존 제한 | 시간 표현과 조회 경계를 명시해야 하고 필요한 데이터 조회를 미리 설계해야 함 |
| 비밀 검사·실제 env 제외 | 실수로 비밀이 이력에 남는 위험 감소 | 자동 검사만으로 모든 민감정보를 찾을 수 없어 사람 검토 병행 |
| 로컬 훅+CI+보호 | 커밋 전·원격·병합 시점에 검증 | 실행 시간이 늘고 도구 장애도 작업을 막음. 검증 우회로 해결하지 않음 |
| Actions 전체 SHA·명시 OS | 실행할 코드와 OS 계열을 구체적으로 고정 | 태그 추종보다 업데이트 관리 필요. 자동 보안 갱신을 대신하지 않음 |

이 표의 이유는 현재 구조를 이해하기 위한 설명이다. 최초 제안 당시의 실제 동기를 전부 확인했다는 뜻은 아니다.

### 5. 실제 문제를 만나 바꾼 결정

#### private 보호 제한에서 public 선택까지

사용자는 처음 private을 유지하고 싶다고 했다. 원격 조회에서 보호 API는 403과 플랜 제한을 반환했다. AI는 Pro 업그레이드와 public 전환 시의 차이를 설명했고, 사용자 요청에 따라 이력과 원격 자료를 검사했다.

검사 범위에서 실제 비밀번호·토큰·운영 접속 정보는 발견하지 못했다. 그러나 과거 작성자 로컬 이메일·컴퓨터 호스트명·폴더 경로가 남아 있었다. 여기서 컴퓨터 호스트명은 MAC 주소가 아니다. 학습 문서에는 실제 값·개인 식별 정보 자체를 옮기지 않는다.

AI는 파일만 고치면 과거 정보가 남는다는 점, 이력 재작성이나 새 저장소 방식의 영향을 설명했다. 사용자는 그 정도의 공개를 수용하고 직접 public으로 전환했다. 따라서 “개인정보를 완전히 삭제한 뒤 공개했다”는 설명은 틀리다. 이력 재작성·강제 푸시는 하지 않았다.

이후 사용자가 향후 민감정보 관리 강화와 로컬 폴더 경로 예외를 각각 요청했다. 최신 규칙은 폴더 경로를 허용하지만 실제 비밀값·연락처 등을 넣어도 된다는 뜻은 아니다.

#### worktree에서 비밀 검사가 0건 성공한 문제

기존 스크립트는 .git을 Docker 컨테이너 안에 마운트했다. 일반 저장소의 .git 디렉터리와 달리 worktree의 .git은 실제 메타데이터 위치를 가리키는 파일이었다. 컨테이너는 호스트 절대 경로를 그대로 해석할 수 없었다.

실행 결과 Git 조회 오류가 났는데 Gitleaks는 0개 커밋을 검사하고 성공처럼 종료했다. 전체 검증 명령의 종료 코드만 보면 놓칠 수 있는 문제였다. 이 상태를 성공으로 인정하지 않아 처음 정책 문서 변경은 커밋하지 않았다.

사용자 승인 후 호스트 Git으로 staged diff와 모든 로컬 ref의 이력을 임시 파일에 먼저 추출하고, 네트워크를 끈 Gitleaks 컨테이너의 stdin으로 전달하도록 수정했다. Git 추출에 실패하면 그 단계에서 중단하고 shallow·빈 이력도 거부한다. root·merge와 삭제된 내용도 검사하는 로그 옵션을 사용한다. 임시 디렉터리는 종료 시 정리하고 탐지값은 마스킹한다.

합성 비밀값으로 일반 저장소·worktree의 정상 검사, staged 탐지, 다른 브랜치에서 삭제된 비밀 탐지, shallow 거부를 확인했다. 이 회귀 검증은 당시 임시 저장소에서 실행한 확인이며 저장소에 상설 회귀 테스트 코드가 추가됐다는 뜻은 아니다.

“전체 이력”은 로컬 ref로 도달 가능한 Git 이력을 뜻한다. 외부 복제본·삭제된 원격 자료·조회하지 못한 자료까지 검사한다는 뜻은 아니다. CI는 fetch-depth: 0을 유지한다.

### 8. 앞으로 구현하는 순서와 인프라가 움직일 때

1. 공통 문서·규칙을 정리하고 전체 검증·PR 병합으로 같은 시작점을 만든다.
2. 합성 JSON 한 건을 저장하고 최소 API 조회·중복 처리를 확인한다. 인프라는 기존 MySQL·실행·검증을 지원한다.
3. 최소 Next 환경·목록·상세를 연결한다. 이때 실제 도구 호환성·안전한 중계·크기·기한·이미지와 필요한 프론트 검증을 함께 결정한다.
4. 샘플 WAS 한 대가 만든 로그를 자동 전송한다. 승인된 전송 한도·재시도·진단·업무 요청 영향 확인을 지원한다.
5. 검색·필터·커서·복구를 완성한다. 안전한 키 주입·수명은 이 기능 도입 전에 정한다.
6. 세 WAS로 확대해 장애·포화·중복·종료·통합을 검증한다. 필요한 측정 결과로 초기값을 조정하고 이유를 기록한다.

현재 요청은 학습 기록 작성이다. 이 순서를 읽었다고 기능 구현·검증 실행을 시작하지 않는다. 이후 실제 작업에서도 최신 main·규칙을 확인하고 기능별 브랜치·worktree를 사용한다.

### 9. 블로그에 옮길 수 있는 구성과 표현

#### 권장 글 목차

1. 분산된 서버 로그를 한곳에서 찾고 싶었던 이유
2. 제품 기능보다 먼저 실행·검증 기반을 만든 이유
3. Maven에서 Gradle로 전환하며 함께 바꾼 부분
