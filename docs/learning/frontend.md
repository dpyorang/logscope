### 1. 해결하려는 문제와 프론트의 역할

여러 서버에 로그가 따로 쌓이면 오류가 발생할 때 어느 서버부터 확인해야 할지 찾는 데 시간이 든다. logscope의 목표는 로그를 한곳에 모아 발생 서버와 원인 메시지·stack trace를 찾는 것이다. 개발 취지는 총괄이 전달한 사용자 설명을 근거로 하며, 프론트 채팅에서 처음 제안한 제품 아이디어가 아니다.

프론트는 로그를 저장하는 역할보다 **사람이 읽고 좁혀 찾도록 돕는 역할**을 맡는다. 예를 들어 합성 서버 was-2의 ERROR를 목록에서 발견하고, 상세에서 메시지와 예외의 호출 경로를 읽는 흐름이다. 서버 ID·시각·레벨이 잘 보여야 하고, 조회 실패를 ‘로그 없음’으로 잘못 표현해서도 안 된다.

Spring Boot는 수집·입력 검증·중복 판정·저장·검색을 담당한다. MySQL은 데이터를 보관한다. Next.js는 화면 렌더링과 브라우저 조회 중계를 담당한다. 프론트가 Spring Boot의 검색 규칙을 별도로 다시 만드는 구조는 채택하지 않았다.

### 3. 비슷해 보이는 기술의 역할 구분

| 이름 | 쉬운 설명 | logscope에서 맡을 역할 |
| --- | --- | --- |
| TypeScript | JavaScript에 자료형 검사를 더하는 언어 | 시각·서버 ID·응답 구조·화면 상태를 코드에서 구분 |
| React | 화면을 작은 구성 요소로 나누고 상태에 맞게 보여주는 도구 | 목록·필터·상세·로딩·오류 화면 구성 |
| Next.js | React 앱의 라우팅·서버 렌더링·서버 요청 처리를 제공하는 프레임워크 | 처음 화면의 SSR과 후속 조회 중계 |
| Node.js | 서버에서 JavaScript를 실행하는 환경 | Next.js SSR 서버 실행. Java를 대체하는 것이 아님 |
| npm | 프론트 패키지를 설치하고 정해 둔 작업을 실행하는 도구 | 의존성·잠금 파일·개발·검사·빌드 명령 관리 |

자료형 예를 들면 `hasException`은 true/false이고 `message`는 문자열이다. TypeScript는 코드에서 둘을 잘못 사용하는 실수를 발견하는 데 도움이 된다. 그러나 서버에서 실제로 잘못된 JSON이 오지 않는다고 보장하지는 않는다. 실행 중 응답 구조 확인과 오류 처리가 별도로 필요하다.

#### SSR, Client Component, hydration

SSR은 요청을 받은 서버가 데이터를 읽고 초기 화면의 HTML을 만들어 보내는 방식이다. logscope의 채택 방향은 Next.js가 Spring Boot 목록 API를 호출해 첫 화면을 만드는 것이다. 사용자가 필터를 편집하거나 로그 상세를 여는 동작은 브라우저의 상태와 이벤트 처리가 필요하다.

hydration은 서버가 만든 초기 화면에 브라우저가 React 동작을 연결하는 과정으로 이해할 수 있다. 서버에서 ‘최근 15분’을 계산하고 브라우저가 즉시 다른 현재 시각으로 다시 계산하면 초기 조건이 달라질 수 있다. 그래서 **서버가 계산한 절대 시간 경계와 첫 데이터를 함께 전달하고 브라우저 준비만으로 첫 조회를 반복하지 않기로 했다.** 이것은 명세상 선택이며 실제 hydration 성공을 확인한 결과는 아니다.

Server Component라는 이름만 보고 매 요청마다 최신 데이터를 읽는다고 가정하지 않는다. 요청 시 렌더링과 데이터 캐시 정책을 함께 정해야 한다. 관련 공식 설명은 [Server/Client Components](https://nextjs.org/docs/app/getting-started/server-and-client-components), [connection](https://nextjs.org/docs/app/api-reference/functions/connection)을 참고한다. 이 문서는 기존 공식 참고를 연결하며 새 설치나 동작 검증은 수행하지 않는다.

#### 조회 중계란 무엇인가

```text
최초 화면: 브라우저 → Next.js SSR → Spring Boot → MySQL
후속 조회: 브라우저 → Next.js 조회 중계 → Spring Boot → MySQL
로그 수집: 샘플 WAS → Spring Boot → MySQL
```

중계는 브라우저 요청을 대신 전달하는 얇은 창구다. SSR이 자기 Next.js 중계 주소로 HTTP 요청을 한 번 더 보내지 않고 공통 서버 전용 API 클라이언트를 직접 사용하도록 했다. 브라우저 후속 조회도 중계 안에서 같은 클라이언트를 사용하면 오류 처리와 데이터 변환이 따로 달라지는 일을 줄일 수 있다.

브라우저가 같은 출처의 Next.js만 호출하는 구조에서는 해당 조회 흐름의 브라우저 CORS 구성이 단순해진다. 하지만 중계는 인증 장치가 아니다. 인증 전에는 로컬·격리 개발 환경에서 합성 로그로 검증한다. 내부 주소는 서버 전용으로 두고 `NEXT_PUBLIC`에 넣지 않는다. 브라우저가 화면에 표시할 로그 데이터까지 비공개가 된다는 의미도 아니다. [공식 중계 패턴 설명](https://nextjs.org/docs/app/guides/backend-for-frontend)

#### 캐시 비사용과 실시간은 다르다

캐시는 이전 결과를 재사용하는 방식이다. 로그 화면에서는 이전 목록이 최신 결과처럼 보일 수 있어 Next.js 로그 조회에 `cache: no-store`, 조회 응답에 `Cache-Control: no-store`를 적용하는 방향을 채택했다. ISR·공유 데이터 캐시도 사용하지 않는다. [fetch 설명](https://nextjs.org/docs/app/api-reference/functions/fetch)

캐시를 쓰지 않아도 이미 열린 화면에 새 로그가 자동으로 들어오지는 않는다. MVP는 사용자가 누르는 수동 새로고침 방식이다. 외부 프록시까지 같은 캐시 규칙을 적용하는 세부 설정은 인프라 영역과 맞춰야 한다.

### 4. 화면 상태가 API 연동의 일부인 이유

#### 입력값, 요청 조건, 성공 결과의 조건은 다를 수 있다

사용자가 was-2 결과를 보고 있는 중 서버 선택을 was-3으로 바꿨다고 가정한다. 아직 조회 버튼을 누르지 않았다면 목록은 계속 was-2 결과다. 이때 화면이 was-3 결과라고 표시하면 잘못된 설명이 된다. 그래서 편집 중 입력·진행 중 요청·마지막 성공 조건을 구분한다.

시간도 같다. 합성 예로 03:00~03:15 UTC 요청이 실패했을 때 재시도는 같은 범위를 쓴다. ‘최근 15분 새로고침’은 실행 시각에 맞춰 범위를 다시 계산한다. **재시도는 같은 조사를 다시 하는 행동이고 새로고침은 새로운 시점의 결과를 요청하는 행동**이므로 구분했다.

#### 성공 0건과 실패는 다르다

| 상태 | 의미 | 명세상 처리 |
| --- | --- | --- |
| 최초 로딩 | 아직 결과를 모름 | 진행 안내. 0건으로 단정하지 않음 |
| 정상 빈 결과 | 서버가 성공 응답으로 빈 목록을 줌 | 조건에 맞는 로그 없음. 수집 시스템 정상 여부는 추정하지 않음 |
| 첫 조회 실패 | 데이터를 받지 못함 | 오류와 수동 재시도 제공 |
| 재조회 실패 | 예전 성공 결과만 있음 | 기존 목록·상세·적용 조건 유지, 이전 결과임을 표시 |
| 상세 404 | 선택한 이벤트가 없음 | 통신 실패와 구분해 목록 복귀·재조회 안내 |
| exception=null | 정상 로그이나 예외 내용이 없음 | ‘예외 정보 없음’. 조회 실패로 처리하지 않음 |
| 비JSON·잘못된 성공 응답 | 기대한 API 구조가 아님 | 빈 성공으로 바꾸지 않고 안전한 오류 안내 |

API `code`와 필드별 오류로 안내를 정하고 서버 `detail` 문구에 의존하지 않는 방향이다. 내부 SQL·서버 stack trace·원시 HTML을 오류 안내에 그대로 출력하지 않는다. 수집된 로그의 합성 stack trace를 상세에서 보여주는 것과, API 서버 자신의 내부 오류를 노출하는 것은 다르다.

#### 커서와 늦은 응답

커서는 다음에 읽을 위치를 서버가 알려주는 표식이다. 프론트는 내용을 해석하거나 조립하지 않고 그대로 전달한다. 다음은 오래된 로그, 이전은 더 최신 로그 방향이며 응답 커서가 null이면 해당 이동을 막는다. 총 페이지나 번호 이동은 제공하지 않는다.

페이지를 읽는 중 ‘최근 15분’을 매번 다시 계산하면 조사 범위가 흔들리므로 절대 from/to를 고정한다. 만료·무효·조건 불일치에서는 기존 결과를 보존하고 커서만 제거하는 수동 복구를 제공한다. 서버가 처음 목록으로 자동 대체한 것처럼 취급하지 않는다. 완전한 스냅샷은 보장되지 않으며 늦게 수집된 로그는 새로고침으로 확인한다.

이전 요청이 늦게 도착하는 문제도 있다. was-2 조회 뒤 was-3을 조회했는데 was-2 응답이 나중에 왔다면 이를 폐기해야 한다. 요청 취소를 시도하는 것과 늦은 결과를 화면에 반영하지 않는 것은 별도 책임이다. 목록 재조회 중 새 상세 선택 제한·기존 상세 요청 무효화의 정확한 동작은 검토 의견이며 디자인과 최종 조율이 필요하다.

#### UTC, 한글 안내와 접근성

서버와 브라우저의 시간대가 다를 수 있어 목록·상세·필터에 UTC를 명시하기로 했다. 예: `2026-10-27 03:15:42.123 UTC`. 시작은 포함, 종료는 제외한다. 조회 폭 최대 24시간은 한 번의 검색 범위이며 보존 기간이 아니다.

한글 안내는 ‘실패’라는 단어만 보여주기보다 사용자가 다음에 할 일을 설명하는 방향이다. 예를 들어 ‘조건에 맞는 로그가 없습니다’와 ‘로그를 불러오지 못했습니다’는 다르게 쓴다. `stack trace` 같은 기술 용어는 ‘예외가 발생한 호출 경로’처럼 짧은 설명을 붙일 수 있다. 다만 전체 언어 정책과 개별 최종 문구를 모두 확정한 상태는 아니다.

접근성은 화면을 조작하는 방법도 명세로 만드는 일이다. 상세 버튼은 마우스 행 클릭 외에 키보드로도 실행할 수 있어야 한다. 열 제목·입력 레이블·오류 연결·눈에 보이는 초점이 필요하다. 레벨은 빨간색만으로 ERROR를 나타내지 않고 텍스트도 보여준다. 비모달 상세 패널은 다른 화면 조작을 막지 않으며 초점을 가두지 않는다. 명시적으로 상세를 열면 제목으로 이동하고 닫으면 원래 버튼으로 돌아오는 기준을 채택했다. 이는 접근성 통과 결과가 아니라 앞으로 확인할 요구사항이다.

### 5. 채택한 방식의 이유, 대안과 비용

| 선택 | 선택 이유 | 검토할 수 있는 대안과 단점 |
| --- | --- | --- |
| TypeScript | 데이터·상태의 자료형 실수를 일찍 확인 | JavaScript만 사용하면 초기 구성이 적을 수 있으나 타입 검사의 도움은 줄어듦. TypeScript도 실행 중 응답 검증을 대신하지 못함 |
| Next.js SSR + 브라우저 상호작용 | 사용자 직접 선택 방향. 처음 화면은 서버에서 만들고 이후 조작은 브라우저 상태로 관리 | 브라우저 중심 SPA도 대안이지만 채택하지 않음. SSR에는 Node 실행·서버/브라우저 경계·hydration 확인이 추가됨. 성능·SEO 개선을 측정해 선택한 것은 아님 |
| npm | Node에 포함된 도구를 사용해 초기 설치·학습 부담을 줄임 | pnpm·Yarn도 대안이나 이 채팅에서 속도·용량을 비교 측정하지 않음. npm이 항상 빠르다고 주장할 근거 없음 |
| 정확한 버전·잠금 파일·npm ci | 로컬과 CI의 의존성 차이를 줄이고 선언 불일치를 실패로 발견 | 자동 최신 추종은 갱신 작업이 적어 보이나 예상치 못한 변경이 들어올 수 있음. 고정해도 보안 갱신 책임은 남음 |

| 제한된 조회 중계 | 같은 출처 연결과 공통 API 처리를 유지 | 브라우저 직접 호출은 중계가 줄지만 CORS·주소·향후 인증 연결을 별도로 다뤄야 함. 중계는 네트워크 경유와 오류 경계를 추가함 |
| 캐시 비사용 | 이전 로그 결과를 최신처럼 재사용하지 않게 함 | 조회 부하를 캐시로 줄이지 못함. 실제 부하와 응답 시간은 미측정 |
| 수동 갱신·이전/다음 | 첫 MVP의 조작과 상태를 단순하게 유지 | 자동 갱신은 최신성에 도움이 될 수 있으나 읽던 행·상세가 움직이는 정책이 추가됨. 이후 범위로 분리 |

채택 버전 기록: Next.js 16.4.3, TypeScript 7.0.2 strict, React/react-dom 19.3.1, Node.js 24.22.1 LTS, npm 11.19.1. 이 조합은 설치·빌드·SSR로 검증하지 않았다. 최신 또는 무취약 조합이라고 쓰면 안 된다. 구현 단계에서 공식 지원·보안·peer dependency와 실제 동작을 확인하고 문제 시 이유를 기록해 조정한다. [환경 명세의 공식 참고와 변경 근거](../contracts/frontend-environment-draft.md)

### 7. 실제로 한 일과 아직 하지 않은 일

| 근거 범위 | 수행·결정 | 한계 |

작성 시 읽은 추적 대상 파일 목록에는 Java 초기 앱과 설정·테스트가 있고 프론트 소스는 확인되지 않았다. 이는 현재 주 작업 폴더에서 확인한 범위이며 다른 체크아웃·채팅 전체를 조사한 결과는 아니다. 이 프론트 채팅에는 후속 기능 구현 기록이 없다. 이번 학습 문서 작성에서도 설치·테스트·전체 verify는 실행하지 않는다.

### 8. 이후 구현은 어떻게 진행하나

최신 기준은 [기능 단위 개발 방식](../feature-development-workflow.md)이다. 초기에는 WAS 전송을 화면보다 먼저 두었지만, 사용자가 작은 결과를 보며 이해하도록 순서가 바뀌었다. 모든 추천을 지금 확정한 다음 개발하는 방식도 대체됐다.

1. 공통 문서·규칙을 정리하고 전체 검증·PR 병합으로 시작 기준을 맞춘다.
2. 백엔드에서 합성 JSON 한 건을 저장하고 최소 조회로 다시 읽는다.
3. 프론트 최소 환경과 목록·상세를 연결해 브라우저에서 서버·메시지·trace를 읽는다. 이때 버전 호환성, 필요한 중계·응답 제한·기한·실행·검증 연결을 정한다.
4. 샘플 WAS 한 대의 자동 전송을 붙인다.
5. 검색·필터·커서·복구를 완성한다. 안전한 키 주입 등 그 기능의 필수 사항을 착수 전에 결정한다.
6. 세 WAS와 장애·포화·중복·종료·통합 흐름을 확인한다.

기능 하나가 크면 작은 PR로 나눈다. 승인 초기값은 시작점으로 유지하되 실행 근거가 생기면 변경 이유를 기록한다. 보안·필수 검증·API 호환성은 뒤로 미루지 않는다. Java는 Gradle, 프론트는 npm을 쓰고 verify.sh에서 필요한 전체 검증을 실행하는 원칙은 확정이지만 프론트 검사 연결 구현은 아직 없다. 문서 채택은 기능 착수 승인이 아니므로 실제 구현은 별도 요청 후 시작한다.

### 9. 블로그 글로 옮길 때

#### 추천 목차

## 주제: 프론트 초기 환경과 SSR 실행 기반 / 시간: 2026-10-27 16:16 KST

### 1. 사용자 요청과 목표

사용자는 최신 main에서 별도 브랜치와 worktree를 만들고 프론트 초기 환경을 세팅하며 필수 검증까지 진행하도록 요청했다. 백엔드 API 연결은 다음 작업으로 남겼다. 이번 도착점은 실제 브라우저와 Node 컨테이너에서 한글 기본 화면을 열 수 있는 상태다.

### 2. 추가·변경한 내용

frontend/에 Next.js App Router·TypeScript strict·React 프로젝트와 잠금 파일을 만들었다. 루트 페이지는 connection()으로 요청 시 서버에서 렌더링하며 현재 로그 데이터가 연결되지 않았음을 표시한다. 가짜 로그 결과를 넣지 않았다. HTML lang=ko, 본문 바로가기·랜드마크·초점 표시·모바일 줄바꿈을 구성했다.

개발·타입·lint·포맷·빌드·브라우저 검사 명령을 구성하고 verify.sh에서 기존 Java·실제 MySQL·비밀 검사·Compose·이미지 검사와 함께 실행한다. standalone 빌드 뒤 public과 .next/static도 복사한다. 별도 Node 이미지와 로컬 Compose 서비스로 실행하며 기본 node 사용자, loopback 바인딩, 자체 health/live를 사용한다. health UP은 서버가 응답한다는 의미이며 API·DB 준비를 뜻하지 않는다.

### 3. 선택 이유와 대안

처음 채택했던 TypeScript 7.0.2는 tsc가 실행돼도 typescript-eslint가 컴파일러 API 미지원 오류로 중단됐다. 단일 컴파일러로 검사·빌드를 맞추기 위해 TypeScript 6.0.3으로 조정했다. TypeScript 7과 6을 나란히 두는 대안도 있지만 첫 환경에 두 컴파일러를 유지하는 복잡성을 추가하지 않았다.

ESLint 9는 Next 기본 구성과 실행 가능했으나 npm의 지원 종료 경고가 있었다. 최종은 ESLint 10.13.0에 공식 Next 플러그인·React Hooks·typescript-eslint 권장 규칙을 직접 연결한다. peer 제한을 강제 우회하거나 lint를 끄지 않는다. Next.js 16.4.3·React 19.3.1·Node 24.22.1·npm 11.19.1은 유지한다. Prettier 3.9.10과 Playwright 1.64.1도 정확히 고정한다.

JavaScript를 끈 Chromium 확인은 ‘브라우저가 나중에 그렸으니 SSR도 될 것’이라는 추측을 피하기 위해 넣었다. 백엔드 없이도 환경을 확인하고 다음 API 연결 작업의 실패 원인을 나눌 수 있게 했다.

### 4. 동작 확인과 한계

JavaScript 없는 첫 HTML에서도 한글 제목·내용·no-store가 전달된다. Chromium에서 본문 바로가기와 360px 화면의 가로 넘침, 페이지 오류와 API 미호출, health와 정적 자산 제공을 확인했다. 데스크톱 1280px와 모바일 360px 화면도 직접 읽었다. 실제 standalone 서버와 최종 Node 이미지의 생존·SSR 응답을 확인했다.

기존 MySQL 통합 테스트는 1건, 프론트 Chromium은 3개 시나리오 범위다. 전체 접근성·다른 브라우저·부하 성능·로그 API 연결을 보장하지 않는다. Node는 공식 체크섬을 확인한 배포본을 임시 도구 경로에서 실행했으며 시스템 전체 영구 설치를 뜻하지 않는다. 프로덕션 의존성 audit 조회는 당시 알려진 항목 0건이었으나 영구 무취약 보장이 아니다.

### 5. 배운 개념과 남은 일

컴파일러가 실행된다는 사실과 그 컴파일러를 사용하는 도구 전체가 호환된다는 사실은 다르다. 이번에는 타입 검사와 lint를 따로 실행했기 때문에 차이를 발견했다. standalone은 서버 코드만 복사하면 끝나는 것이 아니라 브라우저가 사용할 CSS·JS와 public 자산도 포함해야 한다.

기본 화면은 기능 완료 화면이 아니라 다음 연결을 위한 시작점이다. 다음 작업에서 실제 저장된 합성 로그의 목록·상세, 공통 서버 클라이언트·제한된 GET 중계·오류·기한·응답 상한을 해당 범위에 맞게 결정한다. 현재 백엔드 연결 주소나 조회 중계는 만들지 않았다.
