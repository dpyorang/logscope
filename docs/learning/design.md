## 주제: MVP 디자인 설계와 결정 과정 / 시간: 2026-10-27 (작성 시각 미기록)

### 이전 문서 안내와 기록 방식

작성일: 2026-10-27. 이 문서는 디자인 채팅의 직접 대화와 아래 프로젝트 문서를 바탕으로 요청·제안·결정 이유를 설명하는 학습 자료다. 새로운 정책이나 구현 승인이 아니다. 예시는 합성 데이터이며 실제 고객·서버 정보가 아니다.

### 기록을 쌓는 방식

2026-10-27 사용자 요청에 따라 이 문서에 기능별 학습 내용을 계속 추가한다. 기존 기록은 보존하고, 새 기록은 문서 아래에 시간순으로 덧붙인다. 각 기록의 상단은 `주제 / 시간`으로 통일하고 그 아래에 추가 내용을 정리한다. 시간은 Asia/Seoul(KST) 기준이며 실제 시각을 확인한 경우 분까지 적고, 날짜만 확인되는 과거 기록은 시각을 추정하지 않는다.

기능별로 사용자의 요청, AI 제안과 선택·보류 이유, 실제 구현·변경 내용, 쉬운 개념·예시, 확인한 결과와 근거, 남은 문제·다음 단계를 기록한다. 제안·확정·구현·검증 상태는 구분하고 확인하지 않은 결과는 완료로 쓰지 않는다. 다른 채팅의 구현은 근거를 전달받거나 확인한 범위만 기록한다. 문서 작성만 한 경우에도 구현 기록과 구분한다.

향후 기록 제목 예시: `## 주제: 최소 로그 목록·상세 연결 / 시간: YYYY-MM-DD HH:mm KST`. 이는 형식 예시이며 해당 기능을 구현했다는 뜻은 아니다.

상태: 설계·학습 문서 작성. UI 구현·실행 검증 전.

### 1. 해결하려는 문제와 디자인의 역할

사용자가 공유한 출발점은 이커머스 환경의 분산 로그다. Front Office WAS 두 대, Back Office WAS 두 대와 BATCH에 로그가 따로 쌓여, 오류가 나면 먼저 어느 서버인지 찾고 많은 로그에서 원인을 찾아야 했다. MVP는 같은 샘플 앱을 was-1·was-2·was-3으로 실행해 이 문제를 작게 재현한다.

디자인의 목표는 예쁜 통계 화면을 먼저 만드는 것이 아니라 개발자가 ‘오류 발견 → 발생 서버 확인 → 상세 메시지·stack trace 확인’을 이어가게 하는 것이다. 디자인은 사용자 흐름·정보 배치·상태·조작·접근성을 맡고, 프론트는 이를 구현하며 백엔드는 저장·검색·API를 담당한다. 화면이 조회에 성공했다는 사실과 로그가 빠짐없이 수집됐다는 주장은 다르다.

### 2. 누가 요청·제안했고 무엇이 승인됐나

직접 대화의 출처와 총괄이 전달한 승인 기록을 구분한다. 문서 반영 요청은 다른 분야와 최종 합의했다는 뜻이 아니다.

| 주제 | 사용자 직접 요청 또는 공유된 요청 | AI 제안·설명 | 승인 여부와 현재 상태 |
| --- | --- | --- | --- |
| 제품 목표 | 총괄을 통해 분산 서버 로그를 한곳에서 관측하려는 사용자 배경 공유 | 오류와 서버·원인 탐색을 중심 흐름으로 해석 | 제품 목표로 공유됨. 최초 기술 선택 제안자는 출처 확인 필요 |
| 첫 화면 | 직접 ‘사용자 흐름과 첫 화면 구성 제안’, 파일 수정 없이 논의 요청 | 통합 목록과 우측 상세, 필터·페이지·수동 갱신 제안 | 후속 공통 합의에 목록·비모달 상세가 확정됨 |
| 차트보다 로그 | 공유된 MVP 계획이 첫 화면을 목록·필터·상세에 집중하도록 명시 | 오류 서버와 원문 확인에 필요한 정보부터 배치한 이유 설명 | MVP 범위로 확정. 차트 우선 제외의 최초 제안자는 출처 확인 필요 |
| 디자인 초안 | 총괄을 통해 지정 문서 작성 요청 | 상태·접근성·API 의존 사항까지 초안 작성 | 문서 작성 수행. UI 구현 승인은 아님 |
| 미합의 항목 | 직접 추천안·이유·프론트/백엔드 확인점 정리 요청 후 문서 반영 요청 | 1,200px·55:45·16/14px·8px, 기본 줄바꿈, 51건 등 제안 | 문서 반영 승인. 수치·세부 동작은 분야 간 합의 전 제안 |
| 시간·검색·커서 | 공통·백엔드·프론트 문서에 후속 사용자 승인 기록 | 디자인의 오래된 미결정 표현을 최신 기준에 맞춤 | 최근 15분·UTC 밀리초·최대 24시간·기본 50건 커서 등 확정. 최초 제안자 전체는 직접 확인 불가 |
| SSR 복구 | 직접 SSR 최초 로딩·실패·재시도 추천과 문서 반영 요청 | 같은 절대 조건 목록 재시도와 페이지 재진입 구분 | 기존 SSR·재시도 원칙은 확정. 화면 표현·복구 세부는 합의 대기 |
| 상세 경합·초점 | 직접 검토한 수정·구체화안을 문서에 반영 요청 | 진행 중 상세 무효화, 기존 원문 유지, 제거되는 상세 내부 초점 복귀 제안 | 디자인 문서에 제안으로 반영. 프론트 등과 최종 합의 전 |
| 총괄 전달 | 직접 확정·미합의 사항 전달 요청 | 확정/제안을 구분해 총괄에 메시지 전달 | 실제 전송 수행. 이번 학습 작업에서는 추가 전송 없음 |
| 진행 방식 | 총괄이 기능 단위 개발 방식의 사용자 승인 공유 | 한 건 표시 후 필요한 결정을 단계별로 진행 | 최신 공통 기준. 모든 시각·복구 제안의 선확정을 요구하던 방식 대체 |
| 문서·용어 | 사용자 요청으로 공유된 문서 보존 및 용어 정책 | 기존 파일 보존, 변경 이유 기록, API 명세·공통 로그 형식·분야 간 합의 표현 적용 | 공통 규칙으로 확정 |

### 3. 핵심 개념을 예로 이해하기

#### 정보 우선순위와 점진적 상세

목록에는 발생 시각·레벨·서버·메시지를 둔다. 예를 들어 `03:00:00.123 UTC / ERROR / was-2 / Synthetic failure`만으로 먼저 오류와 서버를 식별한다. 서비스명·eventId·전체 메시지·trace는 선택한 상세에서 읽는다. 목록에 모든 trace를 펼치면 다른 오류를 비교하기 어렵기 때문에 요약과 원문을 나눈다. 서버는 원문을 자르지 않고 화면에서만 요약한다.

hasException은 ‘예외 정보 있음’을 뜻하는 작은 텍스트·아이콘 표시다. ERROR라고 항상 trace가 있는 것은 아니며 다른 레벨에도 예외가 있을 수 있다. 상세의 exception=null은 정상적인 예외 없음이고, 필드 누락이나 통신 실패를 예외 없음으로 바꾸면 안 된다.

#### 비모달 상세와 모달의 차이

모달은 대화상자에 조작을 집중시키는 방식이다. 비모달 패널은 목록과 상세를 함께 살펴볼 수 있게 한다. MVP는 넓은 화면에서 우측 패널, 좁은 화면에서 하단 상세를 사용한다. 목록 맥락을 보존할 수 있지만 긴 원문을 읽을 폭이 줄고 초점 관리가 필요하다는 단점이 있다. 별도 상세 페이지나 모달이 일반적으로 나쁜 것은 아니며 이 탐색 흐름에서는 패널을 선택한 것이다.

#### 로딩·빈 결과·오류는 서로 다른 사실

| 상태 | 뜻 | 화면에서 피할 오해 |
| --- | --- | --- |
| 로딩 | 결과를 아직 모름 | 0건이라고 표시하지 않음 |
| 빈 결과 | 정상 조회했지만 조건에 맞는 항목이 없음 | 수집 정상·장애 여부를 단정하지 않음 |
| 조회 실패 | 데이터를 판단할 수 없음 | 빈 배열 성공으로 바꾸지 않음 |
| 재조회 실패 | 새 요청 실패, 기존 성공 결과는 남아 있음 | 기존 결과를 최신 결과처럼 표시하지 않음 |

따라서 최초 실패에는 ‘이전 결과’를 쓰지 않고, 재조회 실패에는 이전 결과임을 알린다. API 내부 오류 stack trace와 사용자가 조회하려는 합성 로그의 trace도 서로 다르다. 전자는 노출하지 않고 후자는 제품의 상세 정보로 보여준다.

#### UTC·발생 시각·시간 경계

공통 시간대와 정밀도를 사용해 여러 서버의 시각을 비교하려는 설계다. 화면은 `2026-10-27 03:00:00.123 UTC`처럼 표시하고 API는 Z 형식을 사용한다. `03:00~03:15`는 시작 포함·종료 제외이므로 정확히 03:15에 발생한 로그는 제외된다. 최대 24시간은 한 번에 조사할 범위이며 보존 기간이 아니다. UTC 사용만으로 서버 시계 오차가 자동 보정되지는 않는다.

초기 AI 제안은 초 단위 표시였으나 후속 승인 명세에서 밀리초로 구체화돼 대체됐다. 기본 최근 15분은 방금 발생한 오류 탐색의 출발점이고 확정된 성능 보장값은 아니다.

#### 새로고침과 재시도

03:00~03:15 조회가 실패했다면 03:17의 재시도도 같은 범위를 사용한다. 최근 15분 새로고침은 03:02~03:17로 다시 계산한다. 직접 입력한 절대 범위는 새로고침에서도 유지한다. 편집 중 필터와 마지막 성공 조건, 실패 요청 조건을 구분해야 같은 버튼이 다른 조사를 몰래 실행하지 않는다.

목록은 자동으로 삽입·재정렬되지 않는다. 수동 갱신은 읽던 위치를 안정적으로 유지하지만 새 로그를 보려면 사용자가 갱신해야 하는 단점이 있다. 마지막 조회 시각은 결과를 성공적으로 받은 시점이며 마지막 로그 발생 시각이나 수집 완전성을 뜻하지 않는다.

#### 커서와 페이지 일관성

커서는 ‘다음 탐색 위치’를 서버가 준 불투명한 값이다. 화면은 내용을 해석하지 않고 전달한다. 최신순 50건을 읽고 다음을 누르면 더 오래된 쪽으로 간다. 동일 발생 시각은 eventId 순서로 구분한다. 탐색 중 절대 시간과 조건을 고정하지만 완전한 스냅샷을 보장하지 않으며 늦게 수집된 로그는 새로고침으로 확인한다. 총 건수·번호 이동이 없는 것은 오류가 아니라 채택한 탐색 방식이다. 화면 50건 고정은 아직 UI 제안이고 API는 size 1~100을 지원한다.

#### 접근성은 흐름의 일부

마우스 없이 필터·페이지·상세·복사를 사용할 수 있어야 한다. ERROR를 빨간색만으로 나타내지 않고 텍스트도 표시한다. 상세를 열면 제목으로, 닫으면 실행 버튼으로 돌아가는 흐름은 키보드 사용자가 위치를 잃지 않게 한다. 패널 안에 초점을 가두지 않는다.

목록 성공으로 상세가 제거될 때 그 안에 초점이 있으면 목록 제목으로 복귀시키자는 추가안은 합의 전이다. 화면에 남는 요소의 초점까지 옮기지는 않는다. 대비 목표·200% 확대·보조기기 상태 알림은 문서에 있지만 실제 UI 접근성 통과를 검증한 것은 아니다.

### 4. 채택 방식의 이유·대안·단점

| 선택 또는 제안 | 이유 | 대안과 부담 | 상태 |
| --- | --- | --- | --- |
| 차트보다 목록·필터·원문 | 첫 목표인 오류 서버와 원인 로그를 직접 찾음 | 차트는 추세 파악에 유용하지만 상세 탐색 외 작업·집계가 추가됨 | MVP 확정 |
| 비모달 상세 | 목록을 잃지 않고 여러 로그 비교 | 모달은 영역 집중, 별도 페이지는 넓은 원문에 유리하나 탐색 맥락 이동 필요 | 형태 확정 |
| 수동 갱신 | 읽던 내용을 갑자기 바꾸지 않음 | 실시간·자동 갱신은 새 로그 인지가 빠르지만 재정렬·연결·상태 복잡성 증가 | MVP 확정 |
| UTC·밀리초 | 서버 간 비교 형식을 통일 | 사용자 현지 시간은 익숙하지만 변환·표시 규칙이 추가됨. UTC는 익숙해질 필요가 있음 | 확정 |
| SSR 첫 목록·후속 중계 | 채택된 프론트 구조에서 같은 상태로 첫 표시와 후속 조작 연결 | 브라우저 첫 조회만 쓰는 구조도 가능하나 현재 승인 방향은 SSR. SSR에는 별도 Node 실행·실패 경계가 추가됨 | 방향 확정, 세부 합의 대기 |
| trace 기본 줄바꿈 | 처음에는 가로 이동을 줄임 | 끄면 긴 경로 비교가 편하지만 가로 탐색 필요. 켜면 줄이 길게 감겨 구조 파악이 어려울 수 있음 | 기본값은 제안, 전환·원문 복사는 확정 범위 |
| 밝은 테마·구체 배치값 | 초기 검토 기준을 작게 정함 | 어두운 테마도 가능하지만 두 테마의 대비·상태 검토가 추가됨 | 미확정 제안 |

SSR은 첫 HTML을 서버가 만드는 방식이다. logscope에서는 Next가 첫 절대 범위를 계산해 Spring Boot를 직접 조회하고 같은 데이터·시간·성공 시각을 브라우저에 인계한다. 브라우저 준비만으로 중복 첫 조회를 하지 않는다. 후속 조회는 Next 중계를 사용하며 검색·저장 로직은 Spring Boot가 맡는다. SSR 채택의 원래 사용자 대화·최초 제안자는 이 디자인 채팅에서 직접 확인할 수 없으며 공통 문서의 승인 기록을 근거로 한다. 성능·SEO 개선을 측정했다는 이유를 덧붙이지 않는다.

디자인과 직접 관련한 채택 방식은 위 표로 설명한다. 라이브러리 버전은 프론트 환경 문서의 채택 기록을 따른다. 이 학습 문서는 현재 버전 지원·보안·호환성을 새로 확인하지 않았다.

### 5. SSR 복구를 별도로 설계한 이유

SSR이 API 결과를 기다릴 때는 화면 틀과 진행 안내를 보여주자는 안이다. 최초 조회 실패에는 절대 조사 범위와 수동 재시도를 제안했다. 데이터 조회 실패는 화면을 유지하고 중계로 같은 조건을 다시 요청한다. Next 페이지 자체가 전달되지 않았다면 이 목록 복구 화면도 보장할 수 없어 페이지 재진입으로 나눈다. 재진입은 새로운 SSR이므로 같은 범위 보존을 보장하지 않는다.

첫 조회 완료와 브라우저 준비 전 필터·버튼을 제한하고 실패 후 편집을 허용하는 안은 입력 충돌을 줄이지만 기다리는 동안 편집할 수 없는 단점이 있다. 재조회 중 기존 상세는 읽고 닫고 복사하되 새 상세는 제한하는 안도 같은 절충이다.

이미 진행 중인 상세는 목록 재조회 시작 때 무효화·가능하면 취소하고 늦은 응답을 폐기하자는 안이다. 예를 들어 was-2를 읽던 중 새 목록을 요청했는데 이전 trace가 늦게 오면 새 선택의 내용처럼 보이면 안 된다. 이미 표시된 상세와 아직 끝나지 않은 요청을 구분하며 미완료 상세의 수동 재시도도 제안했다. 이 동작들은 프론트와 합의 전이며 취소가 서버 작업까지 즉시 멈춘다고 보장하지 않는다.

SSR·중계 5초와 브라우저 8초는 미합의 시작값이다. 표준·SLA·실측 응답 시간으로 쓸 수 없다. 오류·크기·기한은 중계 도입 시 필요한 범위를 먼저 합의한다.

### 7. 실제 한 일과 하지 않은 일

이 디자인 채팅에서는 역할·규칙 확인, 채팅 안 첫 화면 제안, 지정 디자인 문서 작성·수정, 공통/API/프론트 문서 대조, 명시적 요청에 따른 총괄 결과 전송을 수행했다. 이전 문서 수정 뒤 git diff --check의 공백 오류 확인을 수행한 기록이 있다. 이것은 UI 동작 검사나 전체 verify 통과가 아니다.

실제 UI 코드·앱·설정·테스트를 구현하거나 화면을 실행하지 않았다. 키보드·보조기기·대비·200% 확대·SSR 복구·성능을 실측하지 않았다. 디자인 작업은 화면 설계·학습 정리 범위였다. 초기 환경·CI·브랜치 보호의 성공은 인프라 기록에 있으며 이 채팅의 직접 실행 검증 결과가 아니다. 이번 작성에서 저장소 전체 기능 코드의 존재를 새로 감사하지 않았으므로 타 채팅의 이후 구현 여부를 단정하지 않는다.

이 문서에는 이해를 돕는 텍스트 예시가 있으며 실제 화면 캡처나 사용자 사용성 조사 결과는 없다. 제안 반영·명세 승인·코드 구현·실제 검증은 별개의 단계다.

### 8. 앞으로 진행하는 순서

최신 기능 단위 개발 방식을 따른다. 앞서 모든 제안을 구현 전에 확정하자는 설명은 각 기능에 필요한 결정만 하는 방식으로 대체됐다. 미결정을 전부 없애기 위해 첫 저장·조회 구현을 막지 않는다.

1. 총괄 중심으로 공통 문서·규칙 정리, 전체 검증과 PR 병합을 진행한다.
2. 백엔드가 합성 JSON 한 건 저장·최소 조회를 만든다. 디자인이 동시에 별도 UI를 시작하는 단계는 아니다.
3. 프론트·디자인이 최소 환경과 목록·상세를 연결해 서버 ID·메시지·trace 한 건을 읽게 한다. 이때 필요한 기본 화면·로딩·실패·중계 사항을 정한다.
4. 샘플 WAS 한 대의 오류가 화면에 나타나도록 자동 전송을 연결한다.
5. 검색·필터·커서·복구를 도입하면서 초점·상세 경합·지연 응답과 안전한 커서 키 주입 등 해당 기능 필수 사항을 정한다.
6. 세 WAS와 장애·중복·포화·종료를 통합 검증한다.

승인 초기값은 유지하되 측정 결과로 조정할 때 이유를 기록한다. 보안·필수 검사·분야 간 호환성은 미루지 않는다. 시각 수치와 큰 성능 목표는 필요 시점에 다루며 구현은 별도 요청 후 시작한다.

### 9. 블로그로 옮길 때

추천 목차는 ‘분산 로그에서 겪은 문제 → 첫 사용자의 질문 → 차트 대신 목록을 먼저 둔 이유 → 목록과 상세의 정보 분리 → 빈 결과와 실패의 차이 → UTC·새로고침·재시도 → SSR에서 새로 생긴 복구 경계 → 접근성과 미합의 제안 → 한 건부터 검증하는 다음 단계’다.

| 지금 쓸 수 있는 표현 | 아직 쓸 수 없는 완료 표현 |
| --- | --- |
| 오류·서버·trace를 찾는 사용자 흐름을 설계했다 | 실제 오류 원인을 찾아주는 UI를 완성했다 |
| 비모달 상세와 상태 전환을 명세에 정리했다 | 실제 키보드·스크린리더 검증을 통과했다 |
| SSR 실패와 페이지 자체 실패의 복구안을 구분했다 | SSR 복구·취소가 정상 동작함을 검증했다 |
| 시각 수치와 51건을 검토 시작값으로 제안했다 | 1,200px 배치가 최적이며 대규모 성능을 입증했다 |

블로그에서 ‘왜 선택했는지’는 설계 의도이고 ‘얼마나 좋아졌는지’는 측정 근거가 필요한 별도 주장이다. 이 글은 아직 설계 기록이다.

### 1. 사용자 요청과 목표

사용자가 백엔드 문서를 기준으로 모든 영역의 상단에 주제·시간·간략한 내용을 쌓고 아래에서 주제별 상세를 읽는 형식을 요청했다. 앞으로 구현 결과도 같은 형식으로 누적한다.

### 2. 추가·변경한 내용

이 파일의 최상단 목차를 세 열로 통일하고 각 행을 상세 기록에 연결했다. 이전 설명과 기록 시각은 보존했으며 새 기록은 목차 마지막 행과 본문 끝에 시간순으로 추가한다. 이번에는 문서 구조만 변경했다.

### 3. 선택 이유와 대안

영역마다 다른 구조를 읽는 부담을 줄이고 요청·선택 이유·실제 결과를 주제별로 찾기 위해 통일했다. 기존 자료를 삭제하거나 과거 시각을 추정해 새로 만들지 않았다. 초기 기록의 하위 구성은 이전 설명으로 보존하고 새 기록부터 공통 여섯 항목을 사용한다.

### 4. 동작 확인과 한계

형식·기록 보존·목차 연결을 확인하는 문서 변경이다. 기능 코드·설정·테스트 구현이나 실행 검증을 수행한 기록이 아니다. 기능 구현 기록과 문서 형식 변경을 구분한다.

### 5. 배운 개념과 남은 일

목차는 기록을 찾는 요약이고 상세는 판단과 결과를 이해하는 본문이다. 기록 시점과 실제 구현·검증 시점이 다르면 본문에 별도 표시한다. 이후 기능·기술 변경이 검증과 커밋까지 완료되면 같은 파일에 새 항목을 추가한다.
