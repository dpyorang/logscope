## 주제: 백엔드 설계 배경과 핵심 개념 / 시간: 2026-10-27 (작성 시각 미기록)

### 이전 문서 안내와 기록 방식

이 문서는 기능을 구현할 때마다 학습 내용을 누적한다. 기존 기록은 보존하고, 새로운 기능 기록은 아래 목차와 본문 끝에 시간순으로 추가한다. 각 기록의 상단에 **주제 / 시간(KST)**을 표시하고 그 아래에 배경·구현·결정 이유·검증 결과를 정리한다. 작성일만 확인되는 과거 기록에는 시각을 추정해서 넣지 않는다.

명세 자체는 [API 명세](../contracts/log-api-draft.md), 진행 방식은 [기능 단위 개발 방식](../feature-development-workflow.md)을 따른다. 제안·사용자 승인·실제 구현·실행 검증은 구분한다.

이전 목차의 주제·시각·상태는 이 문서 최상단의 공통 목차로 옮겨 보존했다. 기존 상세 설명은 아래에 유지한다.

아래 내용은 최초 학습 정리 당시의 기록이다. 이후 구현 상태는 뒤에 추가되는 기능별 기록에서 확인한다.

### 1. 해결할 문제와 백엔드 역할

사용자는 여러 WAS와 BATCH 서버에 로그가 따로 쌓여 오류 발생 서버부터 찾아야 했던 경험을 공유했다. logscope의 목표는 로그를 한곳에서 읽고 오류 발생 서버와 원인 stack trace를 찾는 것이다. 실제 쇼핑몰 업무를 다시 만드는 것이 목표는 아니다.

MVP는 같은 샘플 앱을 was-1, was-2, was-3으로 실행하고 HTTP로 로그를 전달하는 환경이다. 백엔드는 로그 수집 API, 입력 검증, 중복 판정, MySQL 저장, 목록·상세 조회와 서버 테스트를 맡는다. Next.js는 화면과 조회 중계를 담당하고 데이터 저장·검색 규칙을 다시 구현하지 않는다.

공부할 때는 ‘한 건을 보냈을 때 무엇을 약속하는가’를 먼저 생각하면 좋다. 저장 전 성공이라고 응답하면 응답 직후 장애에서 로그가 사라질 수 있다. 그래서 명세는 DB 저장 트랜잭션이 커밋된 뒤에만 신규 저장 성공을 반환한다.

### 2. 요청·제안·승인 상태

직접 사용자 대화가 있는 것은 그 대화를 근거로 적었다. 총괄에서 전달된 승인·배경은 전달 기록과 공통 문서 근거이며, 원래 대화의 문구를 직접 확인한 것으로 쓰지 않는다.

| 중계·응답 한도·미래 시간 허용 | 총괄이 검토 요청 | 목록 4 MiB·상세 512 KiB·URL 16 KiB·미래 5분 등 제안 | 미승인 검토 의견. 현행 확정값으로 쓰면 안 됨 |

| 첫 저장·조회 구현 | 이 채팅 사용자가 최신 main·별도 worktree·전체 검증·커밋·PR 요청 | 원격 갱신부터 시도 | 요청은 있었으나 코드 구현 전. 후속 학습 문서 요청으로 현재는 문서 작성만 수행 |

‘계약’이라는 초기 표현은 사용자 요청으로 API 명세·공통 로그 형식·분야 간 합의로 바꿨다. docs/contracts 경로는 기존 참조를 보존하기 위해 유지한다.

### 3. 기술별 역할

| 기술·개념 | 쉬운 설명 | logscope에서의 역할·한계 |
| --- | --- | --- |
| API | 다른 프로그램이 정해진 형식으로 요청하는 창구 | POST /api/v1/logs 수집, GET 목록·상세. API 명세는 입출력 규칙이며 구현 완료를 뜻하지 않음 |
| Java | 서버 동작을 작성하는 언어 | 입력 처리·저장·조회·전송 로직 작성. 채택 기록은 Java 25 |
| Spring Boot | 웹 서버·설정·데이터 접근 구성의 기반 | HTTP 요청을 처리하는 앱 실행과 구성. 채택 기록은 4.1.2 |
| JPA | Java 객체와 관계형 DB의 대응을 다루는 표준 | 저장 모델과 조회의 기반. JPA 자체가 DB는 아님 |
| Hibernate | JPA를 구현하는 라이브러리 | 실제 매핑·SQL 실행을 지원. 잘못된 쿼리나 인덱스 문제를 자동 해결하지 않음 |
| JDBC | Java와 DB가 통신하는 기본 접근 수단 | JPA 아래에서도 쓰이며 초기 테스트는 JdbcTemplate로 DB 연결 확인 |
| MySQL | 로그를 지속 저장하고 조회하는 관계형 DB | 채택 기록은 8.4.13 LTS. 대규모 검색 성능이 검증됐다는 의미는 아님 |
| Flyway | DB 구조 변경을 순서 있는 파일로 적용 | V1 이후 새 변경은 V2 등 새 migration. 적용된 파일을 고치지 않음 |
| Testcontainers | 테스트에서 실제 컨테이너 DB를 실행하는 도구 | 실제 MySQL·마이그레이션·앱의 결합 확인. Docker가 없으면 생략하지 않음 |
| Gradle | 서버 의존성·컴파일·테스트·빌드 도구 | 9.8.2 Wrapper와 Kotlin DSL. 앱 언어가 Kotlin이라는 뜻은 아님 |

JPA·Hibernate·JDBC·Flyway·Testcontainers의 버전은 Boot BOM을 따른다. 조합의 버전을 한 기준에서 관리한다는 뜻이며 각 라이브러리를 임의의 최신 버전으로 바꾸지 않는다. 초기 Maven 구성을 Gradle로 전환했다는 기록은 총괄 공유 근거다. 개별 기술을 최초에 누가 추천했는지는 출처 확인 필요다.

기본 설정은 UTC, open-in-view=false, ddl-auto=validate다. validate는 엔티티와 DB 구조가 맞는지 확인하는 설정이고 자동으로 테이블을 바꿔주는 설정이 아니다. DB 변경 이력은 Flyway가 담당한다. open-in-view=false에서는 HTTP 응답 작성 중에 지연 조회가 계속 일어나도록 의존하지 않고 서비스 단계에서 필요한 데이터를 준비해야 한다.

### 4. 로그 한 건에 필요한 정보

| 필드 | 예시·의미 | 필요한 이유 |
| --- | --- | --- |
| eventId | 7b2a8c30-8d94-4d5f-a6d8-931cf6a6a101 | 같은 사건의 재전송을 식별 |
| occurredAt | 2026-10-27T03:00:00.123Z | 발생 시각을 공통 기준으로 정렬·검색 |
| serviceName | sample-was | 어느 서비스인지 구분 |
| instanceId | was-2 | 같은 서비스의 어느 서버인지 구분 |
| level | ERROR | 중요도·오류 조건으로 탐색 |
| message | Synthetic failure for logscope demo | 사람이 읽는 사건 설명 |
| exception | 합성 예외의 여러 줄 stack trace 또는 null | 오류 발생 경로를 상세에서 확인 |

UUID v4는 사건 식별자로 사용하며 시각 순서 자체를 의미하지 않는다. 우연한 ID 충돌 가능성이 수학적으로 0인 것도 아니므로 DB 유일성 제약과 내용 충돌 처리가 필요하다. 정확한 정렬은 occurredAt DESC 다음 eventId DESC다. 두 사건의 발생 시각이 같아도 순서를 정할 수 있다.

필수값·자료형·문자 수와 요청 byte 제한은 별개다. message는 최대 4,096 코드 포인트, exception은 최대 32,768 코드 포인트이고 단건 JSON 본문은 최대 256 KiB다. 같은 글자 수라도 UTF-8·JSON escaping에 따라 byte 수가 달라질 수 있다. 길이를 넘는 원문은 거절하고 저장된 원문을 조용히 자르지 않는다. 목록 축약은 화면 표현이다.

### 5. 재전송과 중복 안전성

예를 들어 서버는 저장했지만 성공 응답이 네트워크에서 유실될 수 있다. 보내는 WAS가 ‘응답을 못 받았으니 저장도 안 됐다’고 판단하고 새 ID를 만들면 같은 사건이 두 번 저장된다.

그래서 재시도는 같은 eventId와 같은 본문을 유지한다.

| 상황 | 확정 명세 |
| --- | --- |
| 처음 받은 이벤트 저장 | 커밋 후 201, STORED |
| 같은 ID·같은 내용 재전송 | 추가 저장 없이 200, DUPLICATE |
| 같은 ID·다른 내용 | 기존 값 유지, 409 EVENT_ID_CONFLICT |

이것이 이 서비스에서의 중복 안전성이다. HTTP POST라는 메서드만으로 자동 보장되는 성질이 아니다. 동시에 들어온 요청에도 한 건만 남는지는 DB 제약·트랜잭션 처리와 실제 테스트로 확인해야 한다. ‘먼저 조회해서 없으면 저장’만으로는 두 요청이 동시에 없다고 판단할 수 있다.

exception 생략과 null, 시각 표기의 밀리초 정규화는 같은 내용으로 비교한다. 메시지의 공백·줄바꿈·대소문자를 임의로 바꿔 같다고 처리하지 않는다. 로그 전달 전체가 정확히 한 번 실행되거나 무손실이라는 뜻도 아니다.

### 6. UTC와 조회 기간

Z는 UTC를 나타낸다. 서버마다 다른 현지 시각 표기를 그대로 비교하면 시간 해석이 엇갈리기 쉽다. logscope는 UTC 밀리초 저장·응답·화면·입력을 공통 기준으로 선택했다. 소수 초 0~3자리를 받아 응답은 3자리로 통일하고, 다른 오프셋이나 더 긴 정밀도는 명세상 거절한다. 이는 제품의 입력 정책이며 다른 시간 표기가 일반적으로 잘못됐다는 뜻은 아니다.

조회 from은 포함, to는 제외다. 예를 들어 03:00 이상 04:00 미만을 조회한 다음 04:00 이상 05:00 미만을 조회하면 04:00 경계가 두 범위에 동시에 포함되지 않는다.

첫 화면은 최근 15분, API는 from/to 필수이며 최대 24시간이다. 방금 생긴 오류를 먼저 보여주고 의도치 않은 전체 검색을 막는 절충이다. 지난달의 특정 하루도 저장돼 있다면 조회할 수 있다. 24시간은 보존 기간이 아니며 실제 데이터 양·검색 성능의 보장도 아니다.

수집 occurredAt의 과거·미래 제한은 조회 범위와 다른 문제다. AI가 제안한 ‘과거 제한 없음·미래 5분’은 아직 승인되지 않았다. UI나 서버가 확정값처럼 적용하면 안 된다.

### 7. offset 대신 커서를 선택한 과정

offset은 ‘앞에서 50건을 건너뛰고 다음 50건’을 읽는 방식이다. 첫 목록을 본 뒤 앞쪽에 새 로그 3건이 추가되면 위치가 밀려 다음 목록에서 이전 로그 3건을 다시 볼 수 있다. 조회 경계를 고정해도 그 경계 안으로 지연 로그가 들어올 수 있다. 깊은 목록에서 많은 항목을 건너뛰는 비용도 고려해야 한다.

커서는 ‘마지막으로 읽은 시각과 ID보다 오래된 쪽’을 읽는다. logscope는 번호 점프·총 페이지 대신 이전·다음을 사용하므로 이 방식이 목적에 맞았다. offset은 금지 기술이 아니라 작은 정적 목록·번호 이동 요구에는 단순한 대안이다. 이 채팅의 초기 초안은 page/size였고, 이후 AI 추천과 사용자 승인으로 커서를 구체화했다. 사용자가 추천을 질문했을 때 이미 갱신된 공통 문서의 커서 승인을 뒤늦게 확인해 설명을 정정한 이력도 있다.

next는 더 오래된 방향, previous는 더 최신인 가까운 방향이다. 응답 정렬은 항상 내림차순이다. 정렬 인덱스와 실행 계획이 적절해야 하며 커서 사용 자체가 모든 검색을 빠르게 만드는 것은 아니다. 특히 메시지 부분 검색은 별도로 확인해야 한다.

승인된 커서는 버전·방향·경계 시각/ID·조회 조건 식별값·발급/만료를 담고 HMAC-SHA256으로 서명한다. 클라이언트는 값을 해석하지 않고 전달한다. Base64url은 URL에 쓰기 위한 인코딩이며 암호화가 아니다. HMAC은 키를 가진 서버가 발급한 내용인지 검증하기 위한 장치다. 인증·접근 권한을 대신하지 않는다.

최대 길이는 4,096 ASCII 문자, 최초 탐색 기준 수명은 30분이다. 필터·size 변경과 새로고침은 커서를 없애고 첫 목록부터 시작한다. 서명 오류·만료·조건 불일치는 서로 다른 400 code로 안내한다. 탐색 도중 시간 경계는 고정하지만 완전한 스냅샷은 아니며 늦게 도착한 로그는 새로고침으로 확인한다.

안전한 서명 키 외부 주입은 커서 구현 전에 필요하다. 고급 회전·다중 인스턴스 키 운영은 필요 시점에 다룬다. 상세 키 운영안은 아직 제안이다.

### 8. 비동기 대기열과 전송 수치

WAS 요청을 처리하는 사람이 로그 서버의 응답까지 기다리는 대신, 전송할 일을 제한된 상자에 넣고 별도 작업자가 보내는 형태다. logscope 장애가 업무 요청 실패로 이어지지 않게 하는 목적이다. 비동기라는 이름만으로 직렬화 비용·CPU·메모리 영향이 사라지지는 않는다.

| 승인 초기값 | 의미·선택 이유 |
| --- | --- |
| WAS별 단일 작업자·동시 전송 1건 | 작은 MVP에서 전송 순서와 장애 분석 단순화 |
| 진행 중·재시도 포함 100건 또는 본문 합계 8 MiB | 건수와 긴 stack trace의 자원 점유를 함께 제한 |
| 한도 초과 시 새 이벤트 거절 | 이미 받은 이벤트를 유지하고 업무 요청을 공간 대기로 막지 않음 |
| 단건 최대 256 KiB | API 수집 본문 제한과 일치 |
| 연결 1초·시도 전체 3초 | 연결 실패와 느린 시도에 대한 자원 점유 제한 |
| 최초 포함 최대 3회 | 짧은 장애는 다시 시도하되 무한 반복 방지 |
| 대기 0~500ms, 다음 0~1초 | WAS들이 같은 순간 재시도하는 부하를 분산하는 jitter |
| 정상 종료 최대 5초 | 남은 로그를 보낼 기회와 유한한 종료 대기 사이 절충 |

8 MiB는 직렬화 본문 합계이고 JVM 전체 힙의 최대값이 아니다. 단일 작업자가 한 건 재시도 중이면 뒤의 로그도 대기한다. 이 단순함의 대가로 장애 중 포화와 처리 지연을 받아들인다. 초기값은 사용자 승인이지 업계 표준이나 성능 실측 결과가 아니다.

재시도 대상은 네트워크·타임아웃·500/502/503/504/429다. 검증 오류·409를 반복 전송해도 원인이 없어지지 않으므로 전달 포기로 구분한다. 429/503의 유효한 Retry-After는 존중하되 남은 대기가 3초를 넘으면 단축해서 재시도하지 않고 포기한다. 이 3초 정책은 시도 전체 기한과 구분해 읽어야 한다.

### 9. 실패 횟수와 누락 건수는 다르다

로그 한 건이 두 번 실패하고 세 번째 성공하면 실패 시도는 2회지만 전달 포기는 0건이다. 응답 타임아웃 뒤 포기해도 서버가 이미 저장했을 수 있어 실제 DB 미저장 건수라고 단정할 수 없다.

명세의 관측 항목은 generated, enqueued, queueRejected, sendAttempts, failedAttempts, acknowledged, abandoned, queueDepth다. 신규 저장과 중복 성공, 영구 오류와 재시도 소진도 구분한다. 정상 종료의 shutdownPending과 abandoned는 중복 합산하지 않는다. 구체적인 노출 경로·지표 이름·집계 원자성은 해당 전송 기능에서 인프라와 정할 사항이다.

재시작하면 누적 계수가 초기화되고 메모리 대기열도 복구하지 않는다. 비정상 종료 직전의 정확한 손실을 모두 알 수 있다고 쓰면 안 된다. 전송기 자체 진단을 다시 수집해 반복 전송되는 순환도 막아야 한다.

### 11. 실제 수행과 검증 상태

이 채팅에서는 API 초안 작성, 교차 검토, 용어 변경 확인, 사용자 승인된 세부 명세 반영과 요청받은 총괄 공유를 수행했다. 설계가 구현됐다는 뜻은 아니다.

2026-10-27 학습 문서 작성 시 확인한 주 작업 폴더의 src에는 기본 LogscopeApplication, V1 초기 migration, 설정과 초기 Testcontainers 테스트가 있다. LogscopeApplicationTests는 SELECT 1·Flyway V1·검증·재실행을 확인하는 코드이며 로그 수집·중복·목록 기능을 테스트하는 코드는 아니다. 이 문서 작성 중 테스트를 실행하지 않았다.

[초기 설정 기록](../setup-status.md)은 과거 실제 MySQL 테스트·Compose·이미지·readiness·CI·브랜치 보호 결과와 관련 변경의 선행조건 충족을 기록한다. 이 채팅에서 그 실행을 새로 수행하거나 원격 상태를 다시 확인한 결과는 아니다.

사용자가 별도 worktree로 첫 기능 구현·전체 검증·커밋·PR을 요청해 원격 갱신을 시도했지만 .git/FETCH_HEAD 쓰기 권한 제한으로 실패했다. GitHub CLI도 현재 명령 경로에서 찾지 못했다. 캐시된 원격 ref 조회는 최신 원격 확인 성공과 같지 않다. 자동 승인 심사의 거절이 발생한 것은 아니며 권한 확장 요청도 아직 하지 않았다. worktree·브랜치 생성, 도메인 코드 변경·기능 테스트·커밋·PR은 아직 없다.

이어 총괄에서 이 학습 문서만 작성하고 구현·커밋·worktree 생성을 하지 말라는 후속 요청이 도착해 범위를 문서로 한정했다. 첫 구현 요청을 완료했다고 보고하지 않는다. 현재 사용자 대화의 구현 요청과 명세 파일의 과거 ‘별도 요청 전’ 문구도 구분해 읽어야 한다.

### 12. 향후 구현 순서와 결정 시점

1. 공통 문서·규칙의 전체 검증과 PR 병합 상태를 확인한다.
2. 최신 원격 main 기반 별도 작업 공간에서 합성 JSON 한 건 수집·저장·최소 조회를 구현한다. 저장 구조·새 migration·필드 검증·중복 처리·실제 MySQL 테스트가 첫 범위다. 필수 시간 경계는 지키고 모든 검색·페이지를 한 번에 넣지 않는다.
3. 최소 Next 환경·목록·상세로 서버 ID·메시지·trace를 화면에서 확인한다. 이때 중계 크기·기한·오류 등 필요한 호환성을 정한다.
4. 샘플 WAS 한 대의 자동 전송과 승인된 대기열·재시도·진단을 구현·검증한다.
5. 검색·필터·서명 커서·오류 복구를 구현한다. 커서 키 안전 주입 등 필수 결정을 착수 전에 끝낸다.
6. 세 WAS와 장애·포화·중복·종료·통합 검증으로 확대한다.

매 커밋 직전 verify.sh 전체 검증·비밀 검사, PR과 CI verify를 지킨다. Java는 Gradle, 프론트는 npm이며 프론트 도입 시 필요한 검사를 같은 검증 진입점에 추가한다. 제안된 큰 성능 목표를 모두 확정해야 첫 저장 기능을 만들 수 있는 것은 아니다. 보안·필수 검증·분야 호환성은 미루지 않는다.

### 13. 블로그 목차와 표현 예시

추천 목차는 ‘분산된 로그를 찾던 문제 → 중앙 관측 MVP의 범위 → 로그 형식과 중복 안전성 → 시간과 탐색 방식 선택 → 전송 실패를 감수하는 경계 → 결정과 검증의 차이 → 한 건부터 구현할 다음 단계’다.

| 지금 쓸 수 있는 표현 | 아직 쓰면 안 되는 표현 |
| --- | --- |
| 공통 로그 형식과 HTTP API 명세를 정리했다 | 수집 API를 구현하고 운영 검증했다 |
| 중복 전송을 한 건으로 처리하도록 설계했다 | 동시 재전송에서도 중복이 없음을 검증했다 |
| 커서 탐색을 채택하고 이유를 기록했다 | 커서로 모든 검색 지연을 해결했다 |
| 전송 초기값을 승인하고 검증 계획을 남겼다 | 3대 환경에서 초당 10건 성능을 보장한다 |
| 초기 환경의 검증 기록과 도메인 미구현을 구분했다 | 초기 DB 연결 성공으로 로그 기능도 검증됐다 |
| 목록 4 MiB 등은 추가 검토 제안이다 | 모든 추가 수치가 확정·검증됐다 |

성능을 나중에 쓸 때에는 데이터 양·분포·메시지 크기·하드웨어·동시성·측정 구간·실행 revision·실패율을 함께 남긴다. 문서의 제품 버전은 채택 기록이며 현재 지원·보안 적합성 확인을 대체하지 않는다.

첫 기능에 모든 검색·페이지를 넣지 않는 승인된 진행 방식을 적용했다. 필터·커서 미구현 요청과 추가 페이지 필요 상황은 501로 알리며 조용히 조건을 무시하거나 마지막 페이지로 오인시키지 않는다. 이는 후속 커서 구현 때 대체할 임시 단계다.

JDBC의 명시적 INSERT와 DB PK를 사용해 먼저 조회하고 저장하는 경쟁을 피했다. TransactionTemplate 밖에서 중복 예외를 처리하므로 실패한 트랜잭션에서 다시 읽지 않는다. JPA merge에 의한 기존 행 갱신을 피하고 비교할 원문을 보존하는 선택이다. JPA 관련 기반을 제거한 것은 아니다.

DATETIME(3)·UTC LocalDateTime 변환으로 JVM 기본 시간대에 의존하지 않는다. MEDIUMTEXT는 최대 32,768 코드 포인트 stack trace를 UTF-8로 저장할 수 있게 한다. 코드 포인트 제한과 본문 byte 한도는 별도로 검사한다. MySQL의 날짜 표현 범위를 문서화했으며 미래 5분 제안을 임의 적용하지 않았다.

## 주제: 로그 입력 단위 테스트로 오류 원인 분리 / 시간: 2026-10-27 16:02 KST

### 1. 사용자 요청과 목표

사용자는 문자열 A의 검증 오류를 HTTP·DB 통신 오류와 구분하려면 단위 테스트가 필요하다고 설명했다. 기존 통합 테스트를 유지하면서 LogInput 단위 테스트를 추가하고 앞으로 모든 백엔드 기능에 단위 테스트를 함께 작성하도록 요청했다. 이 기록은 해당 테스트 변경의 전체 검증과 작업 커밋 이후 작성했다.

### 2. 추가·변경한 내용

LogInputTests는 Spring 컨텍스트·HTTP 서버·MySQL·Docker 없이 LogInput을 직접 호출한다. JUnit Jupiter의 일반·매개변수 테스트와 AssertJ를 사용한다. 기존 통합 테스트 파일과 운영 코드는 변경하지 않았다. 향후 기능에 단위 테스트를 함께 작성하고 통합 테스트를 대체·생략하지 않는 기준을 루트 작업 규칙에 추가했다.

입력값의 누락·null·공백·잘못된 JSON 자료형, 알 수 없는 필드, UUID v4의 대소문자·버전·variant, 로그 레벨, 서비스·서버 이름 패턴, 메시지·예외 길이를 확인한다. Unicode는 ASCII·한글·이모지의 최대 길이와 한 글자 초과, 짝이 없는 surrogate를 구분한다. 시간은 소수 초 정밀도·윤년·날짜 범위·잘못된 UTC 표현을 확인한다. 반환값뿐 아니라 오류의 HTTP 상태·상위 코드·필드명·필드 오류 코드도 검사한다.

### 3. 선택 이유와 대안

통합 테스트만 실패하면 입력 검증·요청 파싱·응답 변환·DB 중 어느 부분인지 더 살펴봐야 한다. 입력 규칙을 직접 테스트하면 같은 A를 넣어 해당 단계가 예상대로 동작하는지 빠르게 좁힐 수 있다. 예를 들어 level=A는 level 필드의 INVALID_ENUM이어야 하고, 잘못된 조회 종료 시각은 to 필드의 INVALID_UTC_TIMESTAMP여야 한다.

데이터를 담은 실제 JSON 노드를 사용하되 네트워크·DB는 연결하지 않는다. 순수 검증 로직에 불필요한 Spring 초기화나 mock을 도입하지 않았다. 여러 입력에서 같은 규칙을 확인할 때 매개변수 테스트를 사용해 실패한 입력 사례를 구분한다. 단순히 내부 메서드가 호출됐다는 사실보다 반환 데이터와 오류라는 관찰 가능한 동작을 검사한다.

### 4. 동작 확인과 한계

40개의 단위 테스트 사례에서 정상 원문·공백·줄바꿈 보존, exception 생략/null의 동등성, 필드별 검증 오류와 Unicode·시각 경계를 확인했다. 예외 없이 처리되는 것만 확인하는 대신 정상 기본 사례는 기대 LogEvent 전체를 비교한다.

단위 테스트는 HTTP 본문의 UTF-8·JSON 파싱, 실제 byte 제한, SQL·트랜잭션·동시성·DB 원문 저장을 보장하지 않는다. 이를 위해 기존 HTTP·실제 MySQL 통합 테스트 13개를 함께 유지한다. 단위 테스트가 통과해도 실제 장애 입력과 동일한 조건을 다뤘는지 확인해야 하며 앱 로직에 문제가 없다고 단정할 수 없다.

### 5. 배운 개념과 남은 일

단위/통합은 JUnit이라는 도구의 차이가 아니라 검사하는 범위의 차이다. 이번 단위 테스트는 입력 규칙을 격리하고, 통합 테스트는 구성 요소 사이의 연결을 검사한다. 두 종류의 결과를 함께 보면 오류 원인을 더 좁힐 수 있다.

특정 문자열 오류를 재현할 때 그 사례를 테스트 입력으로 추가하고 기대 반환값 또는 필드 오류를 명시한다. 다음과 같이 단위 테스트 클래스만 실행하거나 --tests에 메서드 이름을 붙여 진단할 수 있다. 이 명령은 빠른 진단용이며 커밋 전 전체 verify.sh를 대체하지 않는다.

```sh
./gradlew test --tests com.logscope.log.LogInputTests
./gradlew test --tests 'com.logscope.log.LogInputTests.rejectsUnknownOrNonCanonicalLevels'
```

앞으로 새로운 기능에도 정상·실패·경계에 맞는 단위 테스트를 함께 작성하고, DB·HTTP 연결에 의존하는 성질은 통합 테스트로 확인한다. 아직 구현하지 않은 필터·커서·자동 전송에 대한 테스트까지 이번에 만들지는 않았다.

## 주제: 두 WAS의 파일 로그와 Vector 배치 수집 / 시간: 2026-10-27 23:10 KST

### 1. 사용자 요청과 목표

두 샘플 WAS가 1분마다 랜덤 로그를 만들고 수동 버튼으로도 생성하도록 요청했다. Logback 파일을 Vector가 읽어 묶어 전송하는 방식을 승인했으며 Kafka는 뒤로 미뤘다. 로그 탐색 화면은 기존 프론트의 책임으로 유지하고 이번 화면은 합성 로그 발생 도구다.

### 2. 추가·변경한 내용

sample-was Gradle 모듈 하나를 was-1·was-2로 실행한다. TRACE부터 ERROR까지 생성하고 예외 버튼은 실제 합성 예외의 stack trace를 포함한다. 전용 Logback logger가 중앙 API의 일곱 필드만 JSON Lines로 기록한다. 개행을 escape하므로 예외가 여러 줄이어도 파일에서는 한 행이다. 프레임워크·수집기 자체 진단은 대상 파일에서 제외한다.

Vector는 WAS별 파일 볼륨을 읽기 전용으로 마운트하고 회전 파일도 읽는다. 최대 100건·직렬화 전 64KiB·2초 기준으로 배치 전송하고 HTTP sink acknowledgements와 100건 메모리 버퍼를 사용하고 체크포인트는 별도 볼륨에 보존한다. 서버에는 기존 단건 경로와 별도로 /api/v1/logs/batch를 추가했다. 배열 1~100건·본문 1MiB 제한, 항목별 256KiB·기존 입력 규칙을 적용한다. 잘못된 항목은 index·code로 거절하고 정상·중복 항목을 유지한다.

### 3. 선택 이유와 대안

WAS가 중앙 HTTP 호출·재시도 대기열을 직접 관리하는 대신 파일 생성과 전달을 나눴다. 수집기 교체와 장애 분석이 쉬워지고 여러 이벤트를 한 요청으로 보낼 수 있다. Kafka는 더 큰 버퍼·여러 소비자 등 요구가 생길 때 검토한다. 처음 시도한 0.60.0 디스크 버퍼는 저빈도 이벤트가 버퍼에 남고 sink로 넘어가지 않는 정체를 재현했다. 공식 이슈 #26523에도 같은 증상이 있어 메모리 버퍼로 변경하고 전송 확인을 파일 source까지 연결했다. 미출시 패치를 직접 배포하거나 가짜 주기 로그로 문제를 숨기지 않았다. 공식 수정 버전은 후속 검증 대상이다.

Logback의 일반 진단 JSON에는 중앙 명세 밖의 필드가 포함될 수 있어 명시적인 encoder로 일곱 필드를 맞췄다. UUID는 파일 기록 전 한 번 발급해 전송 재시도에도 같은 값을 유지한다. 화면 응답 LOG_GENERATED는 로깅 호출 완료만 뜻하며 중앙 저장이나 fsync를 보장하지 않는다.

### 4. 동작 확인과 한계

JUnit 단위 테스트로 레벨·잘못된 입력·예외·UUID/MDC·JSON 행·수동/자동 정지·배치 집계·과대 항목·DB 장애 전파를 분리 확인했다. 실제 MySQL/HTTP 테스트로 혼합 배치의 신규·중복·거절·충돌과 100건·본문 상한을 확인했다. 기존 단건·조회 통합 테스트도 유지했다.

실제 브라우저에서 두 WAS의 예외 버튼을 누르고 다섯 레벨·1KB 테스트 회전·기본 60초 자동 생성과 추가 로그 없이 고립된 이벤트의 전달이 실제 Vector JSON 배열과 MySQL 상세까지 이어짐을 확인했다. 수집기 재시작 뒤 새 이벤트 수집과 한 번의 503 후 재시도를 확인했다. 초기 시간 기반 장애 주입은 유한 재시도가 소진될 수 있어 실패했고, 단일 503을 확실히 주입하는 방식으로 바꿨다. 최종 검증은 장기 장애 복구 보장이 아니다.

Vector는 HTTP 200의 항목별 거절을 재처리하지 않는다. 서버 WARN은 거절 건수만 남긴다. 메모리 버퍼는 강제 종료 시 사라질 수 있으며 원본 파일·마지막 체크포인트가 남아 있어야 다시 읽을 수 있다. DB 장애 전 앞선 항목이 저장될 수 있으므로 전체 배치 재전달은 중복 판정으로 안전하게 처리한다. 유한 재시도 소진·회전 파일 보존 삭제·디스크 장애에서는 누락될 수 있다.

검증 이미지도 worktree 사이에서 공유되는 Docker 이름이다. 고정 verify 태그가 다른 실행에 의해 덮어써지면 새 API가 없는 이미지로 405를 받을 수 있어, 전체 검증이 자기 이미지 태그를 생성·전달·정리하도록 바꿨다. 네트워크·볼륨뿐 아니라 이미지 참조도 격리해야 같은 코드를 확인할 수 있다.

### 5. 배운 개념과 남은 일

Logback은 애플리케이션의 로그를 파일에 남기고 Vector는 그 파일의 읽은 위치를 기억하며 중앙으로 전달한다. 배치는 여러 로그를 한 HTTP 요청에 담는 방식이며, 체크포인트는 파일을 어디까지 읽었는지 기록하는 위치다. 중앙 저장 확인은 이 위치와 다르다. 같은 eventId로 다시 보내도 한 건만 남기는 중복 판정이 재시도의 안전장치다.

범용 로그·장기 장애·격리와 재처리·운영 인증·Kafka·세 번째 WAS는 후속 설계다. 기존 최소 목록은 size보다 많은 결과에 아직 501을 반환하므로 자동 생성으로 데이터가 쌓이면 조회 기간을 줄여 확인하고 커서 구현에서 해결해야 한다. 이번 변경은 검색·페이지 기능을 구현하지 않는다.

## 주제: 단독 로그 전달 지연 측정과 단계별 진단 / 시간: 2026-10-27 23:31 KST

### 1. 사용자 요청과 목표

샘플 WAS의 단위·통합·전체 검증을 요청했다. 서로 다른 실행 환경에서 단독 이벤트가 10초 안에 확인되지 않는 사례를 구분하기 위해 검증 자체의 관찰과 진단을 보강했다. 제품의 전송 간격·배치·재시도 정책을 바꾸는 작업은 아니다.

### 2. 추가·변경한 내용

단독 이벤트 여섯 건을 검사하는 동안 자동 생성을 잠시 멈춘다. 다른 이벤트가 정체를 풀어 통과시키지 못하게 한 다음, 각 이벤트의 저장을 최대 30초 관찰하고 실제 소요 밀리초를 출력한다. 검사가 끝나면 자동 생성을 다시 켜 기본 60초 주기도 확인한다.

실패하면 WAS 파일의 행 수·JSON 오류 수·대기 이벤트의 파일 존재 여부, Vector HTTP 상태·재시도 횟수, 중앙 API의 stored·duplicates·거절 코드만 남긴다. 원문·eventId·주소·호스트명·진단 헤더를 출력하지 않는다. 임시 자원 정리는 성공과 실패 모두 유지한다.

### 3. 선택 이유와 대안

배치 대기 2초는 파일 감지·실행 대기·HTTP·DB를 모두 포함하는 시간 목표가 아니다. 공유 환경에서 고정된 10초 초과만 보고 어느 단계가 느린지 알 수 없어, 관찰 상한과 실제 시간을 구분했다. 30초는 검증 제한이며 제품 SLA나 성능 측정 결론이 아니다. 시간이 더 지나도 저장되지 않으면 계속 실패하며 추가 로그로 강제로 깨우지 않는다.

### 4. 동작 확인과 한계

자동 생성이 멈춘 상태에서 여섯 단독 이벤트가 추가 로그 없이 실제 MySQL에 저장됐다. 이번 로컬 실행의 각 전달은 약 2.6~3.6초였다. 기존 단위·HTTP/MySQL·브라우저·회전 파일·수집기 재시작·503 재시도 검증도 유지했다. 이 수치는 다른 환경의 최대 지연을 보장하거나 이전 지연의 내부 원인을 확정하지 않는다.

### 5. 배운 개념과 남은 일

진단은 단순히 실패라고 출력하는 것보다 파일 생성 실패·수집기 전달 정체·중앙 항목 거절을 구분할 수 있어야 한다. 반대로 진단을 위해 원문이나 접속 정보를 무조건 출력하면 안 된다. 검증의 시간 상한과 제품의 성능 목표는 따로 설계한다. 서로 다른 환경에서 나타나는 지연은 단계별 근거를 더 모아 판단해야 한다.

| 단독 이벤트의 10초 관찰 한도 초과 | ARM 로컬에서는 약 2.6~3.6초에 저장됐지만 다른 실행 환경에서는 10초 안에 확인되지 않았다. ARM 호스트에서 x86_64 Vector 바이너리를 실행한 비교에서는 6건이 약 3.1·3.6·12.3·4.1·12.3·3.6초에 추가 자동 로그 없이 저장됐다 | 관찰 상한을 30초로 두고 실제 밀리초를 기록했다. 검사 중 자동 생성을 멈춰 다른 로그가 정체를 풀지 못하게 했다. 실패 시 파일 기록·HTTP·배치 집계를 구분하는 진단을 추가했다 | 10초 초과만으로 영구 정체라고 단정할 수 없다는 근거다. x86_64 비교에는 에뮬레이션이 포함됐다. 실제 원격 환경의 내부 지연 원인을 확정하거나 제품 지연을 개선한 것으로 보지 않는다 |
| 시간 기반 장애 주입의 불확실성 | 수신기를 일정 시간 막아 두면 제한된 재시도가 모두 소진될 수 있었다. 이 경우 복구 후 저장되지 않는 것은 재시도 정책상 가능하다 | 정확히 한 번의 503을 반환한 뒤 다음 시도를 받을 수 있게 해, 일시 실패 후 동일 이벤트의 재전송을 검사했다 | 재시도 복구 검증과 재시도 소진 상황을 구분한 것이다. 유한 재시도를 장기 장애의 무손실 전달로 바꾼 것은 아니다 |

### 3. 선택 이유와 대안

실패를 없애기 위해 무조건 대기 시간만 늘리거나 다음 로그를 계속 만들어 넣으면, 실제 정체를 가릴 수 있다. 디스크 버퍼 문제에는 사용 경로를 바꾸는 조치를 했고, 이미지 문제에는 이미지 참조를 격리했다. 전달 시간 문제에는 실제 시간을 측정하고 실패 단계를 구분하도록 검증을 보강했다. 서로 다른 문제에 같은 해결책을 적용하지 않았다.

메모리 버퍼는 디스크 버퍼의 내구성을 그대로 대체하지 않는다. 원본 파일과 전달 확인에 연결된 체크포인트를 남기되, 운영 무손실 보장은 별도 설계로 남겼다. 30초 역시 테스트의 관찰 한도이며 제품 SLA가 아니다. Vector의 배치 대기 2초는 파일 감지·스케줄링·HTTP·DB를 포함한 전체 전달 시간과 다르다.

### 4. 동작 확인과 한계

최종 구성에서 실제 브라우저의 두 WAS 수동·예외 버튼, 다섯 레벨, 파일 회전, 단독 이벤트, 기본 60초 자동 생성, Vector JSON 배열, MySQL 상세 저장, 수집기 재시작과 한 번의 503 후 재시도를 확인했다. 기존 단위·실제 HTTP/MySQL 검증을 유지했고 x86_64 Vector 비교 실행도 전체 파이프라인을 통과했다.

오래 걸린 기술적 이유는 한 번에 하나의 문제가 아니라 위 문제들이 서로 다른 단계에서 발견돼, 근거를 수집하고 조치 후 전체 연결을 다시 확인해야 했기 때문이다. 기본 60초 자동 생성은 짧은 간격으로 바꿔 대신 검사하지 않고 실제 간격으로 관찰했다. 파일·수집기·HTTP·DB·브라우저·이미지까지 포함하는 검증은 입력 단위 테스트보다 준비와 실행 비용이 크다. 단계별 소요 시간을 모두 계측하지 않았으므로 각 문제에 몇 분이 들었는지 추정해서 적지는 않는다.

### 5. 배운 개념과 남은 일

로그 생성 응답은 중앙 저장 완료와 다르고, 파일을 읽은 사실도 HTTP 전송 완료와 다르다. 같은 이벤트를 어느 단계까지 확인했는지 비교해야 원인을 좁힐 수 있다. 진단에는 원문·eventId·주소·호스트명 대신 필요한 존재 여부·건수·상태 코드만 출력하도록 했다.

원인이 확인된 이미지 혼용, 디스크 버퍼에서 관찰한 정체, 내부 원인이 아직 확정되지 않은 환경별 지연을 구분한다. 공식 수정 버전의 디스크 버퍼 재검증, 환경별 지연의 세부 측정, 강제 종료·장기 장애·파일 보존 삭제 시 복구는 후속 과제다.

## 주제: SSE 실시간 로그와 저장 순서 기반 복구 / 시간: 2026-10-28 15:01 KST

### 1. 사용자 요청과 목표

샘플 WAS에서 로그가 계속 발생해도 화면에서는 새로고침이 필요했다. 사용자는 주기 조회보다 연결을 유지하며 새 로그를 전달받는 SSE를 선택하고, 최초 조회와 연결 사이 누락·재연결·중복 제거·일시정지 후 복구와 단위/통합 테스트를 요청했다. 이번 백엔드 작업은 이를 위한 snapshot API·SSE 전송·영속 replay 기준이다. 화면에서 연결하고 멈추는 UI는 프론트의 별도 작업이며 현재 프론트 사용자 지시는 검토 단계다.

### 2. 추가·변경한 내용

`GET /api/v1/logs/live`는 최근24시간 최신50건과 cursor를 같은 DB snapshot에서 읽고, 더 많은 기록은 truncated로 알린다. 기존 정적 목록의 50건 초과501 정책은 그대로다. `GET /api/v1/logs/stream?after=...`은 cursor 이후 저장된 summary를 SSE log 이벤트로 전송한다. 재연결의 Last-Event-ID가 있으면 우선하며 입력 형식·다른 DB epoch·미래 순서를 검사한다. ready는 연결 시작점 안내일 뿐 처리 cursor를 앞당기는 이벤트가 아니다.

예를 들어 최초 조회 기준이40일 때 로그41이 저장되고 나서 연결돼도41부터 replay한다. 로그의 발생시각이 과거여도 저장 순서는41이므로 건너뛰지 않는다. 연결을 닫아 일시정지하고42·43이 저장됐다면, 마지막 정상 처리41로 다시 연결할 때42·43을 받는다. 끊어지기 직전에 이미 받은 로그가 다시 올 수 있어 화면에서 eventId 중복 제거가 필요하다. 서버의 중복 수집 판정도 유지해 같은 eventId·같은 내용은 새 순서나 새 이벤트를 만들지 않는다.

V3 migration은 기존 로그에 고유 stream_sequence를 부여하고 DB epoch·마지막 순서를 지속 저장한다. INSERT마다 한 상태 행을 FOR UPDATE로 잠그고 로그와 마지막 순서를 같은 트랜잭션에서 commit한다. commit 후 메모리 신호로 연결을 깨우고, DB가 재전송 원본을 맡는다. 신호 버전을 먼저 읽고 조회 후 변경이 없을 때 대기해 조회/대기 사이 신호도 놓치지 않는다.

한 번에50건을 읽고 연결당128건 또는 약55~60초 후 종료해 이어받는다. 서버 동시 연결은32개다. 응답 초기화 전 SseEmitter의 내부 버퍼도128건으로 제한하고, HTTP 응답 완료와 작업자 종료가 모두 확인돼야 슬롯을 반환한다. heartbeat는 약15초, 재연결 안내는3초이며 DB 장애는 연결 전503 또는 연결 뒤 stream-error 후 종료로 구분한다.

### 3. 선택 이유와 대안

폴링도 실제 API 연동이다. 브라우저가 몇 초마다 새 로그를 묻는 방식이라 구현이 단순하지만 데이터가 없어도 요청하고 다음 조회까지 대기한다. 사용자가 원한 것은 서버가 새 로그를 알리는 흐름이므로 단방향 HTTP 스트림인 SSE를 선택했다. 양방향 메시지가 필요한 채팅/제어 기능이 아니어서 WebSocket은 도입하지 않았다. Kafka는 현재 두 샘플 WAS의 화면 갱신에 필수 구성요소가 아니므로 계속 보류한다.

SSE 자동 재연결만으로 무손실·중복 방지가 완성되지는 않는다. 발생시각은 늦은 전송 때문에 순서 기준으로 부적합하고, AUTO_INCREMENT도 번호 할당과 commit 순서가 다를 수 있다. 작은 번호가 늦게 commit되면 큰 번호를 이미 받은 cursor 뒤로 빠진다. 현재 규모에서는 상태 행 잠금으로 commit 순서를 맞추는 단순한 방법을 선택했다. 대신 수집 쓰기가 직렬화되는 비용이 있어 고부하 성능을 보장하지 않는다.

메모리 이벤트 목록만 보관하면 재시작 때 복구 자료가 사라진다. 저장 로그와 cursor를 DB에 유지하면 연결은 언제든 다시 만들 수 있다. 전송 의미는 at-least-once이며 마지막 정상 처리 cursor와 eventId로 클라이언트가 중복을 제거한다. 프론트는 오류 코드·프레임 검증과 처리 cursor를 직접 관리하는 fetch 기반 SSE 파서를 검토했다. 이는 반복 요청 폴링이 아니며 EventSource가 앱 검증 전에 Last-Event-ID를 갱신할 수 있는 점도 고려한다.

### 4. 동작 확인과 한계

서버와 샘플 WAS의77개 테스트 중 새16개는 cursor 형식·overflow·다른 epoch·미래 cursor, header 우선순위·잘못된 query, 신호 경쟁,32개 연결 상한과 슬롯 반환, DB 장애, 초기 버퍼 한도, 실제 HTTP SSE의 snapshot/연결 간격·신규 push·재연결·일시정지 후 replay·중복,128건 이후 이어받기,50건 snapshot 잘림, 동시 저장 순서, 대기 중 저장과 snapshot 경쟁, 범위 밖 로그 replay, 기존 로그 V2→V3 migration과 재기동 시 migration 상태 보존을 확인했다. 기존 실제 MySQL·HTTP 테스트를 단위 테스트로 대체하지 않았다.

실제 MySQL·Spring Boot·Next.js 목록/상세와 브라우저 기존10개 시나리오, 두 WAS·Logback 회전·Vector 배치/체크포인트/재전송도 유지했다. 현재 프론트에는 SSE UI를 추가하지 않았으므로 이 결과를 실시간 화면의 검증 완료라고 하지 않는다. 재기동 테스트는 DB epoch/순서와 migration의 지속성을 확인하며 다중 앱 운영이나 전체 장애복구 시험은 아니다.

최신50건 snapshot은 전체 이력 조회가 아니다. stream은 모든 신규 저장 로그를 전달하지만 화면의 최근24시간 필터·메모리50건·초점·스크롤·일시정지 버튼 검증은 프론트에 남아 있다. 로그 삭제·DB 복원·epoch 교체 뒤 무손실 복구, 인증·운영 프록시, 고부하/다중 앱 즉시 알림을 보장하지 않는다. Vector 배치 대기2초는 화면 전송을 SSE로 바꿔도 남는다.

### 5. 배운 개념과 남은 일

snapshot은 여러 값을 같은 시점의 DB 모습으로 읽는 것이다. cursor는 마지막 정상 처리 위치를 가리키는 책갈피이며, 이 기능의 책갈피는 화면 정렬 시각과 다르다. epoch는 같은 번호라도 다른 DB의 기록으로 오인하지 않게 하는 구분자다. heartbeat는 로그가 없을 때도 연결 생존·끊김을 확인하는 빈 신호다.

처음 테스트에서는 기존 UTC 밀리초 규칙을 무시하고 나노초 시각을 만들어 입력이400으로 거절됐다. 테스트 합성 시각을 밀리초로 맞췄다. V3 추가 후 초기 검증의 예상 migration 버전2도3으로 갱신했다. 새 동작 때문에 기존 규칙을 완화하지 않고 테스트 입력/기대값을 실제 변경에 맞추는 과정이다.

프론트에는 SSR snapshot 인계·same-origin 중계·연결/재연결/복구불가 상태·정상 처리 cursor·중복 제거·일시정지/재개와 상세/초점/스크롤 보존을 요청했다. 구현은 사용자가 해당 채팅에서 직접 지시한다. 그다음 실제 브라우저 SSE 경로를 함께 검증해야 한다. 추후 쓰기 부하가 커지면 순서 행 잠금 비용과 영속 이벤트 분배 방식을 측정하고 재설계한다.

## 주제: SSE 최초 조회의 DB 연결 대기와 시간 경계 보정 / 시간: 2026-10-28 15:15 KST

### 1. 사용자 요청과 목표

사용자는 기존 SSE 변경을 다시 검토하고 문제가 없으면 반영하도록 요청했다. [앞선 SSE 기록](#backend-sse-replay-20261028)의 저장 순서·동일 DB snapshot 기준을 재검토하면서, DB snapshot 외부에서 먼저 계산한 시간 경계의 경쟁을 발견했다. 같은 snapshot에서 읽는 것과 그 snapshot에 맞는 시간 범위를 정하는 것은 별개다.

### 2. 추가·변경한 내용

기존에는 HTTP 요청 처리 시작 때 종료 시각을 정한 뒤 DB 연결을 얻었다. 예를 들어 종료 시각이10:00:00.000이고 연결 대기 중10:00:00.050 로그가 저장되면, 나중에 읽은 cursor는 이 로그까지 포함하지만 목록은 종료 시각 밖이라 제외할 수 있었다. stream은 cursor 뒤부터 읽으므로 이 로그가 양쪽에서 빠진다.

종료 시각 계산을 DB의 첫 consistent read로 cursor를 읽은 뒤로 옮겼다. 종료 제외 규칙과 UTC 밀리초를 함께 지키기 위해 현재 밀리초의 다음 경계를 종료 시각으로 사용한다. 현재 시각이00.999123이면 종료는01.000이고, 정확히00.999여도 동일하다. 최근24시간 길이는 그대로다. 응답 필드와 기존 정적 조회·수집 API는 바꾸지 않았다.

### 3. 선택 이유와 대안

연결 대기가 짧다는 가정이나 임의로 몇 초를 더하는 여유값은 경쟁을 해결하지 못한다. 요청 시작 시각보다 실제 DB view를 기준으로 시간을 정하면 연결 대기 동안 commit된 정상 시각 로그도 최초 목록에 들어간다. 다음 밀리초 경계는 같은 밀리초 로그를 종료 제외 조건 때문에 건너뛰지 않게 한다. 실제 미래 시각 로그를 모두 포함한다는 뜻은 아니며, 범위 밖·미래 로그 처리와 클라이언트 시계차는 기존 명세대로 구분한다.

### 4. 동작 확인과 한계

실제 MySQL 연결 풀의 모든 연결을 점유한 뒤 HTTP snapshot을 시작해 연결 대기를 확인했다. 점유한 연결로 새 합성 로그와 sequence를 commit한 뒤 연결을 반환했다. 수정 전에는 예상1건 대신0건으로 실패했고, 수정 후에는 로그와 해당 cursor를 함께 받았다. 별도 단위 테스트로 같은 밀리초와 초 경계,24시간 길이도 확인했다. 기존 테스트를 유지해 서버·샘플 WAS79개와 기존 화면·DB·파일 수집 경로가 동작함을 확인했다.

이 검증은 DB 연결 대기로 생기는 경계를 다룬다. 생산자/서버 시계차, 미래 로그의 나중 자동 표시, 고부하 SLA나 프론트 SSE 화면 완료를 보장하지 않는다. 이전 기록의 snapshot 경쟁 테스트는 상태 행 잠금과 commit 대기를 확인한 범위였고 이번 연결 풀 대기 조건을 포함하지 않았다.

### 5. 배운 개념과 남은 일

DB 연결을 얻기 전에 기다릴 수 있으므로 HTTP 요청 시작과 DB를 읽는 시점은 같지 않다. 같은 트랜잭션으로 값을 읽어도 외부에서 미리 만든 시간 조건이 오래됐으면 누락이 생긴다. 시작 포함·끝 제외 같은 경계 규칙은 데이터의 밀리초 정밀도와 함께 검증해야 한다. 프론트에서는 서버가 반환한 from/to/cursor를 함께 인계하고 별도 시각을 섞지 않는 것이 다음 연결의 출발점이다.

## 주제: Elasticsearch 검색과 MySQL outbox 동기화 / 시간: 2026-10-28 16:49 KST

### 1. 사용자 요청과 목표

사용자는 ERROR/INFO 같은 레벨 구분과 코드에 작성한 ‘결제 오류’ 메시지 검색을 원했다. MySQL FULLTEXT와 Elasticsearch를 성능·검색 품질·운영·학습 측면에서 비교한 뒤, Redis를 제외하고 ES 기반 레벨·서버·기간·메시지 검색과 MySQL 원본 유지/색인 동기화를 구현하도록 요청했다. ES를 써야 검색할 수 있어서가 아니라 검색엔진의 분석·색인 원리와 장애 처리를 직접 배우려는 목표에 맞춘 선택이다.

이번 구현은 백엔드 검색 API와 영속 동기화다. 기존 상세·정적 목록·SSE는 유지하며 프론트 검색 화면과 과거 페이지 커서는 별도 작업이다. 현재 검색 결과가 최신50 기본·100 최대이고 더 있으면 잘림을 알린다는 범위를 명확히 했다.

### 2. 추가·변경한 내용

`GET /api/v1/logs/search`는 from/to(UTC·최대24시간·시작 포함/끝 제외), 선택 level/instanceId/keyword와 size를 받는다. 레벨과 서버는 정확히 일치시키고, message는 Nori 분석 후 입력 토큰을 모두 포함하는 AND match로 찾는다. 영어는 lowercase 처리한다. 관련도 점수 대신 발생시각/eventId 내림차순으로 정렬하고, size보다 한 건 더 읽어 truncated를 판단한다. exception 원문은 검색 색인에 복제하지 않고 MySQL 상세에서 읽는다.

Elasticsearch9.5.5 공식 이미지에 같은 버전 Nori를 설치했다. ID/레벨/서버/서비스는 keyword, 메시지는 text, 발생시각은 date, 예외 여부는 boolean이다. dynamic strict로 예상 필드만 받는다. Nori의 mixed 복합어 분해와 lowercase를 조합하고 사용자 검색어는 match의 값으로만 전달해 raw Query DSL/SQL 문법을 실행하지 않는다.

V4 migration은 기존 로그를 색인 outbox에 채운다. 새 로그는 원본·SSE 순서·outbox를 같은 MySQL 트랜잭션에 저장한다. 자동 작업자는 최대50건씩 읽어 ES bulk로 보내고 항목별 성공과 refresh 반영, 색인 UUID를 확인한 뒤 성공 작업만 제거한다. 같은 eventId를 ES document ID로 사용하므로 재전송 시 문서를 중복 생성하지 않는다. 실패 작업은1초부터 최대60초 간격으로 재시도하며 영구 오류도 조용히 버리지 않는다.

색인 형식 버전과 MySQL source epoch를 매핑 metadata에 기록하고 다른 원본의 색인은 덮어쓰지 않는다. 색인 UUID가 바뀌면 원본 전체를 다시 대기열에 넣는다. 검색 응답은 전역 pendingCount/retryingCount/indexingPending으로 미반영 작업을 알린다. ES 장애·잘못된 응답·shard 실패는503이며 빈 결과나 LIKE fallback으로 숨기지 않는다. 동시 검색16개, HTTP 본문/기한과 bulk/응답 byte 상한도 적용했다.

### 3. 선택 이유와 대안

MySQL FULLTEXT도 역색인을 사용하며 별도 검색 서버 없이 구현할 수 있다. ES는 한국어 분석기·필드별 검색 규칙과 검색 부하 분리, 검색엔진 학습을 위해 선택했다. 어떤 데이터에서도 ES가 더 빠르다는 측정 결과나 현재 로그가 적다는 가정은 아니다. Redis 캐시가 필요한 반복 조회 병목은 확인되지 않았고 최신 검색 결과의 무효화 비용도 생겨 제외했다. Kafka는 이번 색인 동기화에 도입하지 않았다.

역색인은 ‘단어→그 단어가 있는 문서 ID’의 찾아보기다. 개념적으로 결제가 있는 문서와 오류가 있는 문서의 교집합을 구하고 서버/레벨/기간 조건을 적용한다. Nori는 문장을 토큰으로 나누고 ES는 이 토큰을 찾는다. ‘결제 처리 중 오류가 발생했습니다’가 ‘결제 오류’ 검색에 포함될 수 있지만, 단순 리터럴 문자열 포함이나 ‘실패=오류’의 의미 추론을 자동 보장하는 기능은 아니다. 실제 `_analyze`에서 결제·오류·payment 토큰을 확인했다.

MySQL에 저장한 뒤 ES에도 직접 저장하면 중간 실패로 한쪽만 남을 수 있다. outbox는 원본과 할 일을 함께 commit해 이 문제를 다룬다. ES 성공 뒤 DB commit이 실패해도 다음 재전송의 같은 `_id`가 문서 중복을 막는다. 전송 의미는 at-least-once다. 작업자 간에는 별도 검색 상태 행을 잠그며 원본의 저장 순서 행을 ES 응답 대기 동안 잡지 않는다.

ES의 refresh는 색인 내용을 검색에서 볼 수 있게 하는 과정이다. MySQL commit과 같은 원자적 시점이 아니다. bulk HTTP200도 전체 성공을 뜻하지 않아 항목별 상태를 확인하고 `refresh=wait_for` 이후에 작업을 제거한다. SSE는 원본 commit에서 전달되므로 화면에 보인 로그가 검색에는 나중에 나타날 수 있다. 대기열0은 관측 이후 새 로그가 영원히 없다는 뜻이 아니며 검색 결과와 원본의 완전한 snapshot을 주장하지 않는다.

### 4. 동작 확인과 한계

기존 테스트를 유지한 서버·샘플 WAS99개 중 새20개는 검색 입력/UTC/Unicode/크기·AND 쿼리,16개 동시 검색과 실패 후 슬롯 반환, bulk 항목별 결과·잘못된/과대 응답·본문 정체 기한·shard 실패, 실제 Nori/MySQL 검색·중복·부분 거절·ES 중단·재전송·색인 유실·다른 원본 소유·두 작업자 동시 소비·outbox 원자성을 검증했다. 기존 데이터가 V4 대기열에 들어가는 migration도 확인했다.

실제 ES의 ingest fail processor로 특정 합성 항목만 거절시켜 정상 항목은 검색되고 거절 작업만 대기하는 것을 확인했다. ES 컨테이너를 일시정지한 동안 원본 저장은201, 검색은503이고 대기 작업이 남았다. 복구 후 새 작업자에서도 처리됐다. 색인을 삭제한 격리 실험에서는 MySQL에서 같은 검색 결과를 재구성했다. 다른 source epoch의 색인은 변경하지 않고503을 반환했다.

별도 이미지 통합 검사 scripts/verify-search.mjs는 수동 호출이 아닌 실제 자동 작업자의 검색·장애 복구·재구성을 검증한다. 기존 프론트 브라우저10개·실제 MySQL SSR/상세·두 WAS의60초 자동/수동·Logback 회전·Vector 배치/체크포인트/재시도도 유지했다. 프론트 검색 화면의 검증 완료를 뜻하지 않는다.

현재 단일 shard·replica0·보안 비활성·호스트 포트 미공개는 합성 데이터 개발용이다. 처리량/검색 지연 SLA, 운영 인증/TLS·디스크 용량·보존·무중단 재색인, 같은 UUID를 유지한 개별 ES 문서의 외부 수정/삭제 자동 감지와 원본 직접 SQL 변경은 보장하지 않는다. 영속 대기열도 장기 장애에서는 디스크를 사용하므로 운영 한도가 필요하다. 최신 결과의 truncated와 색인 대기 상태는 과거 페이지 탐색이나 전체 건수와 다르다.

### 5. 배운 개념과 남은 일

keyword 필드는 정확한 값 필터·정렬에, text 필드는 분석 기반 검색에 사용한다. 원문 `_source`와 분석 토큰은 다르므로 검색은 lowercase로 하더라도 원문 메시지를 바꿀 필요가 없다. bulk는 action과 document를 번갈아 쓰는 NDJSON이며 HTTP 상태와 항목 상태를 따로 읽어야 한다. 검색 결과와 색인 대기 상태를 구분하는 것도 오류를 숨기지 않는 API 설계다.

원자성 실패를 재현하려고 처음 만든 테스트 trigger는 MySQL의 SUPER 권한 제한에 걸렸다. 권한/서버 보안을 완화하지 않고, 격리 테스트의 임시 CHECK 제약으로 outbox만 거절하도록 바꿨다. 원본과 순서까지 롤백되는 것을 확인한 뒤 제약을 제거했다. 또 Mockito에서 예외 stub을 일반 when으로 다시 설정하면 기존 예외가 설정 도중 실행되므로 doReturn으로 장애 해제 상황을 만들었다. 테스트 설정 문제와 실제 저장/네트워크 문제를 분리한 사례다.

다음은 프론트의 검색 조건/잘림/색인 지연·장애 안내 연결, 과거 페이지 커서, 실제 데이터 패턴에 맞는 분석/실행 비용 측정이다. 검색 조건과 실시간 SSE의 관계는 별도 화면 작업에서 맞춰야 한다. 신규 기능을 이유로 기존 API 계약을 몰래 바꾸거나 ES 검색 지연을 원본 유실로 설명하지 않는다.
