# 프론트 화면·API 연동 요구사항

2026-10-27 사용자 승인 조정안 반영. [MVP 분야 간 합의](../decisions/mvp-spec-alignment.md)를 공통 기준으로 사용한다. 명시된 세부 미결정은 구현 전에 확정하며, 이 문서는 기능 구현 승인이 아니다.

## 목표와 범위

오류 발견 → 발생 서버 확인 → 상세 메시지와 stack trace 확인 흐름을 지원한다. 먼저 WAS 한 대의 실제 로그 한 건을 화면에서 확인하고, 이후 was-1·was-2·was-3을 통합 조회한다. 최신순 목록, 시간·서버·레벨·메시지 키워드 필터, 페이지 탐색, 상세 조회와 수동 새로고침이 MVP 범위다. 차트·알림·자동 갱신·실시간 스트림은 후속 범위다.

## 표시 데이터

| 필드 | 목록 | 상세 및 연동 요구 |
| --- | --- | --- |
| occurredAt | UTC 발생 시각 | UTC 전체 시각과 서버가 제공한 정밀도 확인 |
| serviceName | 기본 열에서 제외 | 상세에 전체 값 표시 |
| instanceId | 발생 서버 ID | 전체 값 표시; was-1 등 서버 식별을 항상 유지 |
| level | 텍스트 레벨 | 색상과 별개로 실제 레벨 문자열 표시 |
| message | 읽기 가능한 요약 | 원문 전체와 줄바꿈 표시 |
| exception | hasException으로 포함 여부 표시 | stack trace 전체; 없는 경우 ‘예외 정보 없음’ |
| eventId | 화면 행 식별에 사용 | 진단을 위해 상세에 표시; 상세 조회 식별자로 사용 |

목록은 hasException을 제공하고 exception 원문은 상세에서만 받는다. message는 목록·상세 모두 서버가 자르지 않으며 화면에서만 요약한다. message는 최대 4,096 Unicode 코드 포인트, exception은 최대 32,768 코드 포인트다. 상세 exception=null은 예외 없음이며 빈 문자열은 유효한 수집 값이 아니다. 상세의 필수 필드 누락은 정상적인 예외 없음으로 처리하지 않는다. 로그 문자열은 HTML로 실행하지 않고 텍스트로 렌더링한다.

## 조회 조건과 API 요구

| 항목 | 최신 승인 기준 | 프론트 적용 내용 |
| --- | --- | --- |
| 시간 | from/to 필수, 시작 포함·종료 제외, from < to, 최대 24시간 | 기본 최근 15분; UTC 입력 소수 초 0~3자리, 응답 3자리. 정확히 24시간 허용 |
| 서버 | 전체 또는 단일 instanceId | was-1~3 설정값 사용; 전체이면 파라미터 생략 |
| 레벨 | 전체 또는 TRACE·DEBUG·INFO·WARN·ERROR | 전체이면 파라미터 생략; 알 수 없는 응답 값은 오류 없이 텍스트로 표시하는 방안 제안 |
| 키워드 | message의 대소문자 구분 리터럴 부분 검색 | 앞뒤 공백 제거, 1~200 코드 포인트. %, _도 문자이며 exception은 검색하지 않음 |
| 정렬 | occurredAt DESC, eventId DESC | 사용자 정렬 변경 없음 |
| 페이지 | 기본 50건, size 1~100, 양방향 커서 | nextCursor·previousCursor null이면 해당 버튼 비활성. 커서 내부 해석·조립 금지 |
| 상세 | GET /api/v1/logs/{eventId} | 404 LOG_NOT_FOUND와 통신 실패 구분 |

총 건수·총 페이지·번호 이동은 제공하지 않는다. 페이지 탐색 동안 절대 시간과 적용 조건을 고정하고 커서를 그대로 전달한다. 필터·size 변경이나 새로고침은 커서를 제거한다. 완전한 스냅샷을 보장하지 않으며 늦게 도착한 로그는 새로고침으로 확인한다. 오류는 API의 code 및 errors[].field/code로 분류하고 detail 문구에 의존하지 않는다. 정확한 화면 안내와 복구 동작은 아래 검토 제안으로 남긴다.

## 상태 전환

입력 중인 조건과 마지막으로 적용한 조건을 구분한다. 요청마다 적용 조건·페이지·선택 로그를 식별하고, 이전 요청의 늦은 응답이 새 화면을 덮어쓰지 않게 한다.

| 사용자 행동 | 상태 전환 및 결과 |
| --- | --- |
| 첫 진입 | 합의된 기본 조건 → 목록 로딩 → 성공 목록 / 빈 결과 / 조회 실패 |
| 필터 입력 | 입력값만 변경; 적용 전 목록은 기존 조건의 결과로 유지 |
| 필터 적용 | 시간·길이 등 검증 → 실패 시 필드 오류와 초점 이동; 유효하면 첫 목록 요청, 응답 성공 시 이전 상세 닫기 |
| 필터 초기화 | 최근 15분·전체 서버·전체 레벨·빈 키워드로 복원 후 첫 목록 조회, 성공 시 상세 해제 |
| 페이지 이동 | 적용된 조건 유지 → 대상 페이지 로딩 → 성공 시 교체하고 상세 해제; 실패 시 기존 목록·상세 유지 및 재시도 |
| 로그 선택 | 선택 식별자 저장 → 상세 로딩 → 상세 성공 / 미존재 / 오류; 목록은 유지 |
| 상세 닫기 | 선택 해제 → 목록의 원래 선택 요소로 초점 복귀 |
| 수동 새로고침 | 상대 범위는 현재 기준 재계산하고 절대 범위는 유지, 커서 제거 후 조회 성공 시 상세 해제; 미적용 입력은 보존 |

필터 변경·새로고침 중 이전 결과를 보존한다면 ‘이전 조회 결과’임을 명시하고, 요청 중인 조건의 결과처럼 표시하지 않는다. 실패 후 표시 조건·페이지도 기존 결과와 일치시킨다. 중복 적용·페이지 요청을 방지하되 키보드 초점을 잃지 않게 한다. 새로고침은 첫 목록으로 복귀하고 성공 시 상세를 닫는다. 화면 자동 갱신이나 자동 재시도는 추가하지 않는다.

## 로딩·빈 결과·오류

- 목록과 상세의 로딩·오류를 독립적으로 관리한다. 상세 실패로 목록을 가리지 않는다.
- 첫 로딩은 진행 상태를 알린다. 결과 갱신 중에는 마지막 성공 시각과 갱신 중 표시를 제공하고, 성공한 응답을 반영한 때만 마지막 성공 시각을 바꾼다.
- 빈 결과는 성공한 조회의 0건 상태다. 초기 조건의 로그 없음과 필터 결과 없음은 적용 조건을 바탕으로 안내하고 조건 수정·초기화를 제공한다. 수집 시스템의 정상 여부를 0건만으로 단정하지 않는다.
- 네트워크·시간 초과·서버 오류는 빈 목록으로 바꾸지 않는다. 첫 실패에는 재시도, 갱신 실패에는 기존 결과와 오래된 결과임을 표시한다.
- 잘못된 조건은 관련 필드에 연결해 안내한다. 상세 미존재는 목록 복귀·재조회 경로를 제공한다. 예외 정보 없음은 조회 오류와 구분한다.
- 사용자에게 비밀값이나 원시 서버 오류·내부 stack trace를 오류 안내로 노출하지 않는다. 상세의 수집된 합성 로그 stack trace와 API 내부 오류를 구분한다.

## UTC 표시

발생 시각과 필터 입력은 UTC로 통일하고 ‘UTC’를 눈에 보이게 표시한다. 예: `2026-10-27 03:15:42.123 UTC`. 합의된 정밀도까지만 표시하며 없는 정밀도를 만들어내지 않는다. 상대 시각만으로 표시하지 않는다. API에는 시간대가 명시된 형식을 사용하도록 요구하며 정확한 형식은 백엔드 명세의 UTC Z 표기·밀리초 응답을 따른다. 브라우저의 로컬 시간대로 묵시적으로 변환하지 않고, 날짜 입력 컨트롤의 시간대 없는 값을 UTC로 해석하는 규칙을 명시한다. 시작이 종료보다 늦은 조건과 파싱 불가능한 입력을 요청 전에 차단하며, 시작과 종료가 같은 경우도 거절한다.

## 접근성 요구

- 모든 필터에 명시적 레이블을 제공하고 필수 형식·UTC 안내와 필드 오류를 프로그램적으로 연결한다.
- 목록에는 열 제목과 표 의미를 제공한다. 상세 진입은 실제 버튼이나 링크로 구현하고 행 클릭에만 의존하지 않는다.
- 키보드로 필터·페이지·상세·새로고침을 모두 조작할 수 있게 하며 초점 표시를 유지한다. 결과 갱신이 사용자의 초점을 강제로 이동시키지 않게 한다.
- 로딩과 결과·오류 상태 변화를 보조기기에 알리되 모든 로그 원문을 한꺼번에 읽게 하지 않는다. 레벨·선택·오류는 색상만으로 구분하지 않는다.
- 상세를 대화상자로 구성한다면 이름·초점 진입·초점 순환·Escape 닫기·복귀를 제공한다. MVP는 비모달 패널을 사용하며 초점을 가두지 않는다.
- 긴 메시지와 stack trace의 줄바꿈·가로 스크롤 방식을 정하고 키보드로 원문에 접근할 수 있게 한다. 확대·좁은 화면에서도 필터와 주요 동작이 잘리지 않게 한다. 텍스트 대비는 WCAG AA 기준을 목표로 한다.

## 분야 간 합의와 남은 세부사항

백엔드·디자인 문서를 대조한 사용자 승인 결과는 [MVP 분야 간 합의](../decisions/mvp-spec-alignment.md)를 따른다. 목록·상세·입력은 UTC 밀리초, 시간 경계는 시작 포함·종료 제외다. 최근 15분을 기본으로 명시적 from/to를 전송한다. 서버 선택지는 was-1~3 설정값, 레벨은 API enum을 사용한다. 검색은 대소문자를 구분하는 message 리터럴 부분 검색이다.

기본 50건의 커서 기반 이전·다음 탐색을 사용하며 임의 페이지 이동·총 건수는 없다. 페이지 이동 중 적용 조건·시간 경계를 고정하고 필터 변경·새로고침 시 커서를 초기화한다. 늦게 도착한 로그의 완전한 스냅샷은 보장하지 않는다. serviceName은 상세에, hasException은 작은 텍스트·아이콘으로 표시한다. eventId로 상세를 조회한다. 서버는 저장 원문을 자르지 않으며 exception=null은 예외 없음이다.

상세는 넓은 화면의 비모달 우측 패널, 좁은 화면의 하단 상세로 구성한다. 조건 적용·초기화·페이지 이동·새로고침 성공 시 상세를 해제하고 실패 시 기존 목록·상세를 유지한다. 명시적 상세 열기·닫기의 초점 이동·복귀는 디자인 명세를 따른다.

API 경계 생략·최대 조회 기간과 커서 세부 규칙은 백엔드 문서의 추가 승인으로 확정됐다. UTC API 형식은 Z 표기·밀리초 응답이며 입력은 소수 초 0~3자리를 지원한다. 프론트 개발 환경은 프론트 채팅에서 별도로 정의한다. 공통 합성 사례는 분야 간 합의 문서를 사용한다.

### 프론트 처리 명세: 2026-10-27 사용자 승인 반영

아래 동작은 사용자의 추천안 반영 요청으로 프론트 명세에 적용한다. 백엔드의 응답이나 디자인의 미합의 규격을 새로 확정하지 않는다. 앞선 검토에서 추천으로 적었던 내용 중 다음 항목은 더 이상 프론트 내부 미결정이 아니다.

- 커서 만료·무효·조건 불일치에서는 기존 목록·상세를 유지하고 ‘처음부터 다시 조회’를 제공한다. 자동 대체 요청은 하지 않는다. 복구 버튼은 실패한 탐색의 적용 조건·절대 from/to를 유지하고 커서만 제거한다. 성공 시 목록·적용 조건을 함께 교체하고 상세를 해제한다. 실패 시 기존 결과를 유지한다. 이유는 읽던 내용을 보존하면서 탐색 위치만 다시 잡기 위해서다.
- 편집 중 조건, 요청 조건, 마지막 성공 조건을 구분한다. 수동 재시도는 실패한 요청의 절대 시각·필터·커서를 재사용한다. 커서 오류는 같은 커서 재시도 대신 위 복구 동작을 제공한다. 이유는 재시도할 때마다 시간 범위가 움직이거나 잘못된 커서를 반복 전송하지 않게 하기 위해서다.
- 키워드는 앞뒤 공백 제거 후 빈 값이면 파라미터를 생략하고, 200 Unicode 코드 포인트를 넘으면 입력 오류를 표시한다. 시간은 두 값 필수·시작<종료·최대 24시간을 요청 전에 검사한다. 이유는 API와 화면의 입력 판정을 맞추기 위해서다.
- 비JSON·알 수 없는 오류는 상태 코드와 통신 실패 여부로 안전한 공통 안내를 제공한다. 잘못된 성공 응답도 빈 결과로 처리하지 않는다. 조회는 자동 재시도하지 않고 수동 재시도를 제공한다. 유효한 Retry-After가 있으면 대기 안내를 표시한다. 이유는 오류를 정상적인 0건으로 오인하거나 반복 요청을 만들지 않기 위해서다. 인프라 오류의 실제 형식은 별도 합의 대상이다.
- 빈 커서 목록에서는 이전·다음 버튼을 비활성화하고 ‘처음부터 다시 조회’를 제공한다. 이유는 양쪽 커서가 null인 상태에서도 탐색을 다시 시작할 수 있게 하기 위해서다.
- 알 수 없는 level 응답 값은 원문 텍스트로 표시하고 선택지에는 추가하지 않는다. 응답의 추가 필드는 무시한다. 이유는 새로운 레벨이나 필드 때문에 기존 목록 전체가 깨지는 것을 피하기 위해서다.
- 상세는 비모달 패널로 구현할 명세이며 초점을 가두지 않는다. 명시적으로 열 때 상세 제목으로 이동하고 닫을 때 실행 버튼, 행이 없어졌다면 목록 제목으로 복귀한다. 조회 완료가 초점을 임의로 이동시키지 않게 한다. 이유는 기존 디자인의 키보드 흐름을 일관되게 적용하기 위해서다.

Next.js 후보 구조는 첫 목록을 Next.js 서버가 Spring Boot API에서 조회해 렌더링하고, 필터 편집·상세·재조회·페이지 상태는 Client Component로 관리하는 방식이다. 후속 조회의 Next.js 경유 여부, SSR 실패 시 UI, 캐시 비사용 범위와 요청 기한은 설계 초안으로 남긴다. - 2026-10-27: 최신 백엔드·디자인·분야 간 합의 문서를 대조했다. 조회 기간·커서·원문·예외 정책의 오래된 미결정 문구를 최신 승인 기록에 맞췄다. 이전에는 세부 명세를 기다렸으나 백엔드 추가 승인으로 구체화됐기 때문이다. 이미 합의된 화면 상태 전환은 유지하고, 새로 필요한 화면 복구·검증·환경 선택은 추천 상태로 구분했다. 다른 분야 문서·코드는 수정하지 않았고 실행 검증은 하지 않았다.

이 문서는 구현·검증 완료 보고가 아니다. 초기 세팅 선행조건과 별도 구현 요청을 충족하기 전 기능 구현을 시작하지 않는다.

### 향후 구현의 완료 조건과 변경 이유

별도 구현 승인 후에는 합의된 외형을 실제 화면에서 확인하고, 좁은 화면·확대·긴 메시지·trace·키보드·초점·로딩/빈 결과/실패 상태를 검증한다. 기존 JavaScript 없는 SSR·실제 MySQL/API 목록·상세 흐름과 전체 ./scripts/verify.sh를 유지한다. 접근성 목표는 본문 4.5:1, UI 경계·초점 3:1을 참고하되 자동 검사만으로 전체 접근성 통과를 주장하지 않는다. 필수 검증·기능 커밋 후 학습 문서에 새 기록을 추가한다.

- 2026-10-27: 사용자 요청으로 기존 로그 탐색 외형 개선을 다음 프론트 작업 계획으로 반영하고, 범위·유지할 동작·추가 합의를 분리했다. 현재 API로 검증 가능한 작은 작업으로 진행하고 전체 제품 구상을 일괄 구현하는 오해를 막기 위한 변경이다.
- 근거는 총괄 검토 의견, 현재 프론트 구현, 디자인 문서의 Local 미커밋 초안과 시안 HTML·CSS·JavaScript 비교다. 브라우저 보안 정책으로 로컬 HTML 열기가 차단돼 실제 시안 렌더링·클릭은 확인하지 못했다. 이 절은 문서 계획이며 UI·접근성·성능·API 검증 결과가 아니다. 이번에는 코드·설정·디자인 초안·학습 문서를 수정하거나 커밋하지 않는다.

검색·시간 선택·필터·커서·복구 확장·개요·차트·별도 오류 분석·트래픽은 이번 작업에서 제외한다. 후속 기능의 기존 승인 명세는 유지하며 아직 정하지 않은 세부만 해당 기능 착수 때 조율한다. 디자인 문서의 15분 예시는 최신 24시간 기준에 맞춰 이후 보정한다.

시각적 세부는 디자인·프론트가 매번 총괄 승인을 기다리지 않고 판단하되, 긴 메시지·trace·확대·좁은 화면·키보드·초점·각 상태·대비와 기존 흐름을 완료 전에 검증하고 이유·결과를 기록한다. 범위·기존 동작·API·정책 변경은 관련 분야와 재조율한다. 기존 완료 조건과 필수 검증은 유지한다.

변경 이유: 모든 시각적 수치와 확인 방법을 선결정하기보다, 작업 범위·화면 의미만 먼저 정하고 실제 결과를 보며 세부를 정하는 기능 단위 개발 방식을 적용했다. 기존 기록·문서는 삭제하지 않았다. 이번은 문서 반영이며 구현·실행 검증·커밋 완료 기록이 아니다.

## 2026-10-27 후속 승인: 시안 기반 공통 화면 틀

사용자가 디자인 시안을 기준으로 공통 화면 틀과 현재 로그 탐색을 맞추는 방향을 승인했다. [최신 공통 범위](../feature-development-workflow.md#2026-10-27-후속-승인-시안-기반-공통-화면-틀과-로그-탐색)를 따른다. 앞의 사이드바 보류·단일 화면 외형 개선 범위를 대체하지만 기존 검토 기록은 보존한다. 구현 착수 승인은 아니다.

공통 헤더·사이드바·패널 구조에 실제 API 목록·비모달 상세를 배치한다. 초기 진입·실제 메뉴는 로그 탐색만 제공하고 미구현 메뉴는 숨긴다. 헤더는 logscope / 로그 탐색, 서비스명은 개별 상세 표시를 유지한다. 밝은 테마·기존 표와 상세 버튼을 유지하며 다크 모드는 별도 작업이다. 기존 최근 24시간·50건·초과 제한 안내·SSR/API·실패 보존·원문·복사·초점 등 동작과 필수 검증을 유지한다.

색·간격·너비·좁은 화면의 사이드바 전환은 디자인·프론트가 실제 결과를 보며 정한다. 긴 로그·trace·확대·키보드·초점·각 상태를 검증하고 범위·API·기존 동작 변경은 재조율한다. 시안의 행 선택·조건 초기화를 그대로 복제하지 않는다. 후속 검색·커서·집계·트래픽은 이번 작업에 포함하지 않으며 공통 WAS 전송 → 검색·커서·복구 순서는 유지한다.

변경 이유: 색상 정리에서 시안의 구조를 기반으로 한 일관된 확장으로 방향을 바꾼다. 시안 자체의 실제 렌더링 검증과 기존 구현의 검증은 구분하며 완료 전 실제 화면 확인이 필요하다. 이번에는 문서만 반영하고 구현·커밋을 시작하지 않는다.

## 2026-10-28 SSE 후속 승인: 프론트 처리 기준

사용자가 추천안의 문서 반영·공유를 승인했다. [공통 SSE 합의](../feature-development-workflow.md#2026-10-28-sse-조회-후속-합의)를 따른다. 프론트 구현은 사용자의 별도 착수 지시를 기다린다. 백엔드 작업 공간의 docs/contracts/log-sse.md는 개발 중인 연동 초안이며 main 확정·완료 API로 취급하지 않는다. 구현 시 최신 명세와 응답을 대조하며 차이는 조율한다. 기존 정적 API·최소 화면 기록은 삭제하지 않는다. 새로운 /live의 잘림 표시는 기존 정적 목록 API의 50건 초과 501을 소급 변경하지 않는다.

| 항목 | 채택 기준과 이유 |
| --- | --- |
| 최초 조회 | SSR에서 items/cursor/from/to/truncated를 함께 인계하고 동일 snapshot cursor로 연결. 최초 중복 조회와 조회~연결 사이 누락 방지 |
| SSE 클라이언트 | 동일 출처 중계와 fetch SSE 파서. 프레임·JSON·summary·cursor 검증과 처리 성공 후에만 cursor 진전. ready는 진전 근거가 아니며 id/data.cursor 불일치는 처리·진전하지 않음 |
| 표시·한도 | 자동 연결, 최근 24시간 중 최신 50건, eventId 중복 제거·발생시각/eventId 내림차순. 잘림/최신50 제한 안내. 범위 밖 로그도 처리 cursor 진전 |

| 정지·재개 | 연결·재시도 종료, cursor·목록·상세·정지 시점 화면 보존. 정지 중 로컬 만료도 멈추고 재개 시 범위 재평가와 replay. 별도 정적 모드는 우선 없음 |

시작 5초·idle35초·프레임64KiB·재연결3~30초는 검증 전 시작값이다. 중계와 파서의 누적 미완성 프레임 크기·UTF-8/줄 분할·기한·취소/자원 반환, 정상 EOF와 장애별 재시도·backoff 초기화는 백엔드·프론트·필요 시 인프라가 검증해 구체화한다. 현재 시각 기준과 로컬 만료 주기·시계차·경계는 조율 대상으로 남기며 정지 중 화면 보존 원칙은 유지한다. cursor는 불투명 문자열로 취급하고 내부 순서를 JS Number로 해석하지 않는다.

상태 문구·새 로그 안내의 의미와 위치·자동 삽입/만료/상한에서 읽던 위치 유지 방법은 디자인·프론트가 실제 화면을 보며 정한다. 초기 cursor는 메모리 보관을 출발점으로 하고 숨김/재진입/언마운트 생명주기를 검증한다. 영구 복구·무손실·전체 이력 표시를 약속하지 않는다. 필요한 정상·실패·경계·실제 DB/브라우저 검증은 공통 합의의 완료 조건을 따른다.

변경 이유: 최초 연결·재연결의 데이터 처리와 읽기 경험을 함께 정리하고, 지금 정할 사용자 의미와 구현 중 검증할 수치를 나눴다. 과거 요청의 EventSource 권고는 이 후속 fetch SSE 기준으로 대체한다. 기존 기록은 보존하며 이번은 명세 반영이지 프론트 구현·실행 검증·커밋 완료가 아니다.

2026-10-28 최신 main 대조: 위 작성 당시 개발 중이던 백엔드 SSE는 PR #19로 main에 반영됐다. 현재 API 기준은 [로그 실시간 조회 명세](log-sse.md)이며 프론트 처리 방향은 이 문서의 후속 SSE 합의를 따른다. 백엔드 반영은 프론트 구현·화면 검증 완료나 착수 승인을 뜻하지 않는다. 이전 개발 중 상태 설명은 당시 검토 기록으로 보존한다.

2026-10-28 후속 구현 지시: 사용자가 명세 반영 확인 후 SSE 프론트 구현을 승인했다. 기존의 착수 지시 대기 설명은 당시 상태로 보존한다. 구현의 시간 기준·만료 주기·재시도와 화면 보존 방식은 [프론트 실시간 로그 탐색](../frontend-live-view.md)에 기록하며 필수 검증으로 확인한다. API 자체와 검색·페이지 탐색 범위는 변경하지 않는다.
