# MVP 로그 API 명세

2026-10-27 사용자 승인 조정안 반영. [MVP 분야 간 합의](../decisions/mvp-spec-alignment.md)를 공통 기준으로 사용한다. 2026-10-27 추가 사용자 승인으로 커서 세부 규칙·조회 기간 제한·전송 초기값을 아래에 확정했다. 이 문서는 기능 구현 승인이나 실제 검증 완료를 뜻하지 않는다.

## 범위와 선행조건

WAS 한 대에서 발생한 한 건을 HTTP 수집 → MySQL 저장 → 목록·상세 조회 → 화면으로 연결한 뒤 was-1·was-2·was-3으로 확대한다. 이 문서는 명세만 정리하며 API·DB·테스트·샘플 앱을 구현하지 않는다. 도메인 구현 전 초기 환경 실제 검증, GitHub 연결·CI와 브랜치 보호 적용의 미완료를 해소해야 한다. 과거 성공 기록은 현재 검증을 대체하지 않는다.

인증 도입 전 로컬 또는 격리된 개발 환경에서 합성 로그만 사용한다. 인증 방식과 외부 공개는 이 초안에서 확정하지 않는다. 배치 수집, 실시간 갱신, 범용 수집기, 검색엔진, 무손실 수집과 재시작 후 복구는 MVP 명세에 포함하지 않는다.

## 공통 표현

- 경로 접두사 `/api/v1`, 요청·성공 응답 `application/json`, 오류 `application/problem+json`, UTF-8을 사용한다.
- 시간은 UTC RFC 3339의 `Z` 표기, 소수 초 0~3자리만 허용하고 응답은 밀리초 3자리로 통일한다. 예: `2026-10-27T03:00:00.123Z`. 오프셋 표기와 소수 초 4자리 이상은 400으로 거절해 묵시적 반올림을 피한다.
- 문자열 길이는 Unicode 코드 포인트 수다. 원문 공백·줄바꿈을 저장하며 message를 임의로 자르지 않는다. 길이 초과는 거절한다. 필수 문자열은 null·빈 문자열·공백만으로 된 값이 될 수 없다.
- 요청의 알 수 없는 필드는 400으로 거절한다. 응답 필드는 향후 추가될 수 있어 클라이언트는 알 수 없는 응답 필드를 무시한다.
- 수집 요청 본문은 UTF-8 기준 최대 256 KiB(262,144 bytes)다. 압축 요청은 MVP에서 지원하지 않는다. 한 요청에 이벤트 한 건만 받는다. 실제 한계 적용은 앱·인프라가 함께 확인해야 한다.

## 공통 로그 형식

| 필드 | JSON 자료형 | 필수 | 제한·의미 |
| --- | --- | --- | --- |
| eventId | string | 예 | 소문자 하이픈 포함 UUID v4, 36자. 생성 시 한 번 부여하고 재전송 시 유지. 전체 서비스에 걸친 중복 판정 키 |
| occurredAt | string | 예 | 위 UTC 시각 형식. 발생 시각이며 수신 시각으로 덮어쓰지 않음 |
| serviceName | string | 예 | 1~64자, `[a-z0-9][a-z0-9._-]{0,63}`. 예: sample-was |
| instanceId | string | 예 | 1~64자, serviceName과 같은 패턴. 예: was-1. 서비스 내에서 서버를 유일하게 구분 |
| level | string enum | 예 | TRACE, DEBUG, INFO, WARN, ERROR 대문자 중 하나. 샘플 시연은 INFO·ERROR 사용 |
| message | string | 예 | 1~4,096자. 다중 행 허용, 비공백 문자 최소 하나 |
| exception | string 또는 null | 아니오 | 생략·null은 예외 없음으로 정규화. 값이 있으면 1~32,768자, 비공백 문자 최소 하나. stack trace의 줄바꿈 보존 |

occurredAt의 허용 과거·미래 범위는 미결정이다. 초안은 형식·유효한 날짜만 검사하며, 서버 시계 오차 보정과 보존 정책은 보장하지 않는다. ERROR에 exception을 반드시 요구하지 않으며, 다른 레벨의 exception도 허용하는 안이다.

## 수집 API

`POST /api/v1/logs`

```json
{
  "eventId": "7b2a8c30-8d94-4d5f-a6d8-931cf6a6a101",
  "occurredAt": "2026-10-27T03:00:00.123Z",
  "serviceName": "sample-was",
  "instanceId": "was-2",
  "level": "ERROR",
  "message": "Synthetic failure for logscope demo",
  "exception": "java.lang.IllegalStateException: synthetic failure\n\tat com.logscope.sample.DemoService.run(DemoService.java:24)"
}
```

저장 트랜잭션 커밋 후에만 `201 Created`를 반환한다. `Location: /api/v1/logs/7b2a8c30-8d94-4d5f-a6d8-931cf6a6a101`을 포함한다. 비동기 접수만 하고 저장 성공으로 응답하지 않는다.

```json
{
  "eventId": "7b2a8c30-8d94-4d5f-a6d8-931cf6a6a101",
  "status": "STORED"
}
```

### 중복 처리

- 동일 eventId·동일 내용 재전송은 `200 OK`, 같은 eventId와 `status: "DUPLICATE"`를 반환하며 한 건만 유지한다. 정상 전달 성공으로 취급한다.
- 동일 내용은 occurredAt을 밀리초 UTC로 정규화하고 exception 생략과 null을 동일하게 처리한 뒤 모든 필드를 비교한다. 그 외 공백·대소문자·줄바꿈은 변경하지 않는다.
- 동일 eventId에 다른 내용이 오면 `409 Conflict`와 `EVENT_ID_CONFLICT`를 반환하고 기존 값을 변경하지 않는다.
- 동시 요청에도 DB의 유일성 제약과 충돌 처리를 통해 한 건만 저장해야 한다. 구체적인 스키마는 후속 설계 대상이다.
- 타임아웃은 서버 저장 실패를 뜻하지 않는다. 응답 유실 시 동일 eventId·동일 본문으로 재시도한다. 서버는 임의의 새 eventId를 발급해 중복을 우회하지 않는다.

## 목록 API

`GET /api/v1/logs?from=2026-10-27T00%3A00%3A00.000Z&to=2026-10-28T00%3A00%3A00.000Z&instanceId=was-2&level=ERROR&keyword=Synthetic&size=50`

| 파라미터 | 필수·기본값 | 의미·검증 |
| --- | --- | --- |
| from | 필수 | occurredAt 이상(포함). 공통 UTC 형식 |
| to | 필수 | occurredAt 미만(제외). from < to, to - from ≤ 24시간 |
| instanceId | 선택, 전체 | 정확히 일치, 로그 필드와 같은 패턴. 단일 값 |
| level | 선택, 전체 | 로그 enum과 동일, 단일 값 |
| keyword | 선택, 없음 | 앞뒤 공백 제거 후 1~200자. message에서 대소문자 구분하는 리터럴 부분 문자열 검색. `%`, `_`도 문자로 취급. exception 검색은 제외 |
| cursor | 선택, 첫 목록 | 클라이언트가 해석하지 않는 탐색 커서. 아래 커서 규칙 적용 |
| size | 선택, 50 | 정수 1~100 |

서로 다른 필터는 AND로 결합한다. 빈 파라미터, 반복 파라미터, 알 수 없는 파라미터는 400이다. keyword의 공백만 있는 값도 400이며 필터 해제 시 파라미터를 생략한다. instanceId는 서비스 간 중복될 수 있으므로 해당 ID의 모든 서비스 로그를 반환한다. MVP 샘플은 serviceName 하나를 사용한다. 별도 서비스 필터는 후속 합의 대상이다.

정렬은 `occurredAt DESC, eventId DESC`로 고정하고 사용자 지정 sort는 제공하지 않는다. UUID 문자열의 정규 소문자 표현 순서로 동률을 해소한다. 수신 순서가 아닌 발생 시각 순서다.

```json
{
  "items": [
    {
      "eventId": "7b2a8c30-8d94-4d5f-a6d8-931cf6a6a101",
      "occurredAt": "2026-10-27T03:00:00.123Z",
      "serviceName": "sample-was",
      "instanceId": "was-2",
      "level": "ERROR",
      "message": "Synthetic failure for logscope demo",
      "hasException": true
    }
  ],
  "size": 50,
  "nextCursor": null,
  "previousCursor": null
}
```

`200 OK`. exception 원문은 상세에만 포함하며 목록에는 hasException을 제공한다. 목록 message와 상세 원문은 서버에서 자르지 않고 화면에서만 요약한다. 결과가 없으면 items는 빈 배열이다. nextCursor는 더 오래된 로그, previousCursor는 더 최신 로그 방향이며 해당 방향에 결과가 없으면 null이다. 위 예시는 양방향에 추가 결과가 없는 경우다. 총 건수·총 페이지 수와 번호 이동은 제공하지 않는다.

페이지는 커서 기반 이전·다음으로 탐색한다. 필터·크기 변경과 새로고침은 커서를 제거하고 첫 목록을 조회한다. 정렬 경계는 occurredAt과 eventId를 함께 사용한다. 이동 중 조회 조건과 절대 시간 경계는 고정한다. 완전한 스냅샷은 보장하지 않으며 늦게 수집된 로그는 새로고침으로 확인한다. offset 방식과 page 파라미터는 사용하지 않는다.

화면 기본 최근 15분은 프론트가 명시적인 from/to로 전송한다. API는 from/to 모두 필수이며 한 번에 최대 24시간을 허용한다. 정확히 24시간은 허용하고, 생략은 REQUIRED, 역전·동일 시각·24시간 초과는 field=to와 OUT_OF_RANGE로 400을 반환한다. 지난 날짜도 범위 내에서 조회할 수 있으며 이 제한은 보존 기간을 뜻하지 않는다. 서버 선택지는 was-1~3 설정값, 레벨 선택지는 enum으로 제공한다.

### 커서 세부 규칙과 결정 이유

- 발생 시각과 eventId를 함께 사용하는 keyset 탐색이다. next는 현재 목록 마지막 행보다 작은 정렬 키, previous는 첫 행보다 큰 정렬 키의 가장 가까운 항목을 가져온다. previous 조회도 응답은 항상 내림차순이다. 정렬 키와 조회 조건에 맞는 인덱스는 후속 구현에서 설계·실행 계획으로 검증한다.
- 커서는 버전(v=1), 방향(next/previous), 경계 occurredAt·eventId, 정규화한 조회 조건 식별값, 발급 시각과 만료 시각을 담는다. 조회 조건은 from/to·instanceId·level·keyword·size·고정 정렬을 포함한다. 시각은 밀리초로 통일하고 keyword는 앞뒤 공백 제거 후 대소문자를 보존하며 생략 필터는 null로 통일한다. 이 순서로 구성한 고정 JSON 배열의 UTF-8 SHA-256을 조건 식별값으로 사용한다.
- 외부 형식은 `base64url(payload JSON).base64url(HMAC-SHA256 서명)`이며 패딩은 생략한다. 서명은 첫 번째 인코딩 문자열에 적용한다. Base64는 암호화가 아니므로 커서에 원문 메시지·비밀값을 넣지 않는다. 서명 키는 Git에 저장하지 않고 외부에서 주입하며 실제 값·배포 설정은 지금 만들지 않는다. 클라이언트는 내부 필드를 읽거나 조립하지 않는다.
- 최초 조회 시 탐색 세션을 시작하며 만료는 시작 후 30분이다. 이후 발급하는 양방향 커서도 같은 만료를 유지한다. 만료 시각 이상이면 400 CURSOR_EXPIRED이며 커서를 제거해 첫 목록부터 재조회한다. 만료 전이라도 키 변경·서버 재시작에 따른 키 교체로 무효화될 수 있다.
- 최대 길이는 4,096 ASCII 문자다. 길이·인코딩·서명·버전·방향·필드 형식이 잘못되면 400 INVALID_CURSOR, 유효한 커서와 요청 조건이 다르면 400 CURSOR_QUERY_MISMATCH다. 모두 errors=[]이며 검증 실패한 커서를 첫 목록으로 자동 대체하지 않는다.
- 각 응답 시점의 동일 조건에서 더 오래된/최신 항목 존재 여부를 확인해 커서를 제공한다. 비어 있는 결과에는 양쪽 모두 null을 반환한다. 결과가 변해 빈 목록이 되면 사용자는 첫 목록부터 재조회할 수 있다. 커서 경계 이벤트가 사라져도 커서에 담긴 값으로 비교한다.
- 필터·size 변경과 새로고침은 커서를 제거한다. 페이지 이동 동안 절대 from/to는 고정한다. 번호 이동·전체 건수는 제공하지 않으며 완전한 스냅샷은 보장하지 않는다.

**이유:** 계속 추가되는 로그를 이전·다음으로 읽는 서비스라 마지막으로 본 위치를 기준으로 탐색하는 방식이 적합하다. offset도 작은 정적 목록에는 단순하지만 앞쪽 추가에 따른 위치 이동과 깊은 탐색의 건너뛰기 비용이 있어 채택하지 않았다. 30분 만료는 오래된 탐색 상태를 새로 조회하게 하는 MVP 초기 정책이다. 늦게 수집된 로그는 새로고침으로 확인한다.

**조회 기간의 이유:** 기본 최근 15분은 방금 발생한 오류 탐색에 맞춘다. from/to 필수와 최대 24시간은 실수로 전체 기간을 검색하는 것을 방지하면서 하루 단위 조사를 허용하는 초기 절충이다. 시간 범위만으로 데이터 양·검색 비용을 보장하지 않으므로 실제 합성 데이터로 메시지 검색과 실행 계획을 검증해야 한다.

## 상세 API

`GET /api/v1/logs/{eventId}`

`200 OK`: 공통 로그 형식 전체를 반환한다. 위 수집 요청 예시와 동일하며 exception이 없으면 `"exception": null`을 명시한다. 잘못된 UUID 형식은 400, 유효한 UUID이나 저장된 이벤트가 없으면 404 `LOG_NOT_FOUND`다. 상세는 저장 원문을 반환하고 stack trace의 줄바꿈을 보존한다. 클라이언트는 message·exception을 일반 텍스트로 렌더링한다.

## 오류 명세

```json
{
  "type": "about:blank",
  "title": "Validation failed",
  "status": 400,
  "code": "VALIDATION_ERROR",
  "detail": "One or more fields are invalid.",
  "errors": [
    { "field": "occurredAt", "code": "INVALID_UTC_TIMESTAMP" }
  ]
}
```

| HTTP 상태 | code | 처리 의미 |
| --- | --- | --- |
| 400 | VALIDATION_ERROR | 필드·쿼리·경로 형식 오류. errors에 필드별 코드 포함 |
| 400 | MALFORMED_JSON | JSON 파싱 실패 |
| 404 | LOG_NOT_FOUND | 상세 대상 없음 |
| 409 | EVENT_ID_CONFLICT | 같은 eventId의 내용 충돌 |
| 400 | INVALID_CURSOR / CURSOR_EXPIRED / CURSOR_QUERY_MISMATCH | 커서 형식·서명 오류 / 만료 / 조회 조건 불일치 |
| 413 | PAYLOAD_TOO_LARGE | 본문 byte 제한 초과 |
| 415 | UNSUPPORTED_MEDIA_TYPE | JSON 이외 또는 지원하지 않는 요청 인코딩 |
| 500 | INTERNAL_ERROR | 예상하지 못한 서버 오류 |
| 503 | STORAGE_UNAVAILABLE | DB 장애 등 저장 불가 |

필드 오류 코드는 REQUIRED, INVALID_FORMAT, INVALID_UTC_TIMESTAMP, INVALID_ENUM, TOO_LONG, OUT_OF_RANGE, UNKNOWN_FIELD, DUPLICATE_PARAMETER를 사용한다. from/to 역전은 field=to, code=OUT_OF_RANGE다. 필드 오류가 아니면 errors는 빈 배열이다. 오류에 입력 원문·SQL·서버 stack trace·비밀값을 반사하지 않는다. 프론트는 code를 기준으로 안내하고 detail의 문구에 의존하지 않는다. 인프라에서 생성하는 413·503 등의 오류도 같은 형식을 제공할 수 있는지는 조율이 필요하다.

## 전송 정책: 승인된 MVP 초기값

2026-10-27 사용자 승인. 아래는 구현할 초기 설정이며 성능·안전성이 실제 검증됐다는 의미는 아니다. 변경할 때 측정 근거와 이유를 기록한다.

| 항목 | 확정 초기값·동작 | 결정 이유 |
| --- | --- | --- |
| 전송 | 요청 처리 밖의 비동기 단일 작업자, WAS당 동시 전송 1건 | 작은 MVP의 동작·장애 분석 단순화 |
| 보관 한도 | WAS별 진행 중·재시도 포함 100건 또는 직렬화 UTF-8 본문 합계 8 MiB(8,388,608 bytes), 먼저 도달하는 한도. 단건 최대 256 KiB도 적용 | 건수와 긴 stack trace의 메모리 점유를 함께 제한 |
| 한도 초과 | 새 이벤트를 즉시 거절하고 queueRejected 증가. 기존 이벤트는 유지하고 전송 공간을 기다리지 않음 | 로그 전송이 WAS 업무 요청을 지연시키지 않게 함 |
| 연결 타임아웃 | 1초 | 격리 개발 환경에서 연결 실패를 빠르게 판별 |
| 시도 전체 타임아웃 | 연결을 포함해 3초. DNS·연결·응답 본문까지 기한 적용 여부를 구현 시 검증 | 시도 하나의 자원 점유 제한 |
| 재시도 | 최초 포함 최대 3회. 첫 재시도 전 0~500ms, 두 번째 전 0~1초 균등 무작위 대기 | 일시 장애 대응과 동시 재시도 부하 완화 |
| 재시도 대상 | 네트워크 오류·타임아웃, HTTP 500·502·503·504·429. 그 밖의 4xx·5xx는 자동 재시도하지 않음 | 일시적 가능성이 있는 실패만 제한적으로 재시도 |
| 성공 | eventId가 일치하는 201 STORED 또는 200 DUPLICATE | 응답 유실 후 중복 성공을 정상 전달로 처리 |
| 최종 실패 | 영구 오류 또는 재시도 소진 시 abandoned 증가, 원인별 구분. 409는 별도 원인으로 집계 | 시도 실패와 이벤트 전달 포기 분리 |
| 정상 종료 | 새 이벤트 접수 중단 후 진행 중·대기 이벤트 전송에 최대 5초, 이후 취소하고 남은 건수 보고 | 전송 기회를 주면서 종료 지연 제한 |
| 재시작 | 영속 대기열 없음, 비정상 종료 손실의 정확한 집계·복구를 보장하지 않음 | 승인된 MVP 범위 유지 |

byte 한도는 본문 합계로서 JVM 객체·직렬화 중 임시 메모리·HTTP 버퍼를 포함하는 전체 힙 상한이 아니다. 동일 이벤트 재시도는 같은 본문 버퍼와 보관 슬롯을 유지하며 성공·포기·종료 시 해제한다. 과대 이벤트는 전송 전에 거절하고 원인별 집계한다. 실제 직렬화·전송 과정이 업무 요청에 주는 비용도 후속 검증 대상이다.

Retry-After가 유효한 429·503 응답은 재시도 대기 하한으로 존중하되, 남은 대기가 3초를 초과하면 대기 시간을 줄여 재시도하지 않고 전달을 포기한다. 유효한 헤더가 없으면 위 무작위 대기를 적용한다. 예상 밖 성공 응답·응답 형식 오류는 성공으로 처리하지 않고 진단 후 포기한다. 모든 재시도는 동일 eventId·동일 본문을 유지한다.

단일 작업자가 장애 중 한 이벤트를 재시도하면 뒤의 이벤트도 대기한다. 이 설정은 짧은 장애와 낮은 시연 부하를 위한 것으로 장기 장애·대량 수집에 대한 처리량이나 무손실 전달을 보장하지 않는다. 정상 종료에서 미전송 이벤트는 shutdown 원인으로 abandoned에 포함하며, 타임아웃 이벤트는 실제로 저장됐을 수도 있다.

외부 전송 처리에서 발생한 로그가 다시 전송되어 순환하지 않도록 전송기 자체 진단은 수집 대상에서 제외한다. 전송 성공 여부가 불명확한 최종 타임아웃은 실제 미저장 건수와 같지 않다.

실패·누락 확인은 WAS별 로컬 구조화 진단 또는 격리 환경의 관리 지표를 후보로 둔다. 사용자 화면에 별도 운영 대시보드를 추가하는 것으로 확정하지 않는다. 집계할 항목은 generated, enqueued, queueRejected, sendAttempts, failedAttempts, acknowledged(신규·중복 구분), abandoned(영구 오류·재시도 소진 구분), queueDepth다. 누적값은 프로세스 재시작 시 초기화하며 queueRejected·abandoned를 관측 가능한 전달 포기로 설명한다. 재시도 실패 횟수를 누락 이벤트 수로 합산하지 않는다. 정상 종료 시 남은 이벤트 수는 shutdownPending으로 별도 기록하며 abandoned와 중복 합산하지 않는다. 구체적인 지표 이름과 진단 노출 방식은 인프라와 조율한다.

## 합의 상태와 구현 전 세부 결정

[MVP 분야 간 합의](../decisions/mvp-spec-alignment.md)에 따라 UTC 밀리초, 시작 포함·종료 제외, 최근 15분 화면 기본값, 커서 탐색, 서버 고정 설정, 상세 성공 시 해제, 원문 비절단과 공통 was-2 예시를 적용한다. 이 문서의 API 경로·필드·중복·오류 규칙을 기준으로 프론트와 디자인을 맞춘다.

조회 기간, 커서 형식·검증·응답·만료와 전송 초기값·byte 상한·종료 처리는 위 추가 승인으로 확정했다. 남은 조율은 진단 노출과 지표 이름, 인프라 오류 형식, 검증 데이터 양과 실행 계획·지연·처리량·메모리 검증이다. 공통 합의 문서의 해당 항목에 남은 “미결정/수치 제안” 표시는 이번 백엔드 세부 승인 이전 기록이며, 이 문서의 구체화가 후속 기준이다. 프론트 환경은 프론트 담당, 브랜치 보호는 인프라 담당이며 기능 구현은 별도 요청 전까지 시작하지 않는다.
