# logscope MVP 범위와 개발 순서

2026-10-27 합의 기준. 여러 서버의 로그를 한곳에서 관측하고 오류가 발생한 서버와 원인 로그를 찾는 것을 첫 MVP의 목표로 한다. 현재 승인은 범위 정리와 공유까지이며, 구현은 별도 요청 전까지 시작하지 않는다.

세부 API·화면의 확정 기준과 남은 결정은 [MVP 명세와 화면 합의](decisions/mvp-spec-alignment.md)를 따른다. 브랜치 보호는 인프라 채팅, 프론트 개발 환경은 프론트 채팅에서 담당한다.

## 개발 배경과 목표

기존 이커머스 환경에는 Front Office WAS 2대, Back Office WAS 2대와 BATCH 서버가 있었다. 로그가 서버마다 따로 쌓여 오류 발생 시 개발자가 서버를 하나씩 확인해야 했고, 많은 로그 속에서 원인을 찾기 어려웠다.

MVP에서는 샘플 WAS 3대로 분산 환경을 재현하고, 각 WAS의 로그를 logscope로 전송해 중앙 저장과 통합 조회를 제공한다. 최종 시연은 세 WAS 중 하나에서 오류를 발생시킨 뒤 서버에 직접 접속하지 않고 logscope 화면에서 발생 서버와 stack trace를 찾는 흐름이다.

## 포함 범위

| 영역 | MVP 범위 |
| --- | --- |
| 테스트 WAS | 작은 Spring Boot 샘플 앱 하나를 was-1, was-2, was-3이라는 서로 다른 instanceId로 3개 실행 |
| 로그 생성 | 정상 요청과 의도적인 오류 요청으로 INFO, ERROR와 예외 로그 생성 |
| 로그 전송 | 샘플 앱에서 공통 형식의 로그를 HTTP로 logscope 수집 API에 전송 |
| 중앙 저장 | 수신한 로그를 MySQL에 저장 |
| 통합 조회 | 세 WAS의 로그를 최신순으로 표시하고 페이지 단위로 탐색 |
| 필터 | 발생 시간, 서버 ID, 로그 레벨과 메시지 키워드 |
| 로그 상세 | 발생 시각, 서비스, 서버, 레벨, 메시지와 예외 stack trace |
| 화면 갱신 | 수동 새로고침 |

샘플 WAS에는 실제 쇼핑몰이나 관리자 업무 기능을 구현하지 않는다. 첫 화면은 차트보다 로그 목록, 필터와 상세 확인에 집중한다. MVP는 직접 연동한 샘플 앱을 대상으로 하며 기존 시스템의 로그를 자동 수집하는 범용 수집기는 포함하지 않는다.

## 로그 명세와 전송 조건

공통 로그의 기본 필드는 다음과 같다. 자료형·필수값·길이·API·조회·전송 세부 기준은 사용자 후속 승인이 반영된 [API 명세](contracts/log-api-draft.md)를 따른다.

| 필드 | 의미 |
| --- | --- |
| eventId | 로그 이벤트의 고유 ID. 동일 이벤트 재전송 시 유지 |
| occurredAt | UTC 기준 로그 발생 시각 |
| serviceName | 로그를 생성한 서비스 이름 |
| instanceId | was-1 등 발생 서버를 구분하는 ID |
| level | 로그 레벨 |
| message | 로그 메시지 |
| exception | 예외 발생 시 stack trace |

- logscope 중단이나 전송 실패가 샘플 WAS의 요청 처리 실패로 이어지지 않게 한다.
- 전송 대기열에 크기 제한을 두고 전송 실패와 누락 건수를 확인할 수 있게 한다.
- 동일 eventId의 재전송으로 로그가 중복 저장되지 않게 한다.
- 전송 한도·타임아웃·재시도·종료 정책은 API 명세의 승인된 초기값을 따른다. 무손실 전송이나 재시작 후 복구를 보장하는 범위로 확대하지 않는다.
- 비밀번호, 토큰과 개인정보가 없는 합성 로그를 사용한다.
- 인증 체계를 갖추기 전에는 로컬 또는 격리된 개발 환경에서 검증한다.

## 개발 순서와 완료 조건

2026-10-27 사용자 승인으로 기능별 구현·검증과 적시 결정 방식으로 변경했다. [기능 단위 개발 방식](feature-development-workflow.md)을 최신 진행 기준으로 사용한다. 이번 요청은 문서·공유까지이며 실제 구현은 별도 요청 후 시작한다.

| 순서 | 목표 | 확인할 결과 |
| --- | --- | --- |
| 1 | 공통 문서·규칙 정리, 전체 검증·PR 병합 | 같은 시작 기준 공유 |
| 2 | 합성 로그 한 건 수집·저장·최소 조회 | 직접 보낸 JSON을 조회하고 중복은 한 건 유지 |
| 3 | 최소 프론트 환경과 목록·상세 연결 | 브라우저에서 서버·메시지·stack trace 확인 |
| 4 | 샘플 WAS 한 대 자동 전송 | WAS 오류가 화면에 나타남 |
| 5 | 검색·필터·커서 탐색·복구 | 원하는 로그 검색과 이전·다음·실패 복구 |
| 6 | WAS 세 대와 장애·통합 검증 | 발생 서버 식별과 실패·중복·포화·종료 확인 |

초기 환경·GitHub·CI·브랜치 보호는 인프라 PR #4·#5의 충족 기록을 따른다. 운영 배포 완료를 뜻하지 않는다. 필요한 중계·실행·검증은 해당 기능 도입 시 함께 준비하고, 기존 승인 명세·검증·비밀 관리·PR 규칙을 유지한다.

## 분야별 첫 작업과 이후 책임

| 분야 | 먼저 정리할 내용 | 구현 요청 후 담당할 내용 |
| --- | --- | --- |
| 총괄 | MVP 완료 조건, 범위와 분야 간 합의 | 변경 범위 조율과 검증 결과 검토 |
| 디자인 | 오류 발견 → 발생 서버 확인 → 상세 로그 확인 흐름 | 목록, 필터, 상세 화면 및 로딩·빈 결과·오류 상태 규격 |
| 프론트 | 디자인·백엔드와 표시 필드 및 조회 API 합의 | 합의된 예시 데이터로 화면 구현 후 실제 API 연결, 접근성 확인 |
| 백엔드 | 공통 로그 형식과 수집·조회 API 명세 | 새 Flyway migration, 저장·수집·조회, 샘플 WAS 전송과 실패·중복 처리 |
| 인프라 | 초기 환경, GitHub 연결, CI와 브랜치 보호 실제 상태 확인 | logscope, MySQL과 샘플 WAS 3대의 Compose 실행 구성 및 검증 절차 |

API 명세와 화면 합의는 함께 진행한다. 명세 확정 후 프론트는 예시 데이터로 작업할 수 있고, 백엔드는 API를 구현할 수 있다. 인프라는 한 대로 시작하는 흐름과 세 대로 확장하는 실행 구성을 지원한다. 공통 파일의 수정 담당을 정하고 동시 구현은 별도 worktree에서 수행한다.

## 후속 범위

- 대시보드 차트와 알림
- WebSocket 기반 실시간 전송과 화면 갱신
- 분산 추적
- 기존 로그 파일 수집과 범용 로깅 라이브러리
- 별도 검색엔진 도입
- 실제 운영 배포와 운영 규모 성능 검증

운영 배포와 파괴적 DB 작업은 AGENTS.md 및 docs/operations.md에 따른 명시적 실행 승인이 필요하다.

## MVP 검증 기준

- 세 WAS에서 생성한 로그를 통합 조회하고 발생 서버를 구분할 수 있다.
- 특정 WAS에서 의도적인 오류를 발생시키고 시간·서버·레벨·키워드 필터로 해당 로그와 stack trace를 찾을 수 있다.
- 페이지 탐색과 수동 새로고침이 실제 조회 API와 연결된다.
- logscope 중단 시 샘플 WAS가 요청을 처리하며, 전송 실패와 누락을 확인할 수 있다.
- 같은 이벤트를 재전송해도 중복 저장되지 않고 전송 대기열 제한이 동작한다.
- 커밋 전 scripts/verify.sh와 scripts/check-secrets.sh, PR 및 CI verify 등 AGENTS.md의 검증·병합 규칙을 충족한다.

각 기능 구현 전 그 기능에 필요한 API·화면·전송·검증 조건을 정한다. 이후 기능의 미결정까지 모두 끝낼 필요는 없다. 대규모 운영 성능이나 무손실 수집을 이 MVP의 완료 결과로 주장하지 않는다.

## 후속 결정과 변경 기록

- 2026-10-27: 최초에는 브랜치 보호가 플랜 제한으로 미완료였으나 사용자의 public 전환과 인프라 후속 작업으로 충족했다. 이전 미완료 설명은 현재 상태에서 대체하며 상세 근거는 초기 설정 기록에 보존한다.
- 같은 날 백엔드의 필수 from/to·최대 24시간·커서 30분·전송 초기값과 프론트의 TypeScript·Next.js SSR 기준을 [공통 합의](decisions/mvp-spec-alignment.md)에 반영했다. 큰 MVP 범위와 한 WAS부터 시작하는 순서는 유지한다.
- SSR 구조는 [공통 아키텍처](architecture.md), 남은 조율은 [추가 합의 검토안](decisions/mvp-cross-area-proposals.md)을 참고한다. 검토안은 확정 정책이 아니며 구현·실행 검증 완료를 뜻하지 않는다.

## 이전 개발 순서 보존

WAS 한 대에서 로그 한 건이 화면에 도달하는 흐름을 먼저 완성한 뒤 세 대로 확대한다. 아래 순서는 향후 구현을 요청받았을 때 적용한다.

| 단계 | 작업 | 완료 조건 |
| --- | --- | --- |
| 0 | 초기 세팅 선행조건 확인 | 실제 환경, GitHub 연결과 CI를 확인하고 브랜치 보호 미완료를 해소 |
| 1 | 로그 형식, API와 화면 흐름 합의 | 분야별로 같은 예시 로그와 API 명세를 사용 |
| 2 | 수집, 저장과 조회 API 구현 | 테스트 로그 한 건을 저장하고 조회 가능 |
| 3 | 샘플 WAS 한 대의 전송 구현 | 요청으로 생성한 로그가 logscope에 도착 |
| 4 | 프론트 목록, 필터와 상세 연결 | 실제 수집 로그를 화면에서 탐색 가능 |
| 5 | 샘플 WAS를 세 대로 확대 | 세 instanceId의 로그를 한 목록에서 조회하고 서버별로 필터 가능 |
| 6 | 장애와 통합 검증 | 오류 서버와 stack trace 식별, 전송 실패·대기열 제한·중복 처리 확인 |

초기 세팅·GitHub·CI·브랜치 보호는 인프라의 후속 확인과 PR #4·#5로 선행조건 충족이 기록됐다. [초기 검증 기록](setup-status.md)의 최신 근거를 따른다. 위 단계 0은 이 확인을 기록하는 단계이며 이후 작업에서도 해당 작업 상태를 확인한다. 프론트 SSR 도입의 추가 실행·검증 구성은 아직 합의 전이고, 기능 구현은 별도 요청 후 시작한다.


위 초기 순서는 현재 적용하지 않는다. 화면에서 한 건을 먼저 확인하고 이해를 쌓기 위해 위 최신 순서로 변경했다. 기존 표와 근거는 보존한다.

- 2026-10-27 후속 변경: 모든 제안 확정을 기다리는 방식에서 기능별 결정·구현·검증으로 전환했다. 세부 방식과 결정 시점은 기능 단위 개발 문서에 기록했다. 기능 구현은 시작하지 않았다.
