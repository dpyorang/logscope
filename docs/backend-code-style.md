# 백엔드 코드 구조와 주석 규칙

2026-10-28 사용자 요청으로 정한 백엔드 기준이다. 중앙 서버와 샘플 WAS의 Java 코드에 적용한다. 루트 공통 규칙과 API·DB·수집·검색·실시간 동작 명세는 유지한다.

## 기능별 패키지와 내부 계층

먼저 기능으로 나누고 그 안에서 역할별 계층을 나눈다. 현재 중앙 서버의 기능은 `com.logscope.log`, 샘플 WAS의 기능은 `com.logscope.sample`이다. 앞으로 독립 기능이 생기면 같은 원칙으로 별도 기능 패키지를 만든다. 모든 기능의 컨트롤러를 루트 `controller`에 모으는 방식으로 평탄화하지 않는다.

```text
com.logscope
├── LogscopeApplication.java
└── log
    ├── controller          # HTTP API와 상태·헤더 처리
    │   └── support         # 크기·인코딩 제한이 있는 HTTP 본문 읽기
    ├── service             # 수집·조회·검색·실시간 처리 흐름
    ├── repository          # MySQL SQL·트랜잭션·잠금
    ├── client              # ES 문서 연산·요청 변환·제한된 HTTP 통신
    ├── domain              # 불변 원본·읽기 모델과 cursor 의미
    ├── dto                 # 요청 조건과 API·SSE 응답 값
    ├── validation          # 공통 로그 입력 검증
    ├── config              # 검색 스케줄 활성화·주기 구성
    ├── exception           # 오류 의미와 HTTP 예외 변환
    └── support             # 저장 commit 이후 깨우기 신호

com.logscope.sample
├── SampleApplication.java
├── controller
├── service
├── domain
├── dto
├── config
└── logging                 # Logback JSON 인코더
```

- 파일이 한 개여도 역할에 맞는 패키지를 사용한다. 설정 클래스는 `config`, 컨트롤러는 `controller`에 둔다. 실행 진입점은 Spring의 기능 탐색 범위를 유지하도록 애플리케이션 루트에 둔다.
- 현재 필요 없는 빈 계층·형식적인 서비스 인터페이스·범용 Base 클래스는 만들지 않는다. 도메인이 커져 검색·실시간 자체를 독립 기능으로 나눌 때 그 기능 안에서도 같은 계층 기준을 적용한다.
- 컨트롤러는 HTTP 입력·응답·상태·헤더와 예외 매핑을 담당한다. SQL·ES 호출·배치 처리·스케줄·동시 처리 정책은 직접 구현하지 않는다. HTTP 본문 한도/인코딩 처리는 controller.support의 명시적 경계다.
- 서비스는 기능 처리 순서와 오류 전파를 담당하며 저장소·외부 클라이언트를 조합한다. SSE 전송 서비스는 장기 연결 자원을 관리하는 전송 기능이므로 SseEmitter를 사용한다. 일반 업무 서비스에 HttpServletRequest·ResponseEntity를 전파하지 않는다.
- 저장소는 DB 쿼리·행 잠금·트랜잭션 경계를 담당한다. 컨트롤러·업무 서비스·ES 클라이언트에 역으로 의존하지 않는다. 검색 작업의 상태 행 잠금은 외부 색인 확인까지 같은 트랜잭션을 유지하는 현재 정합성 조건이므로 파일 분리만을 이유로 범위를 줄이지 않는다.
- 클라이언트는 외부 연산·프로토콜 검증을 담당한다. ES Query DSL 변환과 HTTP 기한·응답 크기 처리는 별도 클래스로 나누며 저장소·컨트롤러에 의존하지 않는다.
- domain·dto·validation은 값의 의미와 경계 검증을 드러낸다. DB 접근·외부 통신·스케줄을 넣지 않는다. support는 재사용할 기술 협력 객체에만 사용하며 분류하기 어려운 코드를 몰아넣는 폴더로 사용하지 않는다.
- 클래스·메서드는 기본적으로 필요한 범위만 공개한다. 계층 간 협력 지점은 public, 내부 알고리즘과 통신 버퍼 구현은 private 또는 package-private로 둔다. 예외 필드는 외부에서 수정하지 못하게 하고 읽기 메서드를 사용한다.

## API와 메서드 설명

- 프로덕션 Java 클래스와 직접 작성한 메서드 위에 짧은 한국어 Javadoc을 둔다. 메서드 이름의 반복보다 무엇을 하는지와 필요한 이유·제약을 설명한다. 생성자는 연결하는 의존성과 중요한 설정, 내부 메서드는 목적을 간단히 적는다. 자동 생성되는 record 접근자에 설명을 중복 작성하지 않는다.
- API 메서드는 HTTP 메서드와 경로, 주요 입력 또는 반환 결과를 한두 문장으로 설명한다. 애너테이션 위에 배치해 한 번에 읽을 수 있게 한다.
- 트랜잭션·잠금·commit 이후 신호·재시도·자원 반환처럼 코드를 옮길 때 깨지기 쉬운 이유는 해당 처리 가까이에 남긴다. 모든 줄에 동작을 풀어 적거나 당연한 getter 설명을 길게 늘이지 않는다.
- 주석을 실제 코드·명세와 함께 수정한다. 동작하지 않는 기능이나 보장하지 않는 무손실·정합성·성능을 주석으로 약속하지 않는다. 예시에는 합성 데이터만 사용한다.

```java
/** GET /api/v1/logs/search: 조건에 맞는 검색 결과와 색인 대기 상태를 반환한다. */
@GetMapping("/search")
public ResponseEntity<SearchResult> search(...) { ... }
```

## 변경과 검증

패키지 이동도 동작 변경 위험이 있는 작업이다. 컴포넌트 탐색·생성자 주입·예외 advice·Logback 클래스 경로·테스트 설정·문서 코드 링크를 함께 확인한다. 기존 MySQL/HTTP/ES/SSE·파일 수집 통합 테스트를 줄이거나 단위 테스트로 대체하지 않는다. API 경로·JSON 필드·상태 코드·시간/크기 한도·스키마·트랜잭션과 재시도 의미를 보존한다. 동작을 바꿔야 한다면 구조 변경에 숨기지 않고 이유와 명세를 따로 갱신한다.

`BackendArchitectureTests`는 소스의 기능/계층 위치, config 위치, 컨트롤러→저장소/ES 직접 참조와 저장소/클라이언트→서비스 역참조를 검사한다. 이는 정해진 경계의 회귀 검사이며 모든 의존 그래프와 동작을 증명하는 도구는 아니다. 분리한 서비스의 성공·오류·경계 테스트와 실제 통합 검증을 함께 사용한다.

영역별 기술 변경은 [학습 기록 형식](learning-record-format.md)에 따라 필수 검증·작업 커밋 후 [백엔드 학습 문서](learning/backend.md)에 새 항목으로 추가한다. 루트의 비밀·전체 검증·PR 정책은 동일하게 적용한다.
