# 로그 탐색 화면 규격

2026-10-27 사용자 승인 조정안 반영. [MVP 분야 간 합의](../decisions/mvp-spec-alignment.md)를 공통 기준으로 사용한다. 확정 기준은 최신 [API 명세](../contracts/log-api-draft.md)와 [프론트 연동 명세](../contracts/frontend-integration-draft.md)의 추가 승인 기록도 따른다. 아래 추가 확인 제안은 분야 간 합의 전이며, 이 문서는 기능 구현 승인이 아니다.

## 목적과 범위

루트 AGENTS.md와 docs/mvp-plan.md를 기준으로 작성한다. 특정 WAS에서 발생한 오류를 통합 목록에서 찾고, 발생 서버와 stack trace를 확인하는 흐름을 설계한다. 이 문서는 UI 구현 승인을 의미하지 않는다. 초기 환경·GitHub·CI·브랜치 보호 선행조건을 확인한 뒤 별도 구현 요청에 따라 진행한다.

포함 범위는 최신순 목록, 발생 시간·서버·레벨·메시지 키워드 필터, 페이지 탐색, 수동 새로고침과 로그 상세다. 차트, 알림, 실시간 갱신, 분산 추적, 전송 상태 대시보드는 추가하지 않는다. 전송 실패·누락 확인 방식은 별도 명세와 운영 설계에 의존하며 이 화면에서 수집 완전성이나 서버 정상 여부를 추정하지 않는다.

## 현재 적용 기준과 전체 제품 구상의 구분

2026-10-27 후속 사용자 승인으로 다음 프론트 작업은 밝은 테마의 기존 로그 탐색 외형 개선으로 한정한다. 헤더는 `logscope / 로그 탐색`, 미구현 메뉴·사이드바는 보류하고 다크 모드는 별도 작업으로 분리한다. 표와 명시적 상세 버튼, 상세의 개별 서비스명 표시를 유지한다. 현재 기본 조회는 최근 24시간이며 아래 15분 설명은 이전 설계 기록이다. 전체 제품 구상의 서비스 헤더·메뉴·테마를 이번 구현 범위로 적용하지 않는다.

정확한 색·글꼴·간격·패널·줄바꿈·전환 폭은 파란색 강조 밝은 테마와 현재 1,200px를 시작점으로 디자인·프론트가 실제 화면을 보며 조정한다. 완료 전 긴 로그·확대·좁은 화면·키보드·초점·상태·대비 검증이 필요하다. 범위·기존 동작·API·공통 정책 변경은 관련 분야와 조율한다. [공통 결정 시점](../feature-development-workflow.md#2026-10-27-로그-탐색-외형-개선의-범위와-결정-시점)과 [프론트 승인 반영](../contracts/frontend-integration-draft.md#frontend-design-next-scope)을 따른다. 기존 구상은 학습 근거로 보존하며 기능 구현은 별도 요청 전 시작하지 않는다.

## 전체 제품 화면 구성 초안

2026-10-27 사용자 요청으로 대화에서 검토한 전체 화면과 라이트·다크 모드 구상을 기록한다. 이 절은 디자인 초안이다. 개요 집계·차트·별도 오류 분석 화면·테마 전환을 기존 MVP의 구현 확정 범위에 추가한 것으로 해석하지 않는다. 실제 구현 시점과 필요한 API는 총괄·프론트·백엔드와 해당 기능 착수 때 합의한다. 앞의 목적과 범위 및 아래 로그 탐색의 확정 기준은 유지한다.

### 공통 화면 틀과 정보 구조

```text
logscope · 서비스 이름                           [라이트/다크 전환]
────────────────────────────────────────────────────────────────
개요          화면 제목                               [새로고침]
로그 탐색     공통 조사 시간 · UTC / 발생 서버
오류 분석     ───────────────────────────────────────────────────
              화면별 필터와 본문
트래픽 · 예정
```

왼쪽 탐색 메뉴에서 개요·로그 탐색·오류 분석을 전환하고, 상단에는 서비스 맥락과 오른쪽 테마 전환을 둔다. 샘플 서비스가 하나일 때는 서비스 이름을 표시하며 동작 없는 단일 선택기는 만들지 않는다. 여러 서비스 선택은 후속 합의다. 좁은 화면에서는 메뉴를 상단의 줄바꿈 가능한 탐색 영역으로 바꾸고 본문·상세를 세로로 배치하는 안이다.

조사 시간과 서버는 화면 간 이어지는 맥락으로 취급한다. 공통 조건의 정확한 배치·적용 버튼·주소 반영 방식은 프론트와 합의한다. 기존 로그 탐색의 ‘편집 중 조건과 적용 조건 구분’ 원칙을 유지하며, 초안의 즉시 서버 선택 동작을 필터 적용 방식의 변경 승인으로 보지 않는다.

| 화면 | 목적·구성 | 연결 동작 | 현재 상태 |
| --- | --- | --- | --- |
| 개요 | 선택 시간의 수집 로그 건수·ERROR 건수·로그가 있는 서버 수, 로그 발생 추이, 서버별 ERROR 분포, 최근 오류 | 시간 구간에서 해당 범위의 로그 탐색, 서버별 오류에서 해당 서버의 오류 분석, 최근 오류에서 개별 상세로 이동 | 전체 제품 구상. 집계·차트는 후속 제안 |
| 로그 탐색 | 모든 레벨의 최신순 목록, 시간·서버·레벨·메시지 필터, 페이지와 비모달 상세 | 오류 전후 맥락을 읽고 선택 로그의 서버·메시지·stack trace 확인 | 기존 MVP 핵심 화면. 세부 확정·미합의는 본문 기준 |
| 오류 분석 | 처음에는 ERROR 조건의 개별 로그 목록과 같은 상세를 재사용. 현재 초안은 유형별 묶음을 제공하지 않음 | 개별 오류를 열고 필요하면 같은 시간·서버의 전체 로그로 이동 | 별도 화면·이동 규칙은 제안. ERROR 필터 자체는 기존 범위 |
| 트래픽 | 요청량·응답 시간·실패율을 보여줄 향후 공간 | 특정 구간·서버의 관련 로그로 연결하는 방향 | 추후 확장안. 측정 데이터·API·집계 방식 미확정 |

같은 로그에 대한 목록과 상세를 공유하는 이유는 화면마다 서버·시각·예외 표현이 달라지는 혼선을 줄이기 위해서다. 오류를 유형별로 묶고 반복 횟수·최근 발생을 비교하는 기능은 묶음 기준과 집계가 필요하므로 별도 후속 제안으로 둔다. 현재 명세의 message·exception만으로 근거 없는 오류 동일성을 단정하지 않는다.

### 개요에서 원문까지 이어지는 조사

예를 들어 전체 서버 개요에서 03:00~03:03 구간을 선택하면 기존 공통 시간과 교집합인 범위로 로그 탐색을 열고, was-2의 ERROR 분포를 선택하면 기존 시간·was-2·ERROR 조건으로 오류 분석을 여는 안이다. 이동 시 새 조건을 적용하고 커서를 제거하며, 선택한 개별 이벤트가 없으면 상세를 해제한다. 특정 오류를 선택해 상세로 연결할 때 해당 eventId와 시각이 이동 조건에 포함되게 한다.

화면을 이동해도 사용자가 선택한 서비스·서버·절대 시간은 임의로 전체 범위나 현재 시간으로 바꾸지 않는다. 최근 15분 재계산은 기존 수동 새로고침 규칙을 따른다. 오류 분석에서 전체 로그로 이동하면 ERROR 고정 조건은 해제하고 시간·서버는 유지하는 안이다. 오류 발생 시각 주변의 자동 시간 확장은 아직 제안하지 않는다.

개요 집계는 현재 페이지 50건만 세어 전체 시간 범위의 수치처럼 표시하면 안 된다. 기간 전체 집계·시간 구간 폭·늦은 로그 반영·집계와 목록의 조회 시점 차이는 백엔드와 합의해야 한다. 로그가 있는 서버 수는 서버의 정상·장애 상태를 의미하지 않는다. 차트와 최근 오류도 로딩·빈 결과·실패를 구분하며, 집계 실패를 0으로 표시하지 않는다.

### 라이트·다크 모드 디자인 초안

사용자가 흰색과 밝은 보조색, 오른쪽 위 다크 모드 전환을 요청해 대화형 초안에 반영했다. 라이트는 흰색 본문·패널과 연한 파란색 바탕·선택 영역, 파란색 강조를 사용한다. 다크는 짙은 남색·회색 표면과 밝은 글자·파란색 강조를 사용한다. ERROR는 두 모드 모두 텍스트와 구분 가능한 붉은 계열을 함께 사용한다.

- 헤더 오른쪽에 현재 변경 가능한 동작을 뜻하는 ‘다크 모드’ 또는 ‘라이트 모드’ 버튼을 둔다. 아이콘만으로 동작을 전달하지 않는다.
- 전환은 메뉴·필터·목록·차트·상세·trace에 함께 적용하며 조사 조건·선택 로그·읽던 위치를 초기화하지 않는 안이다.
- 밝은 화면을 이번 초안의 기본으로 사용했다. 실제 앱의 최초 기본값·시스템 테마 추종·사용자 선택 저장 범위·SSR 첫 화면과의 일치는 프론트와 합의한다. 대화형 초안의 선택 보존은 실제 앱 저장 정책이 아니다.
- 기존 ‘밝은 테마 한 가지로 시작’ 제안은 사용자 요청에 따라 라이트·다크 두 모드 구상으로 대체한다. 기존 제안은 초기 검토 근거로 보존한다.
- 구체 색상 토큰과 대비는 미확정이다. 두 모드에서 본문·보조 문구·선택·초점·오류 대비, 키보드 조작, 확대와 긴 trace를 실제 화면으로 확인해야 한다. 접근성 통과 결과는 아직 없다.

### 트래픽 확장안과 데이터 경계

트래픽 메뉴는 이번 구상에서 ‘예정’으로 표시하며 실제 측정값 대신 확장 위치를 보여준다. 향후 요청량(요청 수·초당 요청), 응답 시간(중앙값·p95 등 후보), 실패 요청 비율을 검토한다. 이 지표의 정의·분모·시간 집계·수집 방식·서비스와 서버 식별은 아직 확정하지 않았다.

로그 한 건이 요청 하나와 일치하지 않으므로 로그 발생량을 요청 트래픽·실패율로 바꾸어 표시하지 않는다. 현재 초안의 차트는 ‘로그 발생 추이’다. 트래픽은 별도 요청 측정 근거가 생긴 뒤 수치를 제공하며 기존 로그 API의 필드를 임의로 확대하지 않는다. 실제 앱에서 예정 메뉴를 미리 노출할지 숨길지는 구현 시점에 결정한다.

### 근거·한계와 다음 결정

두 초안은 합성값의 배치·로컬 선택 동작을 보여준다. 고정 시간 선택, 일부 레벨과 소수 행, 비활성 페이지 버튼을 사용하며 실제 API·시간 입력·원문 복사·SSR·성능·운영 상태의 구현 완료를 뜻하지 않는다. 이번에 실제 프론트 코드나 API를 수정하지 않았다.

최신 [기능 단위 진행 방식](../feature-development-workflow.md)에 따라 한 건의 최소 목록·상세를 먼저 연결하고, 공통 화면 틀·테마는 필요한 시점에 프론트와 결정한다. 개요 집계·별도 오류 분석·트래픽을 현재 작업의 선행조건으로 삼지 않는다. 이 절은 당시 미커밋 디자인 정리 기록이다. 후속 문서 검증·커밋은 디자인 구현 완료나 시안의 실제 동작 검증을 뜻하지 않는다.

## 핵심 사용자 흐름

1. 로그 탐색 화면에서 발생 시간 범위를 지정하고 ERROR 레벨로 조회한다. 필요하면 메시지 키워드를 추가한다.
2. 최신순 결과에서 발생 시각, 레벨, 서버 ID와 메시지를 함께 읽어 오류와 발생 서버를 식별한다. 서버 필터로 해당 WAS만 좁힐 수 있다.
3. 행의 상세 보기 버튼을 선택하면 상세 영역에서 발생 시각·서비스·서버·레벨·전체 메시지를 확인한다.
4. 같은 상세 영역에서 stack trace를 읽고 필요하면 복사한다. 예외가 없는 로그는 예외 정보 없음으로 구분한다.
5. 상세를 닫거나 다른 로그를 선택해도 적용된 필터와 현재 목록 페이지는 유지한다.

한 WAS의 합성 로그 한 건으로 이 흐름을 검토한 뒤 was-1, was-2, was-3의 로그를 함께 탐색하는 시나리오로 확대한다. 모든 레벨과 ERROR 로그를 구분할 수 있으며 ERROR가 항상 예외를 포함한다고 가정하지 않는다.

```text
발생 시각 | 레벨 | 서버 | 메시지        | 로그 상세 / 닫기
로그 목록                              | 기본 정보
                                       | 전체 메시지
[이전] [다음]                          | Stack trace / 복사
```

넓은 화면에서는 목록과 오른쪽 상세를 나란히 배치한다. 상세 미선택 시 안내를 표시한다. 목록의 메시지는 한두 줄로 축약하되 원문은 상세에서 제공한다. 서버와 레벨은 축약하지 않는다. 서비스명은 상세에 표시한다. 목록에는 hasException을 작은 텍스트·아이콘으로 표시하고 색상만으로 구분하지 않는다.

좁은 화면에서는 필터를 세로로 배치하고 시각·서버·레벨·메시지를 항목별로 읽을 수 있게 한다. 상세는 목록 아래에 표시하고, 상세로 이동 및 목록으로 돌아가기 동작을 제공한다. 정확한 전환 폭·간격·글꼴·색상 토큰은 아래 제안을 출발점으로 프론트와 후속 합의한다.

## 조회와 탐색 동작

| 항목 | 동작 |
| --- | --- |
| 최초 진입 | 최근 15분, 전체 서버, 전체 레벨, 빈 키워드로 조회. 명시적 from/to 전송 |
| 시간 | 발생 시각 기준. 입력과 표시에 UTC를 명시하며 밀리초까지 노출. 시작 포함·종료 제외, from/to 필수, from < to, 최대 24시간. API 입력은 소수 초 0~3자리, 응답은 밀리초 |
| 서버·레벨 | 전체 또는 단일 값 선택. 다중 선택은 첫 MVP에서 제안하지 않음 |
| 키워드 | 메시지 대상 검색. 대소문자 구분 리터럴 부분 일치, 앞뒤 공백 제거, 1~200 Unicode 코드 포인트. 빈 값은 파라미터 생략, 200자 초과는 입력 오류. %, _도 문자로 취급 |
| 조회 적용 | 조회 버튼 또는 필터 폼의 Enter로 적용하고 첫 페이지로 이동. 편집 중인 값과 현재 결과에 적용된 조건을 구분 |
| 입력 오류 | 두 시간값 누락·형식 오류, 시작≥종료, 24시간 초과를 요청 전에 차단하고 해당 입력에 설명. 정확히 24시간은 허용 |
| 초기화 | 필터를 최초 기본값으로 되돌리고 첫 페이지를 조회 |
| 페이지 | 이전·다음 버튼. previousCursor/nextCursor가 null이면 해당 버튼 비활성. 기본 50건 커서 탐색. 번호 이동·총 건수 없음 |
| 정렬 | occurredAt 내림차순. 동률은 eventId 내림차순. 완전한 스냅샷은 보장하지 않음 |
| 새로고침 | 편집 중 값 대신 마지막 적용 조건으로 첫 페이지 재조회. 상대 시간 범위는 실행 시각 기준 재계산, 직접 입력한 절대 범위는 유지. 미적용 입력은 보존 |
| 상세와 재조회 | 조건 적용·초기화·페이지 이동·새로고침 성공 시 선택을 해제. 실패 시 기존 목록과 상세를 유지하고 이전 결과임을 표시 |
| 조회 경합 | 가장 최근 요청 결과만 반영. 이전 응답이 새 결과나 다른 로그 상세를 덮어쓰지 않음 |

목록은 자동으로 삽입되거나 재정렬되지 않는다. 마지막 조회 시각은 화면이 성공적으로 결과를 받은 시점이며 최신 로그 발생 시각이나 수집 지연을 뜻하지 않는다. 최근 15분 밖으로 밀려난 로그는 새로고침 후 사라질 수 있음을 시간 범위로 설명한다.

## 상세 규격

- 발생 시각, 서비스명, 서버 ID, 레벨, 전체 메시지, eventId와 예외 정보를 표시한다. eventId는 식별과 명세 확인용 보조 정보로 둔다.
- stack trace는 원문 개행을 보존하고 고정폭 글꼴로 표시한다. 줄바꿈 전환과 전체 복사 버튼을 제공하며 복사 성공·실패를 알린다.
- 긴 내용은 상세 내부에서 탐색할 수 있게 하되 페이지 전체에 가로 넘침을 만들지 않는다. 서버는 저장 원문을 자르지 않으며 길이·본문 제한 초과는 수집 시 거절한다. 화면 요약만 해제해 원문을 제공한다. 이전의 서버 잘림 응답 가정은 이 확정 기준으로 대체한다.
- 로그 메시지와 trace는 실행 가능한 HTML로 해석하지 않고 텍스트로 표시한다. 합성 예시는 개인정보와 비밀값을 포함하지 않는다.

## 화면 상태

| 상태 | 표시와 동작 |
| --- | --- |
| 최초 목록 로딩 | 목록 영역에 로딩 안내, 결과 없음 문구는 표시하지 않음 |
| 재조회 중 | 기존 결과를 남기되 갱신 중임을 표시. 중복 실행 제어, 마지막 성공 시각 유지 |
| 정상 결과 | 적용 조건, 최신순 목록, 가능한 페이지 이동 제공 |
| 빈 결과 | “조건에 맞는 로그가 없습니다.”와 적용 조건, 시간 범위 변경·초기화 제공. 로그 미수집으로 단정하지 않음 |
| 최초 조회 실패 | “로그를 불러오지 못했습니다.”와 재시도 제공. 내부 오류·비밀값을 그대로 노출하지 않음 |
| 재조회 실패 | 기존 결과와 상세 유지, 이전 조회 결과임을 명시하고 같은 조건 재시도 제공 |
| 상세 미선택 | “로그를 선택하면 상세 내용을 확인할 수 있습니다.” |
| 상세 로딩 | 선택 로그 식별 정보를 유지하고 상세 로딩 표시. 이전 로그 trace를 새 로그 내용처럼 보여주지 않음 |
| 상세 없음·실패 | 없음과 통신 실패를 구분해 안내. 목록 유지, 실패에는 상세 재시도 제공 |
| 예외 없음 | “이 로그에는 stack trace가 없습니다.” exception=null만 정상적인 예외 없음으로 처리. 필드 누락·잘못된 응답은 조회 실패와 구분해 오류 처리 |

## 접근성 기준

- 모든 필터에 보이는 레이블을 제공하고 시간대·입력 오류를 연결한다. 플레이스홀더만으로 의미를 전달하지 않는다.
- 목록은 적절한 표 제목과 열 머리글을 제공한다. 각 행에 키보드로 접근 가능한 상세 보기 버튼을 두고 서버·시각 등 식별 가능한 이름을 제공한다.
- 레벨은 색상과 텍스트를 함께 사용하고 선택 상태·포커스도 색상만으로 구분하지 않는다. 본문 대비 4.5:1 이상, UI 경계·포커스 대비 3:1 이상을 설계 목표로 한다.
- 상세를 명시적으로 열면 제목으로 포커스를 옮기고, 닫으면 실행한 상세 보기 버튼으로 복귀한다. 해당 행이 사라졌다면 목록 제목으로 복귀한다. 패널은 비모달 영역으로 제공하며 포커스를 가두지 않는다.
- 로딩·조회 완료·오류·복사 결과는 보조기기에 알린다. 목록이나 stack trace 전체를 자동 낭독하지 않는다. 새로고침 성공 후 포커스를 임의로 이동하지 않는다.
- 키보드만으로 필터 입력, 조회, 페이지 이동, 상세 열기·닫기, trace 탐색과 복사가 가능해야 한다. 확대와 좁은 화면에서도 필수 정보·동작을 유지한다.

## API에 필요한 데이터와 의존 사항

| 화면 요구 | 필요한 데이터 또는 명세 |
| --- | --- |
| 목록 | eventId, occurredAt, instanceId, level, message, hasException. 원문은 서버 비절단, 화면만 요약 |
| 상세 | eventId, occurredAt, serviceName, instanceId, level, 전체 message, exception과 예외 없음 표현 |
| 시간 조회 | UTC Z 형식, 밀리초 응답, 시작 포함·종료 제외, 두 값 필수·최대 24시간·기본 최근 15분. 과거·미래 허용 범위는 미결정 |
| 필터 | instanceId·level의 허용값 및 선택지 제공 방식, message 키워드 일치 규칙·길이 제한 |
| 페이지 | 이전·다음 가능 여부 또는 동등한 정보, 페이지 크기, 정렬 보조키, 동시 수집 중 일관성. previousCursor/nextCursor 기반. 시작 후 30분 만료를 공유하는 opaque 커서이며 화면에서 해석하지 않음 |
| 상세 식별 | eventId로 상세 조회 |
| 오류 | 입력 오류·조회 실패·상세 없음의 구분, 사용자에게 표시 가능한 메시지와 재시도 조건 |

수집·목록은 /api/v1/logs, 상세는 /api/v1/logs/{eventId}를 사용하며 API 명세의 필드·중복·오류 규칙을 따른다. 서버 선택지는 was-1, was-2, was-3 설정값으로 제공하고 레벨은 enum을 사용한다. 서버는 원문을 자르지 않으며 화면에서만 요약한다. 페이지 탐색 동안 조회 시간·조건을 고정하고 늦게 수집된 로그는 새로고침으로 확인한다.

## 확정 기준과 남은 세부사항

[MVP 분야 간 합의](../decisions/mvp-spec-alignment.md)의 사용자 승인 기준을 적용한다. 시간 조건 필수·최대 24시간과 커서 세부 명세는 백엔드 추가 승인으로 확정됐으므로 이전 미결정 표시는 대체한다. 화면의 정확한 전환 폭·간격·색상·글꼴 토큰 등은 아래 제안과 확인 사항을 따른다. 구현은 초기 선행조건 충족과 별도 요청 후 시작한다.

공통 검토는 was-2 오류 이벤트를 기준으로 세 WAS 혼합 목록, 예외 없음, 빈 결과, 목록·상세 실패, 긴 내용, 동일 시각 페이지 탐색과 키보드 동작을 포함한다. 공통 합성 데이터와 기대 결과는 합의 문서에 정의하며 현재 실행한 검증 결과는 아니다.


## 최신 확정 기준의 화면 적용

- 실패 재시도는 실패한 요청의 절대 from/to·필터·커서를 그대로 사용한다. 편집 중 조건·요청 조건·마지막 성공 조건을 구분한다. 이유는 재시도마다 조사 시간 범위가 바뀌지 않게 하기 위해서다.
- CURSOR_EXPIRED·INVALID_CURSOR·CURSOR_QUERY_MISMATCH에서는 기존 목록·상세를 유지하고 자동 대체 조회하지 않는다. ‘처음부터 다시 조회’는 실패한 탐색 조건·절대 시간을 유지하고 커서만 제거한다. 성공하면 목록·적용 조건을 교체하고 상세를 해제한다. 커서 만료는 최초 탐색 시작 후 30분이며 이후 페이지도 같은 만료를 공유한다.
- 빈 커서 탐색 결과에서는 이전·다음을 비활성화하고 ‘처음부터 다시 조회’를 제공한다. 최초 조회의 정상 0건과 탐색 도중 빈 결과를 구분한다.
- 조회 자동 재시도는 하지 않는다. 비JSON·알 수 없는 오류와 잘못된 성공 응답은 빈 결과로 취급하지 않고 안전한 오류 안내와 수동 복구를 제공한다. 유효한 Retry-After가 있으면 대기를 안내한다. 실제 인프라 응답 형식·제공 범위는 추가 합의 대상이다.
- 기본 50건을 유지한다. 페이지 크기 선택 없이 시작하고 버튼 표시는 ‘이전(더 최신)’·‘다음(더 오래된)’을 제안한다. API 방향을 사용자가 이해하도록 하기 위한 표현이며 프론트 확인이 필요하다.

| 복구 안내 | 목록 바로 위에 안내와 해당 복구 버튼 배치 | 읽던 결과 가까이에서 문제와 다음 동작을 찾게 함 | 프론트: 초점을 빼앗지 않는 상태 알림. 백엔드·인프라: 오류 코드·Retry-After 제공 범위 |
| 반응형 배치 | 검토 시작값은 화면 폭 1,200px 이상에서 목록:상세 약 55:45, 그보다 좁으면 하단 상세 | 밀리초 시각·서버·메시지와 긴 trace의 가독성 확보 | 프론트: 실제 글꼴, 1,200px 경계·좁은 화면·200% 확대 확인 후 조정. 백엔드: 긴 합성 데이터 제공. 확정된 최소 지원 폭은 아님 |
| 스타일 | 밝은 배경 한 테마, 일반 정보는 시스템 글꼴, 시각·식별자·trace는 고정폭. 본문 16px, 목록·trace 14px, 간격 8px 단위를 시작값으로 검토 | 장식보다 긴 내용의 가독성과 일관성을 우선 | 프론트: 한글·영문 글꼴, 대비·확대·포커스 검토. 구체 색상값은 미확정. 백엔드: API 영향 없음 |
| trace 줄바꿈 | 기본 켜기, 끄기 전환 제공. 원문 개행 유지, 복사는 시각적 줄바꿈이 아닌 저장 원문 대상 | 처음에는 가로 스크롤을 줄이고 긴 경로 비교도 지원 | 프론트: 전환 시 읽던 위치·키보드 스크롤·복사 안내. 백엔드: exception=null과 원문 문자열 확인 |
| 공통 검토 사례 | 최소 51건으로 두 페이지, 세 WAS 혼합·동일 시각 경계·예외 없음·긴 내용·만료·404·실패·지연 포함 | 50건 경계와 상태 전환을 같은 기대 결과로 비교 | 프론트: 버튼·초점·복구 기대 결과. 백엔드: 정렬·필터·커서·오류 응답 기대 결과. 성능 검증 규모는 별도 합의 |

복구 문구 제안은 다음과 같다. 실제 발생 상태에 맞는 문구만 사용하며 최초 실패에 ‘이전 결과’를 표시하지 않는다.

- 재조회 실패: ‘조회하지 못했습니다. 이전 결과를 표시하고 있습니다.’ + ‘다시 시도’.
- 커서 만료: ‘탐색 시간이 만료됐습니다. 같은 조건으로 처음부터 조회해 주세요.’ + ‘처음부터 다시 조회’.
- 커서 무효·조건 불일치: ‘탐색 정보를 사용할 수 없습니다. 같은 조건으로 처음부터 조회해 주세요.’ + ‘처음부터 다시 조회’. 만료로 단정하지 않는다.
- 유효한 대기 시간이 있는 경우: ‘잠시 후 다시 시도해 주세요.’와 남은 시간. 대기 종료 후 자동 조회하지 않는다. 시간 변화는 매초 보조기기에 낭독하지 않는다.

공통 기준 was-2 오류 이벤트와 예외 문자열은 [분야 간 합의](../decisions/mvp-spec-alignment.md) 및 API 명세를 사용한다. 어떤 필터에서 어떤 행·상세·버튼·초점이 나와야 하는지까지 후속 검토 시 정한다. 위 51건은 화면 탐색용 제안이며 처리량·지연 목표나 실제 검증 결과가 아니다.

## SSR 최초 로딩·실패·재시도

2026-10-27 사용자 요청으로 추천안을 반영했다. 기존 일반 로딩·오류 상태를 SSR 첫 진입에 구체화한다. [프론트 환경 명세](../contracts/frontend-environment-draft.md)의 채택 기준과 [프론트 연동 명세](../contracts/frontend-integration-draft.md)의 재시도 원칙을 따르며, 아래 화면 표현·복구 연결 제안의 분야 간 합의나 구현을 완료한 것은 아니다.

### 기존 확정 기준

- 첫 요청에서는 Next.js 서버가 최근 15분의 절대 from/to를 한 번 계산하고 Spring Boot 목록 API를 직접 조회해 HTML로 제공한다. 같은 시간 경계·데이터·마지막 성공 시각을 브라우저에 전달하고, 브라우저 준비만으로 첫 조회를 반복하지 않는다. 필터·페이지·상세·수동 갱신은 클라이언트 상태로 관리한다.
- 후속 조회는 Next.js 조회 중계 방향을 따른다. Spring Boot의 `/api/v1/logs`는 유지하며, 브라우저 중계 경로 `/api/logs`는 아직 미합의다. SSR에서는 자신의 중계 경로를 HTTP로 재호출하지 않는다.
- 조회 캐시는 사용하지 않는 프론트 기준을 따른다. 오래된 공유 캐시나 빌드 시점 데이터를 첫 성공 결과로 재사용하지 않는다. 외부 프록시 캐시 설정은 인프라 합의 대상이다.
- SSR 조회 실패도 빈 배열 성공으로 바꾸지 않는다. 정상 성공 응답의 빈 배열만 빈 결과다. 원시 서버 오류·내부 주소·비밀값과 API 내부 stack trace를 화면에 노출하지 않는다.
- 수동 재시도는 실패한 요청의 절대 시간·필터·크기·커서를 유지한다. 첫 조회에는 커서가 없다. 최근 15분 재계산은 별도 새로고침 동작이며, 자동 재시도는 하지 않는다. 입력 오류는 관련 필드로 안내하고 유효한 Retry-After가 있으면 대기를 안내한다.

이 기준의 이유는 SSR과 브라우저가 같은 조사 범위를 이어받고, 오류를 정상 0건으로 오해하지 않으며, 같은 요청 재시도와 최신 범위 조회를 구분하기 위해서다.

최초 실패 화면의 예시는 다음과 같다. 문구와 배치는 제안이다.

```text
로그를 불러오지 못했습니다.
조회 시간: 2026-10-27 03:00:00.000 ~ 03:15:00.000 UTC
[다시 시도]
```

2분 뒤 ‘다시 시도’를 눌러도 예시의 03:00~03:15 범위를 유지한다. 편집 중 필터는 보존하며 재시도에 몰래 적용하지 않는다. 사용자가 변경 조건으로 ‘조회’를 실행하거나 최근 15분을 ‘새로고침’하면 별도 요청으로 구분한다. 늦은 응답이 새로운 요청 결과를 덮어쓰지 않게 하는 기존 기준도 적용한다.

로딩·실패·복구 완료는 보조기기에 알리되 반복 낭독하거나 성공 시 초점을 임의로 이동하지 않는다. 제한된 버튼이 사라져 초점을 잃지 않도록 프론트와 확인한다. 필드 오류의 초점 처리는 기존 입력 검증 기준을 따른다.

SSR·중계의 백엔드 조회 5초, 브라우저 조회 8초는 프론트 환경 문서의 미합의 시작값이다. 화면에 확정 응답 시간이나 SLA로 안내하지 않는다. 백엔드·프론트·인프라가 요청 기한·취소·응답 크기·오류 형식을 합의한 뒤 적용한다.

후속 검토 사례는 SSR 지연·정상 목록·정상 빈 결과·API 실패·잘못된 성공 응답·재시도 성공과 재실패·재시도 중 입력 편집·조작 준비 전 버튼·페이지 자체 실패다. 절대 시간 보존, 성공 시각 표시, 중복 요청과 자동 재시도 없음까지 기대 결과를 맞춘다. 이는 검토 제안이며 지금 실행한 검증 결과가 아니다.

## 분야 간 검토 후 구체화 제안

2026-10-27 사용자 요청으로 디자인 검토 의견을 반영했다. [최신 확정 기준](../decisions/mvp-spec-alignment.md)과 [공통 아키텍처](../architecture.md)는 유지하며, 아래 내용은 [추가 합의 검토안](../decisions/mvp-cross-area-proposals.md)에 대한 디자인의 구체화 제안이다. 문서 반영 승인이 프론트·백엔드·인프라와의 최종 합의나 구현 승인을 뜻하지 않는다. 앞선 표의 미정 사항은 아래 안을 출발점으로 검토하며, 기존 판단 이유는 보존한다.

### 유지하는 확정 기준

SSR의 절대 시간 경계·데이터 인계와 중복 첫 조회 방지, 같은 조건 수동 재시도, 성공 시 상세 해제·실패 시 기존 결과 유지, 비모달 상세와 키보드 접근을 유지한다. API의 기본 50건·size 1~100 지원도 유지한다. 화면에서 50건 고정으로 제공하는 안은 API 제한 변경이 아닌 UI 제안이다.

초기 개발 환경·GitHub·CI·브랜치 보호는 공통 문서의 PR #4·#5 기록으로 선행조건 충족을 확인한 상태다. 이 문서의 조건부 표현은 선행조건이 여전히 미완료라는 뜻이 아니다. 이후 작업 상태 확인과 별도 구현 요청은 필요하며, 이번 문서 수정에서 환경·원격 상태를 재검증하지 않았다.

### 수정·구체화안과 이유

| 항목 | 구체화 제안 | 이유와 합의할 사항 |
| --- | --- | --- |
| 최초 필터·버튼 제한 | 첫 조회가 끝나고 브라우저 조작 준비도 완료될 때까지 필터 편집·조회·페이지 동작 제한. 최초 조회 실패 후 조작 준비가 됐다면 필터 편집 허용 | SSR 초기값과 준비 전 입력의 충돌을 줄인다. 프론트·디자인이 제한 표시·안내·키보드 초점 유지 방식과 준비 완료 판정을 합의 |

| 상세 해제 시 초점 | 목록 성공으로 상세가 닫힐 때 초점이 상세 내부에 있었다면 목록 제목으로 이동. 화면에 남는 유효한 요소에 있다면 유지. 명시적 닫기는 기존 실행 버튼 복귀 규칙 유지 | 제거되는 요소에 초점이 남는 것을 막는다. 일반적인 ‘성공 시 임의 초점 이동 없음’의 예외로 제안하며 프론트와 합의 |

### 구현 전 합의와 향후 검증의 구분

구현 전에는 최초·재조회 중 조작 허용 범위, 진행 중 상세 요청 처리, SSR 실패 조건 인계·중계 재시도·페이지 재진입 구분, 상세 해제의 초점 복귀, 초기 시각 규격과 공통 사례의 기대 결과를 합의한다. 중계 오류·요청 기한·Retry-After 등 화면이 의존하는 규칙은 백엔드·프론트·인프라가 함께 확정한다. 실제 색상값·글꼴·최종 배치 수치는 아직 확정하지 않았다.

향후 구현 후 검증에서는 다음 기대 결과를 같은 합성 사례로 확인한다. 이는 검사 구현이나 실행 결과가 아니다.

- SSR에서 브라우저로 넘어가도 절대 시간 범위가 같고 첫 조회가 중복 실행되지 않는다.
- 재시도 성공·재실패·지연 응답에서 목록·상세·적용 조건이 서로 맞으며, 무효화한 상세 응답은 반영되지 않는다.
- 키보드로 모든 동작이 가능하고, 상세가 제거될 때 초점이 유효한 위치로 복귀한다. 로딩·실패·복구 상태를 알리되 반복 낭독하지 않는다.
- 색상 외 텍스트로 레벨·선택·오류를 식별하고, 대비·좁은 화면·200% 확대·긴 한글/영문 메시지와 trace의 가독성을 확인한다.
- 최소 51건 제안으로 양방향 탐색과 동일 시각 경계, 빈 결과, 상세 404, 커서 만료·무효·조건 불일치 복구를 비교한다. 세 분야가 입력·기대 행·버튼·상세·초점·복구 결과를 함께 정한다. 51건을 성능 규모로 해석하지 않는다.
