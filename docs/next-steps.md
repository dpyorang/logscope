# 다음 진행 제안

2026-11-03 총괄 검토 제안. 기능·배포 실행 승인이 아니며 사용자가 각 채팅에서 개별 지시한다. 기존 MVP 최종 범위와 과거 진행 기록은 보존한다. 아래는 현재 검색·SSE가 연결된 상태에서 중간 점검을 먼저 수행하기 위한 제안이다.

| 순서 | 할 일 | 사용자가 확인할 결과 | 주 담당 |
| --- | --- | --- | --- |
| 1 | 현재 버전 고정과 전체 로컬 중간 점검 | 최신 이미지/DB migration/색인 반영, WAS→수집→SSE→검색→상세 확인 | 총괄 조율, 백엔드·프론트·인프라 |
| 2 | 발견한 막힘만 작은 단위로 수정 | 필요하면 새 로그 안내·50건 제한 문구·검색/실시간 전환 읽기 경험 개선 | 프론트·디자인, 필요한 백엔드 |
| 3 | 개발용 배포 환경과 공개 범위 결정 | 서버/비용/접근 범위/도메인/비밀 주입/접근 제어/DB·ES 비공개/볼륨·복구 계획 | 사용자·인프라, 백엔드 지원 |
| 4 | 명시적 실행 승인 후 배포·확인 | 배포된 화면에서 동일 핵심 흐름과 재시작 후 데이터 보존 확인 | 인프라, 각 분야 |
| 5 | 블로그·포트폴리오 중간 정리 | 문제→선택 이유→실제 코드/화면→검증 한계, README에 실제 배포 주소·화면 보강 | 사용자, 총괄 지원 |
| 6 | 다음 기능을 하나씩 확장 | 과거 검색 페이지/기간 탐색→동적 서버 목록·세 WAS/장애 점검 등 필요 순서 재평가 | 백엔드·프론트·디자인 |

세 WAS와 장애·통합 검증은 기존 MVP의 남은 목표다. 배포 전에 모두 끝낼지 중간 데모 이후로 둘지는 배포 범위와 함께 정하며 자동으로 목표를 제외하지 않는다. 트래픽/지난날 비교·개요·오류 집계·다크 모드는 로그 핵심 흐름 이후 별도 범위로 검토한다. 지금 Kafka/Redis나 모든 운영 기능을 한꺼번에 추가할 필요는 없다.

## 중간 점검 때 볼 것

- 최신 코드가 저장소에 병합된 것과 실제 실행 이미지·DB 적용을 구분한다.
- 샘플 eventId로 생성→중앙 저장→상세를 대조하고 SSE 정지/재개·재연결을 확인한다.
- 검색의 색인 지연·빈 결과·오류·복구를 확인한다. 수신된 모든 로그가 즉시 검색된다고 가정하지 않는다.
- 서버를 중지·재시작해도 DB/로그/체크포인트 볼륨을 삭제하지 않는다.
- 운영 공개 전 인증·네트워크·TLS·비밀·백업/복구를 실제 배포 범위에 맞춰 확인한다. 현재 인증 비활성 ES를 외부 공개하지 않는다.
